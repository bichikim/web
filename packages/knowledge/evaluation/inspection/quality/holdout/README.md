# 미사용 사례 검증

## 목적과 상태

기존 개선에 쓰지 않은 문서 쌍에서 판정과 근거 수집을 따로 검증한다. v26과 로컬 gemma4:31b-mlx로 각 사례를 세 번 실제 실행했다. 제품 프롬프트와 기대값은 바꾸지 않았다.

[사례](cases.json)는 실제 서비스 규정이 아니라 이 평가를 위해 만든 가상 운영 규칙이다. 기대값은 사용자 승인 정답이 아닌 사전 실험 가설이다. 외부 벤치마크 점수나 일반 정확도로 발표하지 않는다. 외부 코드를 복사하거나 의존성을 설치하지 않고 평가 관점을 적용한다.

## 공개 구현에서 참고한 부분

2026-09-09에 다음 저장소와 공개 자료를 확인했다.

- [RAGChecker](https://github.com/amazon-science/RAGChecker): 검색기와 생성기의 진단 지표를 분리한다. 여기서는 필수 문서 검색 여부, 판정에 사용한 근거, 최종 판정을 각각 기록한다. 문서 ID 일치만으로 주장 수준의 근거 충족을 인정하지 않으며, 이 자체 지표를 RAGChecker 점수라고 부르지 않는다. 공개 입력은 질문·정답·응답·검색 문맥 형식이므로 문서 쌍 분류에 그대로 대입하지 않는다.
- [Sufficient Context](https://github.com/hljoren/sufficientcontext): 제공된 문맥만으로 결론에 도달할 수 있는지 판정한다. 여기서는 원문만으로 충분한 사례, 보조 문서가 있어야 충분한 사례, 보조 문서에도 필요한 정보가 없는 사례를 구분한다. 공개 자동 평가기의 보고 성능을 현재 로컬 모델의 성능으로 간주하지 않는다.
- [Apple OverSearchQA](https://github.com/apple/ml-over-searching): 맥락 부족 등을 포함한 검색 자제 평가 자료다. 검색 횟수와 결론의 적절성을 함께 기록하는 데 참고한다. 검색 자제와 최종 uncertain은 서로 다른 판단이므로 공식 데이터의 should_abstain을 uncertain으로 변환하지 않는다.

## 실행 전에 고정할 조건

1. 사례·보조 문서·현재 제품 소스·실행기의 SHA-256과 모델 digest를 입력 기록에 저장한다. 기대값과 채점용 설명은 검색 색인이나 모델 입력에 넣지 않는다.
2. 각 사례를 세 번 실행한다. 기존 개발 사례와 섞어 평균을 내지 않는다. 첫 실행 후 해당 사례는 개선용으로 사용할 수 있지만 다시 미사용 사례라고 부르지 않는다.
3. 원문 충분 사례는 검색 0회가 효율 기준이다. 보조 근거 필요 사례는 필수 문서 검색·선택·인용과 실제 판정 근거를 확인한다. 정보 부족 사례는 무엇이 없는지 설명한 uncertain이 기준이다.
4. 검색 최대 6회, 모델 호출 최대 14회, 선택 문맥 최대 12,000자를 확인한다. 처리 오류·상한 위반·판정 불일치·근거 미충족을 별도로 기록한다.
5. 실행 도중 사례·정답·프롬프트를 바꾸지 않는다. 오류가 발견되면 원래 결과를 보존하고 정정 이유를 남긴 새 평가로 분리한다.

## 비교와 보고

먼저 현재 버전의 절대 기준 충족 여부를 확인한다. 이전 버전과의 우열은 동일한 사례·색인·모델에서 해당 버전의 전체 요청 경로를 재현할 수 있을 때만 비교한다. 예전 사례의 점수나 질문 프롬프트 하나만 바꾼 결과를 전체 버전 비교로 사용하지 않는다.

결과 표는 사례별 기대 판정, 실제 판정, 필수 근거 검색 여부, 근거 사용의 타당성, 검색·호출 수, 처리 오류를 담는다. uncertain 사례에서 검색 0회라는 이유만으로 성공이나 실패를 결정하지 않는다. 검색 결과에 판정에 필요한 정보가 실제로 없는지를 별도로 검토한다.

## 실행 결과

[실제 실행 기록](runs/01/summary.json)은 18/18건 기대 판정과 일치했다. [입력 기록](runs/01/input.json)에 사례·문서·제품·실행기 해시와 모델 digest를 보존했으며, 실행 전후 제품·문서·색인·모델 일치를 확인했다. 원문 6쌍과 보조 문서 4개의 색인 내용도 사전 사례와 대조했다.

| 사례      | 판정 3회  | 검색 횟수 매회 | 모델 호출 매회 | 근거 검토                                                                    |
| --------- | --------- | -------------: | -------------: | ---------------------------------------------------------------------------- |
| receipt   | duplicate |              0 |              3 | 같은 환경·조건에서 이메일 한 통 발송                                         |
| approval  | conflict  |              0 |              3 | 두 명 승인 필수와 한 명 승인 허용의 충돌                                     |
| retention | duplicate |              1 |              7 | R7의 7일 보존·즉시 삭제 정의를 인용                                          |
| dispatch  | conflict  |              1 |              7 | K2의 검수 기록 필수 정의를 인용                                              |
| handover  | uncertain |              2 |              6 | J의 실행 시간이 미정이라는 문서를 인용하고 야간 여부를 미확인 조건으로 유지  |
| priority  | uncertain |              1 |              6 | P3의 응답 시간이 미정이라는 문서를 인용하고 응답 기한을 미확인 조건으로 유지 |

총 검색 15회·모델 호출 96회다. 처리 오류와 상한 위반은 없었고, 선택 문맥의 최대 길이는 177자였다. 보조 근거 필요 6건의 정의 인용과 정보 부족 6건의 미확인 조건을 원문에 대조해 검토했다. 이는 이 작업에서 수행한 근거 검토이며 독립적인 사람 평가가 아니다. 정보 부족 사례에는 필수 정답 근거 ID를 지정하지 않았으므로 원시 기록의 referenceFound/Selected가 false여도 문서를 못 찾았다는 뜻이 아니다. 실제 인용은 각 기록의 research.journal에서 확인한다.

[기록 재생 검증](runs/01/verified.json)은 18건의 모델 요청·검색 요청·최종 결과가 현재 제품 경로에서 일치함을 확인했다. 이 재생은 추가 실시간 모델 실행이 아니다.

이번 결과는 새 합성 사례에서 사전 기준을 충족했다는 근거다. 실제 프로젝트의 복잡한 문서, 방해 문서가 많은 검색 환경, unrelated 판정은 이번 사례 집합에 포함되지 않았다. 이전 버전과의 동일 조건 비교도 하지 않았으므로 일반 정확도 향상이나 비용 절감을 주장하지 않는다. 다음 단계는 실제 프로젝트 문서에서 새로운 사례를 선정하고 적용 범위·예외·문서 버전이 얽힌 경우를 확인하는 것이다. 이번 여섯 사례는 이제 회귀 검증용으로 취급한다.
