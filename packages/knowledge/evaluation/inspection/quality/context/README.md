# 보조 자료 제공 방식 비교

같은 비교 쌍을 발췌만, 관련 원문 직접 제공, 실제 hybrid 검색으로 평가한다. 제품 프롬프트와 모델은 고정한다. 직접 제공은 기존 연결 근거 입력을 사용한다. 발췌 모드의 검색 결과만 비워 두고, 검색 모드는 실제 Ollama 임베딩과 Qdrant를 사용한다. 모델의 사전 지식은 통제할 수 없으므로 발췌만으로 맞힌 답이 근거 활용을 증명하지는 않는다.

운영 사례는 기존 승인 2쌍과 현재 저장소의 관련 전체 문서를 사용한다. 정답이나 실제 제품 문서는 수정하지 않는다. SolidJS 사례는 공식 자료를 짧게 요약한 별도 `.md`와 실험용 요구사항으로 구성한다. 실험용 값과 예상 판정은 평가자가 작성한 가설이며 사용자 승인 golden이 아니다. 모델 입력에 예상 정답은 넣지 않는다.

## 고정한 실험값

[33차 실행](runs/33/summary.json)은 research v21의 출력 일관성 변경을 기존 6쌍의 실제 검색 조건에서 확인했다. 6/6회 기준 일치, 오류 0회로 이전 32차 검색 조건과 동일한 라벨을 유지했다. [대조·재생 검증](runs/33/verified.json)에서 원문·모델·기준·최초 요청이 같았고 당시 v21 코드의 전체 요청·검색·결과가 기록과 일치했다. 이 실행은 기존 18조건 전체의 재실행이 아니다. 변경 원인과 새 HTTP 반복 평가는 [출력 일관성 개선 평가](../transfer/README.md#출력-일관성-개선-평가)에 정리했다.

[34차 v25 실행](runs/34/verified.json)은 5/6건 일치였다. 정리 정책에서 검색 없는 unrelated로 퇴행하여 v25는 채택하지 않았다. v26은 초기 unrelated의 적용 범위를 추가 감사한다. [35차 실제 실행·재생](runs/35/verified.json)에서 정리 정책이 검색 2회 뒤 uncertain으로 회복됐다. 나머지 5건은 [v26 코드의 정확한 요청·결과 재생](../necessity/runs/06.json)으로 확인했으며 새 모델 실행이 아니다. 이 검증 근거를 합친 6건의 검색 8회·모델 호출 41회는 v21과 합계가 같지만, 저장소 선택은 6→7회, 정리 정책은 7→6회로 호출 수가 달라졌다. 전체 경과와 한계는 [전제 감사 실험](../necessity/README.md)에 기록했다.

| 사례            | A의 요구                             | B의 요구                          | 보조 자료 제공 후 예상 |
| --------------- | ------------------------------------ | --------------------------------- | ---------------------- |
| signal-update   | SIG 규칙 적용, 초기값 7, 다시 7 설정 | 구독 계산을 실행해야 함           | duplicate              |
| signal-suppress | 같은 SIG 규칙과 값                   | 구독 계산을 실행하면 안 됨        | conflict               |
| batch-once      | BAT 규칙 적용, 값 1과 5로 변경       | 구독 계산은 두 변경 뒤 한 번 실행 | duplicate              |
| batch-twice     | 같은 BAT 규칙과 값                   | 각 setter 뒤 총 두 번 실행        | conflict               |

SIG와 BAT의 정의는 비교 쌍 밖의 보조 문서에만 있다. 정의가 없는 발췌 모드의 예상은 uncertain이다. 지연 계산의 직접 읽기, 비동기 중단, 초기 실행 횟수는 요구사항에서 제외한다. 수치 7·1·5는 실험값이며 공식 문서의 성능 측정치가 아니다.

공식 페이지 확인일: 2026-09-08. 전체 문서 복제 대신 실험에 필요한 설명만 출처와 함께 요약했다. createSignal 페이지의 기본값 표기와 설명이 일치하지 않아 기본 옵션은 실험하지 않는다. 명시적인 `equals: false`만 사용한다.

[실행값 확인](measure.mjs): 저장소에 설치된 SolidJS 1.9.14의 클라이언트 반응성 런타임에서 signal 재실행 1회, batch 관찰값 `[[1, 5]]`를 확인했다. `node --conditions=browser packages/knowledge/evaluation/inspection/quality/context/measure.mjs`로 재현한다. Node에서 클라이언트 export를 선택한 실험이며 브라우저 UI 테스트는 아니다. 이 결과는 규칙의 실험값을 검증할 뿐 AI의 해석 정확도를 보증하지 않는다.

## 해석

- 직접 제공도 틀리면 검색만의 문제로 볼 수 없다. 실제 요청에 필요한 본문이 들어갔는지도 검사한다.
- 직접 제공은 맞고 검색은 틀리면 필요한 문서의 검색 결과 포함 여부와 실제 읽은 구간을 비교한다.
- 두 방식 모두 맞아도 이 소규모 자료 밖의 일반 정확도나 대규모 검색 품질을 주장하지 않는다.
- 오류·인용·남은 질문·본문 생략·검색 횟수·입력 토큰과 모델 원응답을 기록한다. 캐시와 질문 이력은 재사용하지 않는다.

## 실행 조건

[실행기](run.mjs)는 평가용 Git 저장소와 새 출력 디렉터리를 인자로 받는다. `KNOWLEDGE_COLLECTION`은 `knowledge-context-`로 시작하는 별도 이름이어야 한다. 기존 운영 컬렉션에는 쓰지 않는다. 현재 로컬 모델 `gemma4:latest`를 사용하고 실제 digest를 입력 기록에 남긴다. `solid direct,search`를 추가하면 SolidJS 네 쌍의 직접 제공·검색 조건만 실행한다.

- 1차: [fixture](repository)에 기존 운영 fixture 11개와 현재 `apps/pomo/docs/plan/development/`의 `architecture.md`, `audio-library.md`, `feed-dialogues.md` 전체를 복사했다. 18개 문서, 45개 unit, 본문 14,582자를 색인했다. 복사한 세 원문의 상위 목차 링크 `../development.md`는 포함하지 않아 `missing-document` 진단 3건이 있다. 원문을 수정하거나 목차까지 완전하게 수집한 것으로 간주하지 않는다.
- 2차: 1차 자료에 [signal 측정 기록](measurements/signal.md)과 [batch 측정 기록](measurements/batch.md)만 추가한다. 비교 쌍·예상 판정·제품 프롬프트는 바꾸지 않는다. 실험 후 작성한 측정 근거를 같은 사례에 제공하는 진단이며 독립적인 일반화 평가는 아니다.
- 보조 문서 직접 제공도 제품의 최대 6개 구간·본문 한도를 적용한다. 특히 운영 문서는 전체를 색인했어도 일부 구간만 모델에 들어간다. SolidJS의 단일 공식 요약 문서는 1차 직접 제공에서 생략 없이 전달된 것을 확인했다.
- 검색 후보에는 다른 비교 요구사항도 들어 있다. 필요한 기준 문서가 실제로 검색되고 읽혔는지는 `relevantHits`·`relevantRead`와 요청 본문으로 확인한다. 읽힌 비교 후보를 기준 규칙으로 오인하는지도 원응답을 검토한다.
- 실행별 `input.json`은 색인된 원문과 hash, 쌍, 예상 판정의 승인 구분을 보존한다. 사례별 JSON은 실제 생성 요청과 모델 원응답을 보존한다. 출력 경로는 새 디렉터리를 사용하며 기존 기록을 덮어쓰지 않는다.

## 1차 결과: 공식 설명과 실험 조건

[결과](runs/01/summary.json): SolidJS 네 쌍은 발췌만 제공했을 때 모두 예상대로 uncertain이었다. 기준 문서를 직접 제공하거나 실제 검색으로 읽힌 경우에도 네 쌍 모두 uncertain으로 남았다. 후자의 두 조건은 예상 판정과 각각 0/4 일치했다. 모델 요청 오류는 없었다.

네 쌍 모두 공식 요약 문서가 검색 결과에 포함됐고 실제 재판정 본문에도 생략 없이 들어갔다. 직접 제공과 발췌 조건의 최초 생성 요청 3개는 같았다. 따라서 이 실행에서 기준 문서 검색 누락이나 보조 본문 잘림이 오답의 원인은 아니었다.

[batch-once 직접 제공](runs/01/batch-once-direct.json)에서 모델은 BAT 정의를 인용하면서도, 그 정의와 B의 실행 횟수를 명시적으로 비교하는 설명이 없다는 이유로 질문을 미해결로 남겼다. [signal-update 직접 제공](runs/01/signal-update-direct.json)에서는 같은 값도 갱신한다는 규칙을 읽고도 실행 빈도 설명을 계속 요구했다. 전자는 규칙 적용 문제를 보여 주며, 후자는 갱신과 구독 계산 실행의 연결을 더 명시한 근거로 추가 진단한다.

운영 승인 두 쌍은 세 조건 모두 uncertain으로 허용 정답을 유지했다. 직접 제공에서는 관련 문서의 일부 구간만 선택됐으므로 전체 원문을 모델이 다 읽었다고 말할 수 없다. 검색 조건에서는 영속 저장 호환 계층과 피드 만료 정책 등 관련 원문을 읽었지만 미해결 조건이 남았다. 이 결과를 운영 계약이 실제로 충돌한다거나 충돌하지 않는다는 확정으로 해석하지 않는다.

## 2차 결과: 측정 근거 추가

[결과](runs/02/summary.json): 측정 문서 2개를 더한 20개 문서·47개 unit·본문 15,559자로 비교했다. 1차와 모델 digest·제품 프롬프트 버전·비교 쌍 hash·예상 판정이 같은 것을 확인했다.

| SolidJS 네 쌍 | 공식 설명·실험 조건 | 측정 결과 추가 |
| ------------- | ------------------- | -------------- |
| 직접 제공     | 0/4                 | 0/4            |
| 실제 검색     | 0/4                 | 3/4            |

검색 조건에서 `signal-update`와 `batch-once`는 duplicate, `batch-twice`는 conflict로 예상에 맞게 바뀌었다. `signal-suppress`는 uncertain으로 남았다. 이 결과는 같은 사례의 자료 보강 효과이며 별도 미사용 사례나 일반적인 정확도 향상은 입증하지 않는다. 공식 문서만 단순히 많이 넣는 실험과도 다르다.

[signal-update 직접 제공](runs/02/signal-update-direct.json)은 측정 결과를 인용해 한 번 실행됐다고 `confirmed`에 적고 duplicate를 제안했다. 하지만 이미 답한 질문들을 `remaining`에도 복사했다. 제품은 남은 조건이 있으면 uncertain으로 반환하므로 최종 판정이 uncertain이 됐다. 남은 조건을 무시하도록 제품을 바꾸지 않고 모델이 확인한 질문을 제대로 닫도록 하는 지침 후보를 별도로 검증한다.

3차는 같은 2차 자료에서 `close-answered`를 마지막 실행 인자로 사용한다. 재판정 요청에만 답한 질문은 remaining에 복사하지 말고, 명시된 정의를 실험값에 적용하라는 지침을 추가한다. 정답 라벨을 강제하거나 미해결 조건의 uncertain 처리를 제거하지 않는다. 최초 분류와 질문 생성은 그대로다. 제품 코드는 이 실험 지침을 사용하지 않는다.

## 3차 결과와 다음 판단

[3차 결과](runs/03/summary.json): 직접 제공 조건의 SolidJS 네 쌍은 여전히 0/4였다. 운영 승인 두 쌍은 uncertain으로 2/2를 유지했다. 짧은 재판정 지침 후보는 개선이 없어 채택하지 않았다.

[조건 검증](runs/checks.json): 세 실행에서 총 32조건이 완료됐고 모델 요청 오류는 0건이었다. 모델·비교 쌍 hash·예상 정답은 같았고, 2차는 측정 unit 두 개만 추가됐다. 3차는 2차와 같은 색인 snapshot을 사용했다. 직접 제공에서 후보 적용 전후의 최초 생성 요청 3개와 실제 읽힌 보조 구간이 같고, 재판정 지침만 한 번 교체된 것을 검사했다.

결론: 이 자료에서는 실행 조건과 관찰 결과를 함께 보강한 검색 판정이 0/4에서 3/4로 개선됐다. 그러나 충분한 근거를 읽고도 확인한 질문을 닫지 못하는 응답이 남아 있다. 문서 수만 늘리거나 짧은 지침 하나를 더하는 것으로 해결됐다고 볼 수 없다. 제품 프롬프트는 유지한다. 다음 비교 후보는 같은 자료를 설치된 더 큰 로컬 모델로 평가하는 것이며, 자원 사용 선택을 사용자에게 확인한 뒤 진행한다. 큰 모델이 더 정확하다는 결론은 아직 없다.

## 4차: 승인된 모델 비교

사용자 승인 후 측정 근거를 포함한 같은 컬렉션에서 `gemma4:31b-mlx`로 발췌·직접 제공·검색을 비교한다. 실행기의 마지막 인자로 모델 이름을 받으며 기본값은 기존 `gemma4:latest`다. `original gemma4:31b-mlx`를 사용해 미해결 질문 지침 후보는 적용하지 않는다. 제품 기본 모델은 바꾸지 않는다.

이 비교는 서로 다른 이름·digest의 로컬 모델 구성 비교다. Ollama 모델 목록의 저장 형식도 기존은 `gguf`, 비교 대상은 `safetensors`로 다르므로 결과 차이를 파라미터 수 하나의 효과로 단정하지 않는다. 문서·쌍·예상 정답·요청 지침·검색 예산은 고정하고 실제 요청과 응답을 보존한다.

### 결과

[전체 결과](runs/04/summary.json)와 [비교 조건 검사](runs/04/comparison.json): 6쌍의 18조건 중 17조건이 기존 예상 또는 승인 정답에 맞았다. 요청 오류는 0건이었다. 아래 네 실험 쌍은 사용자 승인 golden이 아니라 기존 실험 가설이다.

| SolidJS 네 쌍 | gemma4:latest | gemma4:31b-mlx |
| ------------- | ------------- | -------------- |
| 직접 제공     | 0/4           | 4/4            |
| 실제 검색     | 3/4           | 4/4            |

큰 모델의 발췌 조건은 네 쌍 모두 uncertain이었다. 근거를 제공한 조건에서는 각 쌍에 질문 하나를 만들고, 실제 인용으로 답한 뒤 미해결 조건을 비웠다. 직접 제공은 추가 검색 0회, 검색 조건은 쌍마다 1회였다. 실제 인용과 이유를 확인했으며, 검색 횟수 감소만을 품질 개선으로 집계한 것은 아니다.

2차와 색인 47개 point·비교 쌍·예상 정답·프롬프트 버전이 같았다. 최초 분류 요청은 모델 이름 외에 같았고, 직접 제공에서 읽힌 SolidJS 근거 집합도 같았다. 질문 생성 결과에 따라 이후 문맥 순서와 검색어는 달라지므로 모든 후속 요청 본문이 동일한 비교는 아니다.

### 운영 사례의 차이

- 저장 수단: 발췌·검색은 uncertain, 직접 제공은 conflict였다. 기존 승인 정답이 두 라벨을 모두 허용하므로 세 조건 모두 기준을 통과했다. 이것을 예외 관계가 새로 입증됐다는 뜻으로 해석하지 않는다.
- 자동 정리 범위: 발췌·검색은 uncertain이었지만 [직접 제공](runs/04/cleanup-scope-direct.json)은 conflict로 확정해 기존 승인 기준을 통과하지 못했다. 모델은 피드 저장소가 정책 적용 범위에 포함되는지 질문한 뒤, 확인 내용에는 두 정책을 나란히 적고 remaining을 비웠다. 저장소 자체의 정리 정책과 기능별 정리의 적용 관계를 충분히 입증했는지는 남은 검토 항목이다.
- 운영 점수는 기존 승인 라벨을 기준으로 한 검증이다. 1차 운영 실행과 이번 실행은 색인 문서 수가 다르므로 검색 결과 차이를 모델 하나의 효과로 비교하지 않는다. 직접 제공도 모델별 질문에 따라 선택된 원문 구간이 달랐으며, 두 운영 문서 전체가 모델에 전달된 것은 아니다.

결론: 명확한 규칙을 적용하고 답한 질문을 닫는 능력은 이 실험에서 개선됐다. 그러나 모호한 운영 범위를 확정한 한 조건이 있어 전면 교체는 보류한다. 제품 기본 모델·프롬프트와 승인 정답은 그대로 유지한다. 다음 검증 대상은 단순 인용이나 정책의 반복 서술을 적용 범위의 해소로 취급하지 않는지 여부다. 이번 실행만으로 다른 자료의 일반 정확도나 반복 실행 안정성을 보증하지 않는다.

실행 시 색인은 `unchanged=47`, 추가 임베딩·metadata 갱신·삭제는 모두 0이었다. 기존 상위 목차 링크 진단 3건에 더해 측정 문서의 `[[1, 5]]` 표기가 문서 링크로 해석되는 진단 1건이 있다. 모델 비교 조건을 유지하기 위해 이번에는 자료를 수정하지 않았고, 해당 표기를 포함한 본문은 입력 기록에 보존했다.

## 5차: pi를 통한 Luna 연결

기존 pi OAuth 인증과 설치된 `@earendil-works/pi-ai` 0.84.3으로 `gpt-5.6-luna`의 JSON 응답을 확인했다. [평가 연결과 재현 조건](pi.md)은 제품 CLI의 기본 모델을 바꾸지 않는다. 새 의존성이나 package.json script를 추가하지 않았다.

[추론 없음 결과](runs/05/summary.json)는 18조건 중 10조건이 기준에 맞았으며 요청 오류는 0건이었다. [비교 검사](runs/05/comparison.json)에서 4차와 문서 47개 구간·6개 비교 쌍·예상 정답·프롬프트 버전이 같고 최초 프롬프트·JSON schema와 검색 한도가 유지됨을 확인했다. 생성 API와 샘플링·출력 상한 처리 차이는 연결 문서에 기록했다. 완전히 같은 생성 설정의 모델 단독 비교는 아니다.

- SolidJS: 발췌 4/4, 직접 제공 0/4, 검색 1/4였다. 실제 검색으로 signal-suppress만 conflict를 선택했다.
- signal-update 직접 제공에서는 실험 S의 실행값을 읽고도 실험 밖의 모든 상황에서 한 번 실행되는지는 모른다는 조건을 남겼다. 비교 쌍의 실험 범위보다 넓은 증명을 요구한 사례다.
- batch-once 검색에서는 누락된 조건을 알고도 검색어를 빈 배열로 반환했다. 검색기가 문서를 놓친 실행이 아니라 검색 요청 자체를 만들지 않은 실행이다.
- 운영 사례는 6조건 중 5조건이 승인 라벨에 맞았다. cleanup-scope 직접 제공은 uncertain으로 바뀌었지만, 발췌는 conflict로 확정해 승인 기준을 통과하지 못했다. 모든 모호한 사례에서 더 신중해졌다고 볼 수 없다.

[비교 검사 실행기](compare.mjs)는 원문·정답·최초 요청의 동일성, 실제 pi 요청의 schema와 추론 설정, 검색 한도, 판정 결과를 검사하고 새 JSON 파일에 기록한다. 실제 결제 내역이나 원격 가중치 동일성을 검증하는 도구는 아니다.

## 6차: Luna medium 추론 비교

5차에서 비교 범위 밖의 증명을 요구하는 응답이 나와, 프롬프트를 바꾸지 않고 `KNOWLEDGE_PI_REASONING=medium`만 추가했다. [전체 결과](runs/06/summary.json)는 18조건 중 15조건이 기준에 맞았으며 요청 오류는 0건이었다. [비교 검사](runs/06/comparison.json)도 통과했다. 아래 점수는 같은 6쌍을 세 방식으로 평가한 조건별 일치 수이며 독립 표본 18개의 일반 정확도가 아니다. SolidJS 네 쌍은 여전히 실험 가설이고, 운영 두 쌍만 사용자 승인 정답을 사용한다.

| 조건                   | gemma4:31b-mlx | Luna none | Luna medium |
| ---------------------- | -------------- | --------- | ----------- |
| SolidJS 발췌           | 4/4            | 4/4       | 4/4         |
| SolidJS 직접 제공      | 4/4            | 0/4       | 2/4         |
| SolidJS 검색           | 4/4            | 1/4       | 3/4         |
| 운영 사례 세 방식 합계 | 5/6            | 5/6       | 6/6         |
| 전체                   | 17/18          | 10/18     | 15/18       |

medium은 batch 두 쌍의 직접 제공·검색 네 조건을 모두 맞혔다. none에서 conflict로 확정한 cleanup-scope 발췌도 uncertain으로 바뀌었으며, 운영 두 쌍은 세 방식 모두 uncertain이었다. 이는 이번 승인 기준과 맞는다는 뜻이지, 운영 충돌을 잘 탐지한다는 증거는 아니다.

남은 실패는 signal-update의 직접 제공·검색과 signal-suppress의 직접 제공이다. [signal-update 직접 제공](runs/06/signal-update-direct.json)은 실험 S의 관찰값을 읽고도 “모든 경우에 적용되는 규범적 SIG 요구사항인지”와 “다른 실행 조건에서도 동일한지”를 남겼다. 이 비교에서는 자료를 찾았는지뿐 아니라 질문의 적용 범위를 비교 쌍 안에 유지하는지가 다음 검증 대상이다. 실험 관찰과 규범의 구분 자체를 없애거나, 미해결 조건을 무조건 닫도록 바꾸지는 않는다.

두 Luna 실행의 모델 요청은 각각 100회·97회였다. medium 응답에는 reasoning 토큰 합계 14,548개가 기록되어 설정 이름만 바뀐 실행이 아님을 확인했다. 요청 실패·출력 상한 초과는 없었다. 비교 쌍·문서 snapshot·승인 파일 불변과 검색 예산도 검사했다. SDK 응답에는 별도의 서버 model snapshot ID가 없으므로 내부 모델 라우팅과 가중치 동일성은 확인하지 못했다.

결론: pi의 기존 ChatGPT OAuth 경로로 Luna를 연결하고 실제 판정 평가까지 실행할 수 있다. 이 자료에서는 medium이 none보다 개선됐지만 큰 로컬 비교군보다 전체 일치 수가 적었다. 따라서 제품 기본 모델·프롬프트는 유지한다. 다음 후보는 Luna medium에서 비교 쌍의 범위를 벗어난 질문을 만들지 않도록 최소 지침을 실험하고, signal 실패와 모호한 운영 사례를 함께 다시 검증하는 것이다. 이번에는 그 지침을 적용하지 않았다.

검증: Wallaby에서 기존 separated·contextual·research 판정 테스트 27개가 통과했다. pi 연결은 실제 schema 응답과 36조건 실행으로 확인했고, 잘못된 모델·지원하지 않는 추론 설정이 네트워크 요청 전에 거부됨을 별도 assertion으로 검사했다. 평가 연결의 모든 분기에 대한 단위 테스트나 만료 OAuth 갱신 실험까지 수행한 것은 아니다. 변경한 실행 코드의 oxlint와 `pnpm format`을 실행했다.

## xhigh·max 추가 비교의 실행 조건

사용자 요청으로 두 추론 강도를 추가했다. 최초 07·08 실행은 출력 상한 집계 문제를 발견해 중단했고, [07 중단 기록](runs/07/status.json)과 [08 중단 기록](runs/08/status.json)을 남겼다. xhigh의 한 응답에서 output 2,637토큰 중 reasoning이 2,289토큰이었다. 비추론 출력은 348토큰인데 기존 2,048 상한을 초과한 것으로 처리됐다. 이는 판정 오답이 아니라 평가 실행기의 집계 제한이다.

09·10부터 비추론 출력(`output - reasoning`, 형식 처리 토큰 포함 가능)에만 기존 상한을 적용한다. 문서 47개 구간·6개 쌍·프롬프트·정답·검색 한도는 유지한다. 과거 none·medium의 197개 요청에 새 집계 기준을 적용해 모두 상한 이내임을 확인했다. 과거 판정 기록을 다시 쓰거나 점수를 수정하지 않았다. 이전 실행과 자원 제한까지 완전히 같은 비교는 아니며, 서버에 토큰 상한을 설정할 수 없다는 제약은 여전하다.

max의 [직접 제공](runs/10/signal-update-direct.json)과 [검색](runs/10/signal-update-search.json)은 재판정 요청이 각각 약 120초에 중단됐다. 결과는 `inspection-research-unavailable`이며 실제 pi 오류는 `The operation was aborted due to timeout`이다. max의 판정 품질을 오답으로 확정할 수 없어 [실행을 중단](runs/10/status.json)하고 사용자에게 요청당 5분으로 늘릴지 질문했다. 전체 18조건의 점수로 집계하지 않는다.

토큰 집계 회귀 테스트 9개는 Vitest에서 통과했고 해당 함수의 문장·분기·함수·줄 커버리지는 100%였다. 루트 단위 테스트 수집에 knowledge 평가 경로를 추가했으며, 기본 Vitest 설정으로 새 테스트와 기존 판정 회귀 테스트 총 36개가 통과했다. Wallaby는 이 평가 폴더 테스트를 수집하지 못해 Vitest로 검증했다.

### xhigh 최종 결과

[09 전체 결과](runs/09/summary.json)는 18조건 중 14조건이 기준에 맞았고 요청 오류는 0건이었다. [medium과의 비교 검사](runs/09/comparison.json)에서 문서·쌍·정답·최초 프롬프트·schema·검색 한도 불변을 확인했다. 실제 요청 99회의 `reasoning.effort`는 모두 xhigh였다.

| 조건                   | Luna medium | Luna xhigh |
| ---------------------- | ----------- | ---------- |
| SolidJS 발췌           | 4/4         | 4/4        |
| SolidJS 직접 제공      | 2/4         | 1/4        |
| SolidJS 검색           | 3/4         | 3/4        |
| 운영 사례 세 방식 합계 | 6/6         | 6/6        |
| 전체                   | 15/18       | 14/18      |

- 개선: signal-suppress 직접 제공은 uncertain에서 예상한 conflict로 바뀌었다.
- 퇴행: batch-once·batch-twice 직접 제공은 각각 duplicate·conflict에서 uncertain으로 바뀌었다. “제시된 문맥이 모든 별도 조건이나 예외를 포괄하는지” 또는 “별도의 예외·우선 규정이 존재하는지”를 미해결 조건으로 남겼다.
- 동일한 실패: signal-update 직접 제공·검색은 여전히 uncertain이었다.
- 운영 사례는 모두 uncertain으로 승인 라벨과 맞았다. 실제 운영 충돌 탐지 능력을 검증한 결과는 아니다.

추론 토큰은 medium 14,548개에서 xhigh 59,151개로 늘었다. 조건별 경과 시간 합계는 각각 약 10.6분·24.1분이었다. 실행 시점과 동시 요청 상황이 달라 정밀한 속도 비교로 해석하지 않는다. 토큰 수는 SDK가 보고한 사용량이며 실제 구독 청구액이 아니다.

결론: 이번 소규모 단일 실행에서는 xhigh로 높여도 전체 기준 일치 수가 개선되지 않았다. 추론을 많이 쓰는 것과 비교 범위 안에서 미해결 질문을 적절히 닫는 것은 별개로 검증해야 한다. 기본 모델·추론 설정·판정 프롬프트는 바꾸지 않았다. max는 시간 제한 때문에 전체 판정 품질을 비교하지 못했으며, 요청당 5분으로 늘릴지 사용자 선택을 기다린다.

## 11차: 로컬 모델의 판단 완료 기준

사용자가 로컬 Gemma를 유지하며 판단 기준을 개선하는 방향을 승인했다. `bounded-scope`는 [평가 실행기](run.mjs)에서 재판정 요청에만 덧붙이는 후보이며 제품 프롬프트는 바꾸지 않는다. 비교 쌍에 명시된 조건에 답했으면 질문을 닫되, 정책이 해당 행위에 적용된다는 연결 근거가 없으면 미해결 조건을 남기도록 지시한다. 언급되지 않은 가상의 예외까지 모두 없다고 증명하도록 요구하지 않는다.

4차와 같은 `gemma4:31b-mlx` 이름·digest, 문서, 비교 쌍, 정답과 검색 한도로 실행한다. 모델 기본값이나 승인 정답은 수정하지 않는다. [비교 검사](compare.mjs)의 마지막 인자 `assessment`는 모델·자료·최초 요청의 동일성과 재판정에만 후보 지침이 추가됐는지 검사한다. 후속 질문과 검색 결과가 달라질 수 있으므로 후속 요청 전체나 동적 schema enum이 동일하다고 보증하지 않는다.

### 응답 일관성 오류

[batch-twice 검색 응답](runs/11/batch-twice-search.json)은 BAT 규칙을 검색하고 인용했지만 `remaining`을 비운 채 `kind: uncertain`을 반환했다. 이유에는 한 번 실행하는 규칙과 두 번 실행하는 요구가 충돌한다고 적었다. 자료 검색 실패나 시간 초과가 아니라 답한 내용과 최종 판정의 불일치다. [기존 검사](../../../../src/inspection/inquiry.ts)는 미해결 조건 없는 uncertain을 `invalid-inquiry-findings`로 거부했다. 검사나 정답을 완화하지 않으며 이 조건은 성공으로 집계하지 않는다.

### 결과와 채택 여부

[전체 결과](runs/11/summary.json)는 18조건 중 17조건 일치, 응답 일관성 오류 1건이었다. [4차와의 비교 검사](runs/11/comparison.json)에서 같은 모델 이름·digest, 47개 문서 구간, 비교 쌍·정답, 최초 요청·schema와 검색 한도를 확인했다. 재판정 요청에만 후보 지침을 추가했고 그 외 단계의 지침 앞부분과 생성 설정도 비교했다. 후속 질문이나 동적 schema 전체의 동일성 검사는 아니다.

| 조건                   | 기존 지침 | bounded-scope |
| ---------------------- | --------- | ------------- |
| SolidJS 발췌           | 4/4       | 4/4           |
| SolidJS 직접 제공      | 4/4       | 4/4           |
| SolidJS 검색           | 4/4       | 3/4, 오류 1건 |
| 운영 사례 세 방식 합계 | 5/6       | 6/6           |
| 전체                   | 17/18     | 17/18         |

[자동 정리 직접 제공](runs/11/cleanup-scope-direct.json)은 conflict에서 uncertain으로 바뀌어 승인 기준에 맞았다. 같은 저장소를 사용한다는 사실을 정책 적용 관계가 확인된 것으로 처리하지 않고, 피드 대화 저장소가 해당 정책의 적용 범위에 포함되는지 질문을 남겼다. 기존 실행과 같은 보조 문서 6개 구간을 읽었다. 반대로 배치 검색은 기존 성공 조건에 오류가 생겼다. 저장 수단 직접 제공의 conflict→uncertain은 둘 다 승인 정답이므로 개선으로 집계하지 않는다.

결론: 한 운영 사례는 개선됐지만 전체 일치 수가 늘지 않았고 새 오류도 있어 후보를 채택하지 않는다. 제품 기본 모델·판정 프롬프트·버전과 승인 정답은 유지한다. 이번 결과는 같은 6쌍을 세 방식으로 평가한 단일 실행이며 일반 정확도나 반복 안정성을 입증하지 않는다. 다음 검증 대상은 “답한 질문은 닫기”와 “uncertain이면 실제로 남은 비교 조건을 적기”를 함께 지키는지다. 오류 라벨을 자동으로 conflict로 바꾸거나 기존 검사를 완화하지 않는다.

검증: 실제 평가 실행과 비교 assertion이 완료됐으며, 기존 Luna medium→xhigh 비교도 수정한 검사기로 다시 통과했다. 서로 다른 모델을 지침 단독 비교로 지정하거나 서로 다른 지침을 모델 단독 비교로 지정하는 등 잘못된 비교 설정 3건은 거부됐다. 변경한 실행 코드의 oxlint와 `pnpm format`을 실행했다. 제품 코드는 변경하지 않았으며 이번 단계에서 제품 단위 테스트를 다시 실행하지는 않았다.

## 12·13차: 확인 내용과 최종 판정의 일관성

사용자의 다음 단계 진행 요청에 따라 `consistent-scope` 후보를 추가했다. [평가 지침](instructions.mjs)은 미해결 비교 조건이 있으면 `remaining`에 적고, 그렇지 않으면 확인한 규칙에 따라 판정하도록 보완한다. 이미 확인된 양립 불가능성을 uncertain으로 표현하지 않도록 명시한다. 기존 지침 문자열을 옮긴 뒤 03·04·11 입력 기록과 일치함을 검사했다. 제품 지침·검사·정답은 바꾸지 않는다.

[12차 재현 기록](runs/12/replay.json)은 11차 batch-twice 검색 실패의 앞선 모델 응답 4개와 검색 결과를 고정하고 마지막 재판정만 실제 로컬 모델에 다시 요청한 결과다. [재현 실행기](replay.mjs)는 앞선 요청이 저장된 요청과 같은지, 마지막 요청에는 후보 지침만 바뀌었는지 assertion으로 검사한다. 실제 `classifyResearchPair`를 실행하므로 판정·질문·인용의 기존 검사를 그대로 거친다. 다른 오류에도 같은 입력으로 후보를 비교할 수 있도록 기록 경로를 인자로 받되, 지원 범위는 검색 조건의 마지막 재판정으로 제한한다.

재판정은 미해결 조건을 비우고 conflict로 완료돼 기존 예상과 일치했다. 같은 모델 digest임을 확인했지만, 과거 응답을 고정한 진단이므로 전체 검색 흐름의 개선이나 반복 안정성을 입증하지 않는다. 이 결과를 18조건 전체 점수에 합산하지 않는다. 이어지는 13차에서는 앞선 응답을 재사용하지 않고 질문 생성부터 전체 평가를 다시 실행한다.

### 전체 결과와 회귀

[13차 전체 결과](runs/13/summary.json)는 18조건 중 17조건 일치, 응답 오류 0건이었다. [4차와의 비교 검사](runs/13/comparison.json)가 통과했다. 11차와도 모델 이름·digest, 47개 구간·비교 쌍·정답·검색 한도·기존 프롬프트 버전이 같았다. 아래는 같은 6쌍의 조건별 점수이며 독립 표본 18개의 일반 정확도가 아니다. SolidJS 네 쌍은 실험 가설, 운영 두 쌍은 사용자 승인 정답이다.

| 조건                   | 11차 bounded-scope | 13차 consistent-scope |
| ---------------------- | ------------------ | --------------------- |
| SolidJS 발췌           | 4/4                | 4/4                   |
| SolidJS 직접 제공      | 4/4                | 4/4                   |
| SolidJS 검색           | 3/4, 오류 1건      | 4/4                   |
| 운영 사례 세 방식 합계 | 6/6                | 5/6                   |
| 전체                   | 17/18              | 17/18                 |

- 개선: [batch-twice 검색](runs/13/batch-twice-search.json)은 검색부터 새로 실행해도 BAT 규칙을 인용하고 remaining을 비운 뒤 conflict로 완료했다. 11차의 응답 일관성 오류는 이번 전체 실행에서 재발하지 않았다.
- 회귀: [자동 정리 직접 제공](runs/13/cleanup-scope-direct.json)은 uncertain에서 conflict로 바뀌었다. 11차와 같은 보조 구간 6개를 읽었지만 확인 내용에는 자동 정리 금지와 피드의 만료·정리 로직을 나열했을 뿐, 두 정책의 적용 관계를 설명하지 않았다. 그 상태에서 remaining을 비워 승인 기준을 통과하지 못했다.

결론: 응답의 일관성과 질문에 답한 근거의 충분성은 별도로 검증해야 한다. 이번 보완은 앞선 형식 오류를 해소한 실행을 얻었지만 적용 범위 오판을 다시 만들었으므로 채택하지 않는다. 제품 지침·검사·버전과 모델 선택 방식은 유지한다. 다음 실험은 판정 지침을 더 붙이기 전에, 확인 내용이 해당 질문의 적용 관계를 실제로 설명하는지 별도로 검사하는 방식이다. 이 방식의 효과는 아직 검증하지 않았다.

고정 입력 대조에서 [이전 지침](runs/12/control.json)은 같은 `invalid-inquiry-findings` 오류를 재현했다. 실행기는 기록을 저장한 뒤 예상 정답 불일치 assertion으로 종료했다. 모델 연결이나 실행 환경의 실패는 아니다. 기존 결과 파일 덮어쓰기, 지원하지 않는 직접 제공 재현, 알 수 없는 후보 이름도 사전 검사에서 거부됨을 확인했다.

새 지침의 [두 번째 재판정](runs/12/repeat.json)도 conflict로 완료했다. 고정 입력 대조에서는 이전 지침 1회 실패, 새 지침 2회 성공이었다. 이 제한된 재현을 다른 문서나 전체 실행의 안정성으로 확대 해석하지 않는다. 변경한 평가 코드의 oxlint, `pnpm format`, `git diff --check`를 실행했다. 제품 코드와 단위 테스트는 변경하지 않았으며 이번 단계에서 제품 단위 테스트를 다시 실행하지 않았다.

## 14차: 질문과 근거의 별도 검토

사용자 승인 후 [별도 검토 실행기](audit.mjs)로 13차의 확정 판정 9건을 검토한다. 정상 SolidJS 직접 제공·검색 8건을 불필요하게 거부하지 않으면서, 자동 정리 직접 제공의 잘못된 질문 종료를 잡는지 확인하는 실험이다. 기존 uncertain 조건은 대상에서 제외하며 전체 18조건의 재실행 점수로 집계하지 않는다.

같은 로컬 모델 이름·digest로 조건당 한 번만 추가 요청한다. 검토 입력은 원래 비교 문장, 정확한 질문, 모델이 확인했다고 적은 내용과 실제 인용문이다. 기존 최종 라벨·이유와 예상 정답은 보내지 않는다. 출력은 질문별 근거 충분성, 근거 ID, 미해결 조건과 이유이며 기존 판정을 직접 고치지 않는다. 새 검색이나 문서 추가 없이 실제 `generateInspectionJson`의 요청 제한과 응답 검사를 사용하고, 검토 schema와 질문별 인용 ID를 추가 검사한다.

이는 같은 모델의 별도 요청이지 독립적인 사실 판정자가 아니다. 같은 오판을 반복할 수 있으며, 검토 의견은 사람이 승인한 사실이 아니다. 결과는 [실행 기록](runs/14/input.json)에 사용한 지침과 함께 보존한다. 성공하더라도 다음 단계의 실제 검색 루프 통합·새 질문 처리·추가 요청 한도는 별도로 검증해야 한다. 제품 코드·판정 지침·정답은 변경하지 않는다.

### 결과

[14차 결과](runs/14/summary.json): 추가 요청 9회에서 정상 판정 8건의 근거를 모두 충분하다고 평가했고, 자동 정리 오판 1건의 근거는 불충분하다고 평가했다. 검토 응답 오류는 0건이었다. 실제 요청마다 최종 라벨·기존 판정 이유·예상 정답을 보내지 않았고, 질문과 인용문은 저장된 기록과 같음을 assertion으로 검사했다. 기존 입력·결과 snapshot과 모델 digest도 실행 전후 같았다.

[자동 정리 검토](runs/14/cleanup-scope-direct.json)는 확인 내용이 두 규칙을 나열할 뿐, 피드 대화 저장소가 영속 저장 정책 범위에 포함되는지 설명하지 않았다고 지적했다. 검토 결과의 `missing`에는 그 적용 관계가 남았다. 질문이 해결되지 않았다는 후검토 신호를 얻은 것이며, 저장된 conflict 판정을 실제 제품이 uncertain으로 바꾼 결과는 아니다.

이 실험에서는 별도 질문 검토로 목표한 오판을 구분할 수 있었다. 다만 입력은 같은 두 기술 규칙을 공유하는 정상 조건 8건과 운영 오판 1건에 한정되므로 일반적인 검토 정확도나 잘못된 인용 전반의 탐지율을 입증하지 않는다. 문서를 새로 검색하는 흐름이나 추가 검토가 거짓으로 거부하는 다른 사례도 아직 검증하지 않았다.

[15차 반복 대조](runs/15/summary.json)는 같은 지침·모델과 같은 입력으로 signal-update 직접 제공과 자동 정리 직접 제공을 각각 한 번 더 검토했다. 전자는 유지, 후자는 근거 불충분으로 같은 결과가 나왔고 오류는 없었다. 전체 실험의 추가 검토 요청은 11회이며 요청당 기존 120초 제한을 유지했다. `audit.mjs`의 마지막 선택 인자로 저장된 확정 조건만 지정할 수 있으며, 존재하지 않는 조건과 기존 출력 경로는 모델 요청 전에 거부된다.

검토 실행기의 oxlint, `pnpm format`, `git diff --check`를 실행했다. 기존 판정 코드와 단위 테스트는 변경하지 않았고 이번 단계에서 단위 테스트를 다시 실행하지 않았다. 다음 단계는 이 검토 신호를 제한된 추가 호출 안에서 미해결 질문으로 되돌리는 흐름을 연결하고, 실제 검색·재판정 전체를 다시 검증하는 것이다. 이번에는 연결하지 않았다.

## 16차: research v14 통합

사용자 승인 후 별도 검토를 실제 research 검색 루프에 연결했다. [코어](../../../../src/inspection/inquiry.ts)는 기존 형식 검사를 통과하고 모든 질문을 닫으려는 재판정에만 검토를 요청한다. [검토 어댑터](../../../../src/adapters/experimental/audit.ts)는 14·15차와 같은 검토 지침을 사용한다. 이전 `bounded-scope`·`consistent-scope` 재판정 지침은 채택하지 않으며 기존 v13 재판정 지침 자체는 유지한다.

거부된 질문의 확인 내용을 비우고 부족한 조건을 남기되 질문 ID·인용 근거·검색 횟수는 유지한다. 기존 라운드·검색 한도 안에서 다시 조사하며 검토를 반복해서 호출하는 중첩 루프는 없다. 검토는 쌍당 최대 3회 추가되므로 생성 요청 상한은 8회에서 11회로 늘어난다. 추가 응답 시간과 토큰 사용이 생기며, 품질 효과는 실제 통합 실행에서 확인해야 한다.

16차는 4차와 같은 모델 이름·digest, 문서와 정답으로 질문 생성부터 실제 로컬 모델·Qdrant 검색을 실행한다. 변경은 검토 단계와 연구 버전이며 재판정 지침 후보를 덧붙이지 않는다. [통합 검사](verify.mjs)는 과거 입력·최초 요청과의 동일성, 검색·검토 한도, 기록된 응답을 현재 코드에 재생한 결과를 검사한다. 재생 실행은 새로운 모델 측정이 아니다. 실행 도중 검토 당시 질문·답변·인용문을 결과에 보존하는 메타데이터도 보완했으므로, 실제 요청 기록과 메타데이터 보완 후 재생 결과를 별도로 보존한다.

Wallaby에서 기존 관련 테스트 23개를 먼저 확인했고, 실패하는 새 테스트를 추가한 뒤 연결을 구현했다. 이후 관련 46개가 통과했고 검토 코어·어댑터 두 파일의 Wallaby 커버리지는 100%였다. 폴더 단위 Wallaby 실행은 테스트를 수집하지 못해 전체 검증은 Vitest로 전환했으며 53파일·440테스트가 통과했다. 검토 거부 후 재검색·새 근거로 해결·라운드 종료·재시작 예산 보존·질문별 부분 거부·검토 및 인용 오류를 검사했다. CLI의 이전 프롬프트 버전 이력 거부도 검증했다.

### 통합 결과

[실제 실행 결과](runs/16/summary.json)는 18조건 모두 기준과 일치했고 오류는 없었다. 4차의 17/18에서 [자동 정리 직접 제공](runs/16/cleanup-scope-direct.json) 한 조건이 개선됐다. 같은 6쌍을 세 방식으로 실행한 결과이며, SolidJS 네 쌍은 실험 가설이고 운영 두 쌍만 사용자 승인 정답이다. 일반 정확도나 다른 문서에서의 반복 안정성을 입증하지 않는다.

자동 정리 재판정은 기존과 같이 conflict를 제안했지만, 검토가 두 정책의 나열만으로는 피드 대화에 영속 저장 정책이 적용됨을 확인할 수 없다고 거부했다. 해당 질문의 확인 내용을 비우고 적용 관계를 미해결 조건으로 되돌려 최종 uncertain이 됐다. 이어 검색어 생성을 요청했으나 모델이 빈 목록을 반환해 `no-new-queries`로 종료했다. 이 조건에서 실제 추가 검색이 실행됐다고 해석하지 않는다. 검토 거부 이후 새 검색·근거로 해결하는 경로는 회귀 테스트로 검증했으며, 실제 모델이 그 경로까지 수행하는지는 후속 과제다.

[현재 코드 재생 검사](runs/16/verified.json)도 통과했다. 모델 이름·digest, 47개 문서 구간, 비교 쌍·정답과 최초 요청이 4차와 같았다. 모든 실제 생성 요청을 정확히 재현하고 기록된 응답을 재생했을 때 판정과 최종 질문 이력이 같았다. 검토 입력 메타데이터가 추가된 재생 결과는 이 파일에 별도로 남겼다. 검색·원문·검토 한도를 지켰으며 실제 생성 요청은 조건당 5~7회, 검토는 전체 10회였다. 검토가 기존 정상 확정을 거부한 조건은 없었다. 조건별 경과 시간 합계는 약 25.5분이며 동일한 시간대의 통제된 속도 비교는 아니다.

타입 검사, 변경 범위 oxlint, `pnpm format`, 53파일·440개 전체 테스트를 다시 통과했다. 문서 작성 규칙에 따라 사용 계약은 [구현 옆 문서](../../../../src/adapters/experimental/research.md), 평가 근거는 이 디렉터리에 나눠 보존했다. 기본 모델과 승인 정답은 바꾸지 않았다.

## 17차 이후: 검토 거부 후 검색 계획

사용자 승인에 따라 원인 분리, 작은 개선 실험, 근거 유무 대조, 기존 18조건 검증 순서로 진행한다. 16차 자동 정리 직접 제공의 마지막 요청에는 미해결 질문과 빈 시도 이력이 전달됐지만, 검토에서 거부된 conflict 제안도 `Assessment`로 전달됐다. 모델은 빈 검색어 목록을 반환했고 검색기는 호출되지 않았다. 이것만으로 모델 내부의 원인을 단정하지 않는다.

[검색 계획 대조](planning.mjs)는 저장된 마지막 요청과 같은 모델·생성 설정·schema를 사용해 기존 요청, 결론을 제외한 요청, 결론 제외와 첫 검색 지시를 함께 적용한 요청을 비교한다. 질문과 원문은 유지한다. 검색어 생성만의 실험이며 전체 재판정 품질이나 실제 검색 성공으로 집계하지 않는다. 기존 관련 Wallaby 테스트 30개가 통과한 상태에서 시작했다.

후속 검증은 실험용 적용 범위 문서가 있는 경우와 없는 경우를 분리한다. 실험용 문서는 실제 운영 정책이나 승인 정답을 바꾸지 않는 별도 자료로 표시한다. 검색 성공뿐 아니라 인용·최종 판정·미해결 조건·기존 검색 한도를 검사한다. 후보는 이 대조와 기존 18조건의 회귀 검증을 거친 뒤에만 채택한다.

### 17·18차 결과와 발견한 회귀

[17차 검색 계획](runs/17/summary.json)에서 기존 요청은 빈 목록을 다시 반환했다. 결론을 제외한 요청과 첫 검색 지시를 추가한 요청은 같은 검색어를 만들었다. 더 긴 지시는 이 대조에서 추가 이득이 없었으므로 검색 입력의 `Assessment`를 `Original`로 바꾸는 후보만 선택했다. 새 회귀 테스트가 기존 코드에서 실패하고 변경 후 통과했으며, 관련 Wallaby 31개와 전체 Vitest 441개가 통과했다. 테스트는 입력 계약을 검증하며 모델의 검색 품질을 입증하지 않는다.

[18차 후속 실행기](followup.mjs)는 16차의 초기 응답 다섯 개를 고정하고 검색어 생성부터 실제 모델·hybrid 검색을 실행했다. [근거 있음](runs/18/present/result.json)은 별도 컬렉션에 [실험용 적용 조건](followup/coverage.md) 한 구간만 더해 총 48구간을 색인했다. 실제 검색 1회로 이 문서를 찾아 인용했고 검토도 통과해 conflict로 해결됐다. 이는 실험 조건의 판정이지 실제 운영 정책의 새 정답이 아니다.

그러나 [근거 없음](runs/18/absent/result.json)은 기존 47구간에서 검색을 시작한 뒤 다시 conflict로 확정해 승인 기준을 통과하지 못했다. 검토가 공통 저장 방식·형식을 정책 적용 근거로 받아들인 기록을 남겼다. 두 인용 구간은 기존 연결 원문에 있었으며 새 검색 구간이 적용 관계를 명시한 것도 아니었다. 검색을 더 실행한 사실만으로 개선이라고 평가하지 않으며 검색 입력 후보는 아직 채택하지 않는다.

다음 [검토 대조](review.mjs)는 이 실패의 검토 입력을 고정하고, 공통 구현이나 데이터 형식만으로 정책 적용을 확정하지 말라는 한 문장을 추가해 비교한다. 명시적인 실험용 적용 조건을 잘못 거부하지 않는지도 함께 검사한다. 판정 라벨이나 기존 형식 검사를 완화하지 않는다.

### 19·20차 결과와 최종 결정

[19차](runs/19/absent/summary.json)는 기존 지침과 공통 구현·데이터 형식만으로 정책 적용을 확정하지 말라는 보완을 비교했다. 둘 다 같은 근거 불충분 답변을 승인했다. [20차](runs/20/absent/summary.json)는 기존 반복 서술 경고를 정책과 비교 행위를 연결하는 실제 문장을 찾으라는 지시로 대체했지만 역시 승인했다. 출력 형식 오류가 아니라 검토 내용의 오판이다. 두 보완 모두 근거 없음 대조에서 탈락했으므로 명시적 적용 조건 대조나 전체 평가로 확대하지 않았다.

이번 후보를 채택하지 않고 제품 코드·프롬프트 버전·후보 전용 테스트를 v14 상태로 복원했다. 최초 검색 입력 보완이 검색을 시작하게 만들었지만, 그 뒤의 검토가 근거 없는 범위 확정을 막지 못했다. 이 결과만으로 문서량 부족이나 모델 전체 성능을 원인으로 단정하지 않는다. 원문에서 정책이 적용되는 대상과 행위를 구분해 검증하는 방법이 추가 연구 과제로 남았다.

[복원 재생 검사](runs/20/restored.json)에서 16차의 18조건 모두 현재 코드의 요청·최종 판정·질문 이력과 일치했고 호출·검색 한도를 지켰다. 이는 기록된 응답 재생이며 새 모델 실행의 18/18 결과가 아니다. 후보는 앞선 품질 검증 단계에서 탈락했으므로 전체 18조건 실시간 재평가는 하지 않았다. 복원 후 관련 Wallaby 30개와 타입 검사를 통과했고 변경 범위 oxlint와 `pnpm format`을 실행했다. 전체 Vitest 첫 복원 실행은 439개 통과, CLI 인자 오류 검사 1개가 5초 제한을 넘었다. 단독 검사와 전체 재실행으로 추가 확인한다.

해당 CLI 파일은 Wallaby 단독 실행에서 2개 모두 통과했다. 제한 시간과 assertion을 바꾸지 않고 `--maxWorkers=2`로 전체를 재실행해 53파일·440개가 모두 통과했다. 이 대조만으로 시간 초과의 시스템 수준 원인을 단정하지 않으며 제품 코드나 테스트 제한은 수정하지 않았다.

17~20차에서 실제 로컬 생성 요청은 총 12회였다. 18차의 앞선 응답 재생은 여기에 포함하지 않는다. 모델 교체·검색 한도 확대·승인 정답 수정은 없었다. 실험용 48구간 컬렉션은 원래 47구간 컬렉션과 분리해 보존했다. 기록은 덮어쓰지 않았다. [후속 실행기](followup.mjs)는 이후 재현 시 검색 요청 전송 직전에 동일한 입력 후보만 적용하며 제품 코드를 바꾸지 않는다. 기록의 v15는 당시 후보 실행 버전이지 현재 채택 버전이 아니다.

## 21차: 제안 답변과 원문 해석 분리

사용자 승인 후 [검토 대조 실행기](review.mjs)에 원문에서 질문의 답을 확인하는 진단을 추가했다. 기존 답변을 함께 주는 `hypothesis`와 답변을 숨긴 `independent`는 같은 지침·원문·질문·인용 ID·출력 schema를 사용한다. 두 요청의 차이는 제안 답변 제공 여부다. 기존 `original` 요청도 다시 실행해 비교한다. 정책이 적용되는 대상·행위와 저장 수단을 구분하도록 질문하되 예상 정답은 보내지 않는다.

`independent`의 supported는 원문으로 질문에 답할 수 있는지를 뜻한다. 숨긴 제안 답변이 맞는지를 검증한 결과가 아니므로 기존 검토를 대체할 수 없다. 이 실험으로 모델이 제안 답변에 영향을 받는지와 원문만으로도 같은 범위 추론을 하는지 구분한다. 먼저 기존 실패를 대조하고 유효한 후보만 명시적 적용 조건과 기술 규칙 대조로 확대한다. 제품 v14·검색 한도·모델 선택은 바꾸지 않는다.

### 21차 결과와 행위 중심 질문 대조

[21차 결과](runs/21/absent/summary.json)는 세 방식 모두 근거가 충분하다고 판단했다. 답변을 숨긴 조건도 동일 저장 형식·경로와 영속 저장 계층을 연결해 범위를 확정했다. 따라서 이 사례를 제안 답변의 영향만으로 설명할 수 없다. 두 원문 우선 방식은 목표한 구분에 실패해 제품에 반영하지 않는다.

22차는 진단 질문을 “자동 정리 금지가 저장소 자체 동작뿐 아니라 피드 동기화가 수행하는 대화 레코드·WAV 삭제에도 적용되는가?”로 구체화한다. 기존 저장소 범위 질문과 다른 질문이며, 사람이 실험을 위해 작성했다. 원문 우선 지침·인용문·모델은 유지하고 답변은 숨긴다. 정책의 적용 대상만 묻는 질문이 비교 행위까지 충분히 확인하는지 점검하는 진단이다. 자동 질문 생성이나 전체 판정 품질의 개선으로 집계하지 않는다.

[22차 근거 없음](runs/22/absent/summary.json)은 저장소 자체 정리와 피드 동기화 삭제를 연결하는 문장이 없다고 답했다. [근거 있음](runs/22/present/summary.json)은 실험용 문서의 명시적 적용 문장을 근거로 확인했다. 두 조건에서 기대한 구분이 나왔지만 한 운영 사례의 질문을 사람이 구체화한 진단이며 일반적인 검토 정확도를 입증하지 않는다.

23차 [질문 생성 대조](questions.mjs)는 초기 판정까지의 입력을 고정하고 질문 생성만 실제 모델에 요청한다. 기존 지침과 “공통 자원이나 저장 수단뿐 아니라 비교 행위를 규칙이 지배하는지 질문하라”는 일반 지시를 추가한 후보를 비교한다. 사람의 진단 질문이나 새 예상 정답은 보내지 않는다. 성공해도 검색·재판정 전체의 개선과 구분한다.

[23차 결과](runs/23/summary.json)는 기존 지침에서 저장소 범위를 물었고, 후보는 “저장 및 정리 대상”의 저장소 범위를 물었다. 질문에 정리라는 단어가 추가됐지만 여전히 대상의 포함 관계에 초점이 있었다. [24차](runs/24/summary.json)는 금지 규칙이 상대 문장의 구체적인 작업·실행 조건을 지배하는지 묻고 대상 포함 질문으로 대체하지 말라는 지시를 시험했다. 모델이 “피드 대화의 만료 및 정리 작업이 영속 저장 정책에서 금지하는 자동 만료나 자동 정리 정책의 운영 범위에 해당하는가?”라는 질문을 생성했다. 이 질문을 사람이 수정하지 않았다.

[25차 근거 없음](runs/25/absent/summary.json)과 [근거 있음](runs/25/present/summary.json)에 24차 질문을 그대로 전달했다. 전자는 정책과 작업을 연결하는 근거가 없다고 답했고 후자는 실험용 적용 문장을 인용해 확인했다. 21차 independent와 25차 근거 없음의 요청을 대조해 원문·인용문·질문 ID·지침이 같고 질문 문장만 바뀌었음을 assertion으로 검사했다. 두 25차 요청 모두 생성된 질문과 정확히 같고 제안 답변을 포함하지 않았다.

이 결과는 이 사례에서 대상의 포함 여부와 작업에 대한 정책 적용 여부를 구분하는 질문이 유효할 수 있음을 보여 준다. 모든 오판의 원인이나 일반 성능을 입증하지 않는다. 현재 결과는 질문의 답을 원문에서 확인할 수 있는지에 대한 판정이며, 실제 검색·최종 관계 판정까지 실행한 결과가 아니다. 숨긴 제안 답변의 오류 탐지도 별도 과제다. 후속 단계는 이 질문 생성과 검토를 전체 흐름에 연결해 기존 18조건과 새 근거 유무 대조를 함께 검증하는 것이다.

[26차 signal](runs/26/signal/summary.json)과 [batch](runs/26/batch/summary.json)는 기존 정상 질문을 유지하고 제안 답변만 숨긴 검토에서도 명시적 규칙을 확인했다. 기술 사례의 질문 생성 단계를 바꾼 대조는 아니다. 21~26차의 실제 로컬 생성 요청은 총 12회이며 요청·형식 오류는 없었다. 각 실행 전후 모델 이름·digest를 확인했고, 생성 설정·schema를 기록된 요청과 대조했다. 21차 오판은 성공적인 판정으로 집계하지 않는다.

변경은 평가 실행기와 이 디렉터리의 기록에 한정했다. 제품 v14·모델 선택·정답·검색 한도는 유지했다. 실제 요청에서 원문·인용문·질문 ID 보존과 답변 제외 여부, 모델이 생성한 질문의 무수정 전달을 검사했다. 변경 범위 oxlint, `pnpm format`, `git diff --check`를 실행했다. 제품 코드와 단위 테스트는 변경하지 않아 이번 단계에서 제품 단위 테스트를 다시 실행하지 않았다. 문서 작성 규칙에 따라 실험의 질문·출력 의미와 미검증 범위를 제품 사용 계약과 분리해 남겼다.

## 27차 이후: 행위 질문의 전체 흐름 통합

사용자 승인 후 첫 통합 후보는 24차 질문 지시와 17차의 판정 없는 검색 입력을 연결한다. [질문 생성](../../../../src/adapters/experimental/contextual.ts)은 `questionFocus: operation`을 명시한 호출에만 행위·실행 조건 지시를 추가한다. [research](../../../../src/adapters/experimental/research.ts)가 이를 선택하고, 기본 contextual 호출은 기존 지시를 유지한다. 삭제한 v15 후보 이력과 구분하도록 research 후보 버전은 v16이다.

기존 답변 검토는 유지한다. 25차의 답변 없는 확인은 질문에 답할 수 있는지를 검사했을 뿐 제안 답변의 정확성을 검증하지 않았으므로, 답변 검토를 이를 통해 대체하지 않는다. 우선 질문·검색 입력만 연결한 최소 변경이 충분한지 확인한다. 재판정 지침·검토 지침·검색 및 생성 요청 상한은 바꾸지 않는다.

기존 관련 Wallaby 20개가 통과한 뒤 실패하는 입력 계약 검사를 추가했다. 구현 후 관련 22개와 타입 검사가 통과했다. [후속 실행기](followup.mjs)의 마지막 인자 `full`은 초기 판정부터 모든 모델 요청과 검색을 새로 실행하며 평가용 프롬프트 치환도 하지 않는다. 기존 기본 `replay`와 구분해 기록한다. 근거 없음·있음 대조를 먼저 실행하고, 통과하면 원래 47구간의 18조건을 다시 평가한다. 새 모델·승인 정답 변경·실험 문서의 운영 정책 반영은 하지 않는다.

### 첫 후보 실패와 독립 확인 연결

[27차 전체 실행](runs/27/absent/result.json)은 실패했다. 행위 중심 질문을 생성했지만 기존 답변 검토가 두 규칙의 나열을 승인해 검색 전에 conflict로 끝났다. 실제 생성 5회, 약 152초이며 승인 정답 uncertain과 다르다. 단위 테스트 통과가 판정 품질 통과를 뜻하지 않는다.

[28차 독립 확인](runs/28/summary.json)은 이 실행에서 실제로 인용한 두 구간과 질문을 그대로 사용하되 제안 답변을 제외했다. 피드 정리가 영속 저장 정책의 적용 대상인지 연결하는 설명이 없다고 거부했다. 추가 실제 요청 1회이며, 검색이나 최종 판정을 다시 실행한 결과는 아니다.

이에 v17 후보는 행위 질문·판정 없는 검색 입력에 **독립 근거 확인과 기존 답변 검토를 모두** 연결한다. 독립 확인에는 답변을 보내지 않고, 답변 검토에는 기존과 같은 질문·답변·인용문을 보낸다. 두 요청은 서로의 결과를 받지 않는다. 둘 다 승인해야 질문을 닫으며 `audits[].checks.evidence`와 `checks.answers`에 각각의 판단을 보존한다. 한쪽이 거부하면 그 미확인 조건을 후속 검색으로 전달한다. 응답 형식·인용 오류는 uncertain으로 바꾸지 않고 오류로 반환한다.

검토는 재판정당 두 요청, 최대 세 재판정이므로 생성 요청 상한은 쌍당 14회다. 검색은 기존 2라운드·최대 6검색·추가 본문 12,000자 한도를 유지한다. 평가용 원문·정답·기본 모델은 변경하지 않았다. 원래 답변 검토만 사용하는 호출은 기존 동작을 유지하며, research가 독립 확인을 명시적으로 선택한다.

새 계약 테스트의 실패를 확인한 뒤 구현했다. 관련 Wallaby 59개가 통과했고 검토 코어·어댑터의 해당 실행 커버리지는 각각 100%였다. v17의 실제 근거 없음·있음 대조는 29차로 구분한다. 아직 18조건 재평가를 통과한 후보로 취급하지 않는다.

[29차 근거 없음](runs/29/absent/result.json)은 생성 7회·약 194초에 uncertain을 유지했지만 검색어가 빈 목록이어서 실제 검색을 하지 않았다. 최종 라벨은 맞았으나 `queries.length > 0` 검사를 통과하지 못했다. 이를 검색·재판정 전체의 개선으로 계산하지 않으며 근거 있음 실행도 진행하지 않았다.

v18 후보는 조사한 적 없는 미해결 질문이 있으면 첫 검색어를 요구한다. 구조화 응답도 이 경우 최소 한 검색어를 요구하며, 기존 검색 시도가 있으면 유용한 검색어가 없을 때 빈 목록으로 종료할 수 있다. 모델 대신 검색어나 결론을 만들어 넣지 않으며 잘못된 빈 응답은 `invalid-inspection-queries`다. 검색 횟수·재판정·생성 한도는 v17과 같다. 30차에서 같은 전체 대조를 새로 실행한다.

[30차 근거 없음](runs/30/absent/result.json)은 실제 검색 1회를 수행했으나 후속 독립 확인이 `supported: false`와 빈 `missing`을 함께 반환해 `invalid-inquiry-audit`로 끝났다. 생성 9회·약 263초이며 정답으로 계산하지 않는다. 검토 이유에는 적용 관계가 명시되지 않았다고 적었지만 프로그램이 그 이유를 답변이나 미확인 조건으로 대신 채우지 않았다.

v19 후보는 검토 생성 스키마에서 승인·거부를 구분한다. 승인은 인용 ID 하나 이상과 빈 `missing`, 거부는 비어 있지 않은 `missing`을 요구한다. 기존 응답 검증 계약을 생성용 JSON Schema에도 표현한 변경이며, 해석 오류를 문자열 후처리로 고치지 않는다. 31차에서 다시 전체 흐름을 검증한다. 생성 형식 준수와 의미 판단의 정확성은 별도로 평가한다.

[31차 근거 없음](runs/31/absent/result.json)은 실제 검색 2회 후 uncertain을 유지했고 모든 실행기 검사를 통과했다. 생성 11회·약 366초, 추가 본문 4,237자이며 `no-new-evidence`로 끝났다. 다만 두 재판정 모두 독립 근거 확인은 잘못 승인했고, 답변 검토가 정책 나열만으로는 적용 범위를 답하지 못했다고 거부했다. 독립 확인의 의미 판단 문제가 해결됐다고 주장하지 않는다. 두 검토를 합친 결과가 이 한 실행에서 기준을 지킨 것이며, 추가 근거가 있는 반대 조건과 기존 18조건은 별도로 검증한다.

[31차 근거 있음](runs/31/present/result.json)도 실행기 검사를 모두 통과했다. 생성 10회·약 355초, 검색 1회, 추가 본문 4,347자였다. 연결 근거만 본 초기 검토에서는 답변 검토가 거부했다. 이후 검색에서 합성 조건 문서 `experiment/feed-coverage`를 찾았고, 해당 unit을 최종 질문의 근거로 인용했다. 새 문서가 적용 관계와 예외가 아님을 명시한 뒤 두 검토를 통과해 conflict·`resolved`가 됐다. 질문 ID는 유지됐으며 원래 문서에 이 합성 조건을 반영하지 않았다.

두 실행은 초기 판정부터 모든 요청을 새로 보냈고, 평가용 지침 치환·저장된 응답 재생을 사용하지 않았다. 모델 digest와 각 색인 snapshot은 전후 같았다. 이 대조는 동일한 한 운영 쌍에 합성 문서 하나를 추가한 실험이다. 기존 18조건 회귀 평가는 32차로 구분한다.

### 32차: 기존 조건 회귀와 기록 재생

[실제 실행](runs/32/summary.json)은 18조건 모두 기준과 일치했고 오류는 없었다. 기존 v14도 18/18이었으므로 전체 정답률이 올라간 결과는 아니다. 같은 6쌍의 발췌·직접 제공·검색 비교이며, SolidJS 네 쌍은 실험 가설이고 운영 두 쌍만 사용자 승인 정답이다. 저장 수단의 직접 제공은 기존 conflict에서 uncertain으로 바뀌었지만 두 판정 모두 승인 범위다. 자동 정리 범위는 세 방식 모두 uncertain을 유지했다.

정상 확정 8건은 두 검토가 모두 승인했다. 저장 수단의 직접 제공은 두 검토가 모두 거부했다. 저장 수단의 검색 재판정에서는 답변 검토가 승인했지만 독립 확인이 거부했고, 자동 정리의 직접 제공에서는 반대였다. 검토 하나를 무조건 신뢰하거나 두 단계가 모두 정확하다고 해석하지 않는다. 근거 없음 대조와 자동 정리 직접 제공에서는 독립 확인의 오승인을 기존 답변 검토가 막았다.

[재생 검사](runs/32/verified.json)는 현재 코드가 모든 실제 요청을 그대로 만들고 저장된 응답을 받았을 때, 최종 판정뿐 아니라 검토 기록·선택 원문·질문별 조사 이력을 포함한 research 전체가 같음을 확인했다. 모델 이름·digest, 47구간, 비교 쌍·정답·최초 요청은 16차와 같았다. 원문과 승인 파일도 실행 전후 같았다. 재생은 별도 실제 모델 측정으로 세지 않는다.

실제 생성은 총 114회, 조건당 5~9회였다. 검색 포트 호출은 조건당 최대 2회, 읽은 추가 본문은 최대 4,125자였으며 설정된 생성·검색·본문 상한을 지켰다. 발췌·직접 제공 조건의 검색 포트는 기존 평가 설계대로 빈 결과를 반환한다. 실제 Qdrant 검색은 검색 조건과 31차 전체 흐름 대조에서 수행했다. 조건별 경과 시간 합계는 약 35.1분이며 통제된 속도 비교가 아니다.

최종 Wallaby 관련 66개가 통과했다. 전체 실행에서 CLI 프로세스 테스트 하나가 5초를 넘긴 적이 있으나, 코드나 timeout을 바꾸지 않은 단독 Wallaby 재실행은 2/2였다. 모델 평가를 마친 후 최종 전체 Vitest 실행은 53파일·462개 모두 통과했다. 타입 검사와 패키지 oxlint도 통과했다. 문서 작성 규칙에 따라 사용 계약은 구현 옆 문서에, 후보별 실패·실제 결과·한계는 이 평가 기록에 구분했다.

이번 단계에서 확인한 개선은 **미해결 조건으로 실제 검색을 수행하고, 추가 문서가 적용 관계를 명시할 때 그 문서를 인용해 판정을 바꾸는 흐름**이다. 독립 확인 단독의 품질, 개발에 쓰지 않은 문서에서의 일반화, 전체 흐름의 반복 안정성은 입증하지 않았다. 다른 모델이나 실제 운영 정책으로 결과를 확대하지 않는다.
