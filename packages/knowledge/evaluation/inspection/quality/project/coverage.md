# 질문 충족 검증 후보

[실행기](coverage.mjs)는 기존 실패 기록의 답변 검증 요청에만 미확인 조건을 구분하는 지시를 추가한다. 제품 코드는 변경하지 않는다. 문서 작성·한국어 문장 스킬을 적용해 실험 범위와 결과를 이 문서에 분리해 기록한다.

## 조사와 사전 기준

2026-09-11에 [Sufficient Context](https://github.com/hljoren/sufficientcontext)와 [RAGChecker](https://github.com/amazon-science/RAGChecker)의 저자 공개 문서를 다시 확인했다. 전자는 제공 문맥만으로 질문에 답할 수 있는지를, 후자는 세부 주장별 근거 검증을 구분한다. 이 관점을 질문의 미확인 범위·대안이 해소됐는지 확인하는 지시로 한정해 시험한다. 외부 코드나 데이터셋을 가져오지 않는다.

- desktop: 기존 실패 기록의 입력 모드 질문을 unsupported로 처리하고, 요약표의 적용 범위를 missing에 남겨야 한다.
- retention: 보조 문서가 R7의 정의를 명시한 기존 성공 기록은 supported를 유지해야 한다.
- 사례당 동일 요청을 세 번 실행한다. 기존 요청의 모델 설정·스키마·원문·질문·제안 답·인용을 유지한다. 지시는 두 사례에 동일하다.
- 총 여섯 번의 답변 검증 호출만 한다. 독립 근거 검증과 전체 검색·판정 경로는 실행하지 않으므로 전체 품질 개선으로 해석하지 않는다.
- 두 사례 모두 의미 기준 3/3 통과해야 후속 전체 경로 검증 후보로 남긴다. 판정 불리언만으로 통과시키지 않는다.

## 결과

[실제 실행](runs/09-coverage/summary.json)은 검증 호출 여섯 번을 완료했다. 모델 digest는 실행 전후 같았다. 모든 응답은 제품의 실제 감사 스키마와 파서를 통과했고, 기록된 요청이 사전 입력과 같음을 확인했다. 이 검사는 모델 재실행이 아니다.

| 사례      | supported 기준 | 의미 기준 | 결과                                                                 |
| --------- | -------------- | --------- | -------------------------------------------------------------------- |
| desktop   | 3/3 false      | 0/3       | 적용 모드 대신 ‘추가 확인이 필요한지 여부’를 미확인 사항으로 남겼다. |
| retention | 3/3 true       | 3/3       | R7의 7일 보존·정확히 7일 시점 삭제 정의를 근거로 인정했다.           |

desktop의 missing은 세 번 모두 `determination of whether clarification is needed`였다. 사전 기준은 요약표가 어느 모드에 적용되는지 남기는 것이므로, 실행 기록의 `agrees: true`는 불리언·빈 값 검사만 통과했다는 뜻이다. 의미 기준 통과가 아니다. 후보는 미채택이며 제품 v27을 유지한다.

현재 질문에 ‘확인이 필요합니까?’라는 표현이 포함돼 있고 후보가 그 표현을 문자 그대로 다룬 것은 관찰했다. 그 표현이 실패 원인인지는 분리 실험을 하지 않아 확정하지 않는다. 전체 검색·판정을 실행하거나 비용 개선을 주장하지 않는다.

`runs/08-coverage`는 요청에 붙은 JSON 스키마를 데이터와 함께 파싱해 모델 호출 전에 실패한 준비 기록이다. 파싱 경계를 수정한 뒤 새 출력 디렉터리를 사용했다.

## 직접 질문 대조: 사전 기준

같은 가설의 후속 대조로 위 조사를 재사용한다. `direct` 모드에서는 desktop의 질문 문자열만 ‘규칙 A의 아이콘 아래는 배경 조작을 끈 상태에만 적용되는가, 기본 상태에도 적용되는가?’로 바꾼다. 원문·제안 답·근거·질문 ID·검증 지시·모델 설정·스키마는 유지한다. ID는 기록 비교를 위해 유지하며 실제 질문 생성 경로를 시험하는 것은 아니다. retention 요청은 그대로 둔다.

각각 세 번 실행한다. desktop은 unsupported와 함께 A의 적용 모드를 미확인 사항으로 남겨야 하며, retention은 정의 인용과 supported를 유지해야 한다. 이전 기록과 비교해 변경이 질문 문자열 하나뿐인지 검사한다. 이 실험은 수동 질문 교체의 효과만 확인하며, 자동 질문 생성이나 전체 판정 개선의 증거가 아니다.

## 직접 질문 대조 결과: 미채택

[실행 기록](runs/10-direct/summary.json)의 desktop은 세 번 모두 supported=true를 반환해 의미 기준 0/3건 통과다. 이유는 B에서 기본 상태는 아이콘 위이고 조작을 끈 상태만 아래라는 설명이 A의 적용 범위까지 해소한다는 내용이다. 질문을 직접적으로 바꾸는 것만으로는 해당 사례의 범위 오인이 해소되지 않았다. retention은 정의를 인용해 세 번 모두 supported를 유지했다.

이전 `09-coverage`와 비교해 desktop 요청은 질문 문자열 하나만 다르고 retention 요청은 동일함을 검사했다. 모델도 동일하며 실행 전후 digest가 유지됐다. 여섯 응답 모두 제품 감사 스키마와 파서를 통과했다. 이는 형식 검사이며 의미 기준을 대신하지 않는다.

제품 코드와 질문 생성 지시는 변경하지 않는다. 이 결과로 질문 표현이 전혀 영향을 주지 않는다거나 모델의 일반적 한계라고 단정하지 않는다. 관찰된 실패는 B의 동작 조건을 A의 적용 범위에 대한 근거로 받아들이는 것이다. 후속 개선 방향을 정하기 전 방법론을 다시 조사해야 한다.
