# 적용 범위 귀속 대조

## 조사와 가설

2026-09-11에 [MARCH 저자 구현](https://github.com/jeonghyunpark2002/MARCH), [Tree of Clarifications](https://aclanthology.org/2023.emnlp-main.63/), [Evidence Sufficiency Boundary Training 사전 논문](https://arxiv.org/abs/2609.01687)을 확인했다. 해석별 근거 확인과, 부족한 근거에서 충분한 근거로 바뀌었을 때의 답변 전환을 이번 진단에 참고한다. 모델 학습·외부 패키지·데이터셋은 도입하지 않으며 논문의 성능을 이 제품의 기대 성능으로 사용하지 않는다.

가설은 두 계약을 같은 뜻으로 맞추려는 추론과, 특정 계약에 범위를 귀속하는 근거 확인을 분리하면 기존 오인을 구분할 수 있다는 것이다. [실행기](scope.mjs)는 수동으로 범위 선택지를 고정한 진단용 요청이다. 기존 전체 감사 요청과 비교해 질문 수·제안 답·스키마·지시도 바뀌므로 단일 변수 개선 실험이 아니다. 제품 자동화의 효과나 특정 문장의 인과 효과로 해석하지 않는다.

## 사전 기준

- absent: 기존 원문과 근거만 제공한다. A의 범위는 undetermined, 인용은 비어 있어야 한다.
- off: A가 조작을 끈 상태에만 적용된다는 실험용 문장을 추가한다. off-only와 그 문장의 인용이 필요하다.
- default: A가 기본 상태도 포함한다는 실험용 문장을 추가한다. includes-default와 그 문장의 인용이 필요하다. B와 내용이 다르다는 이유로 A의 범위를 바꾸면 실패다.

추가 문장은 실제 프로젝트 사실이나 수정안이 아니다. 조건 간 원문·질문·기존 근거·모델 설정·프롬프트는 같고 범위 문장만 추가된다. 각 조건을 세 번 실행하고 선택·인용·이유를 검토한다. 답의 선택지를 사람이 제한했으므로 제품 채택 전에 일반 질문과 전체 경로 검증이 필요하다. 제품 v27은 변경하지 않는다.

## 결과

[실제 실행](runs/11-scope/summary.json)은 총 아홉 번의 모델 호출을 완료했다. 모델 digest는 실행 전후 동일했다.

| 조건    | 결과                 | 의미 검토                                                                 |
| ------- | -------------------- | ------------------------------------------------------------------------- |
| absent  | 3/3 undetermined     | B의 모드 동작만으로 A의 범위를 정할 수 없다고 설명했다.                   |
| off     | 3/3 off-only         | 추가한 제한 문장을 그대로 인용했다.                                       |
| default | 3/3 includes-default | 추가한 포함 문장을 그대로 인용했다. B의 동작에 맞춰 범위를 바꾸지 않았다. |

조건 간 원문·질문·기존 근거와 모델 설정이 같은지 검사했다. 요청의 차이는 문맥에 추가한 범위 문장뿐이며, 아홉 결과의 선택과 인용을 기록과 대조했다. absent의 인용은 비어 있고 나머지 인용은 각 추가 문장과 정확히 같았다. 반환값은 실행기의 스키마도 통과했다. 의미 검토는 이 작업에서 수행했으며 사용자 승인이나 독립 평가가 아니다.

세 조건 모두 이번 사전 기준을 충족하므로 후속 후보로 남긴다. 제품에는 반영하지 않는다. 다음 검증에서는 사람이 정한 범위 선택지 없이 일반 감사 스키마로 이 구분을 유지하는지, 기존 성공 사례를 훼손하지 않는지 확인해야 한다. 그 후에야 전체 검색·판정 경로의 품질과 호출 비용을 평가할 수 있다.

## 선택지 제한 제거 대조: 사전 기준

일반 감사 형식으로 옮긴 후보들이 실패했으므로 성공한 `11-scope`부터 차이를 분리한다. 같은 원인 분석의 후속으로 기존 조사를 재사용한다. `free` 모드는 choice 필드의 enum만 문자열로 바꾼다. API format과 프롬프트에 포함된 동일 스키마 양쪽에 반영하며, 지시·질문·문맥·모델 설정은 유지한다. undetermined로 답할 수 있다는 기존 지시는 유지하므로 보류 표현까지 완전히 자유로운 실험은 아니다.

세 조건을 각각 세 번 실행한다. absent는 A의 적용 범위가 미확인이라는 설명과 빈 인용, off/default는 해당 범위의 자유 서술과 추가 문장의 정확 인용이 필요하다. 자유 서술에서는 기존 코드 문자열과 일치하는지로 점수를 매기지 않고 agrees를 null로 기록해 의미 검토와 구분한다. 제품은 변경하지 않는다.

## 선택지 제한 제거 결과

[실제 실행](runs/15-free/summary.json)은 세 조건을 각각 세 번 완료했다. 인용·설명을 함께 검토한 의미 기준은 9/9건 충족했다. absent는 세 번 모두 undetermined와 빈 인용을 반환하며 B의 동작 설명으로 A의 범위를 정할 수 없다고 설명했다. off는 choice를 determined로만 적었지만 정확 인용과 reason에서 조작을 끈 상태에만 적용된다고 설명했다. default는 choice·reason에서 두 상태 모두 적용됨을 설명하고 추가 문장을 정확히 인용했다. choice 필드 단독으로 범위가 구조화되어 반환된 결과는 아니다.

11-scope와 비교해 API format 및 프롬프트에 포함된 스키마에서 choice의 enum만 제거됐음을 검사했다. 원문·질문·문맥·지시·모델 설정은 같고, 모델 digest는 실행 전후 같았다. 아홉 실제 요청이 사전 요청과 일치하고 인용이 각 조건의 추가 문장(없으면 빈 문자열)과 정확히 같은지도 확인했다.

이 사례에서 성공이 정답 선택지 제한에만 의존하지는 않았음을 확인했다. 일반 감사로 옮겼을 때 실패한 원인이 무엇인지는 아직 확정하지 못했다. 다음 대조에서는 성공한 자유 출력·지시를 유지하고 단일 질문 문맥을 질문 목록으로 감싸는 입력 구조 차이를 분리할 수 있다. 제품 반영과 전체 경로 검증은 하지 않았다.

## 질문 목록 대조: 사전 기준

기존 원인 분석의 후속으로 같은 조사를 재사용한다. `list` 모드는 free의 지시·자유 출력 스키마·문서·모델 설정을 유지하면서 입력의 evidence/question만 questions 배열의 한 항목으로 옮긴다. original은 최상위에 둔다. 질문 ID·제안 답·추가 질문은 넣지 않는다. 따라서 일반 감사 입력 전체를 재현하는 실험은 아니다.

같은 세 조건을 세 번씩 실행한다. absent는 A의 범위 미확인 설명과 빈 인용, off/default는 범위를 식별하는 설명과 추가 문장 인용을 요구한다. 요청 비교로 문맥의 감싸기 외에는 변경이 없는지 확인한다. 자유 출력이므로 agrees는 null이며 의미 검토를 별도로 기록한다. 제품은 변경하지 않는다.

## 질문 목록 대조 결과

[실제 실행](runs/16-list/summary.json)은 아홉 번 모두 undetermined와 빈 인용을 반환했다. absent는 A에 적용 범위가 명시되지 않았다는 이유로 3/3건 통과했지만, off/default는 범위 문장이 있는데도 없다고 설명해 각각 0/3건이다. 의미 기준 합계는 3/9이며 이전 평면 입력의 9/9보다 낮았다.

15-free와 요청을 비교해 질문·근거를 questions 배열의 한 항목으로 옮기는 것 외에는 변경이 없음을 검사했다. 두 명시 조건의 scope-control ID와 본문도 실제 요청에 그대로 있었다. 모델 digest는 실행 전후 같았다. 입력 누락으로 설명되는 실패는 아니며, 이번 동일 자료 대조에서 입력 구조 변경과 함께 명시 근거를 사용하지 않는 결과가 나타났다.

이 결과를 목록 구조가 항상 열등하거나 전체 제품 결함의 유일한 원인이라고 일반화하지 않는다. 모델 digest가 같아도 모든 실행 환경 상태가 통제된 것은 아니다. 제품은 변경하지 않는다. 다음 검증은 평면 입력을 실제 감사 경로의 질문별 처리와 연결할 수 있는지, 그때 호출 증가와 다른 사례의 퇴행이 생기는지 확인하는 것이다. 구조 변경을 바로 채택하거나 전체 경로를 고쳤다고 판단하지 않는다.
