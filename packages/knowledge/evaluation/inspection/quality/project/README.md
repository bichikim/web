# 프로젝트 원문 검증

기존 합성 사례의 후속 검증이다. 앞선 [공개 평가 방법 조사](../holdout/README.md)를 재사용한다. 제품 v26의 프롬프트와 검색 상한을 유지한다. 이 사례들은 사용자 승인 정답이 아닌 사전 가설이다.

## 고정 기준

[cases.json](cases.json)에 실제 원문, 파일 경로·행 번호, 허용 판정과 이유를 모델 실행 전에 기록했다. 원문은 고치지 않으며 정답·설명·출처 메타데이터는 검색 색인에 넣지 않는다. 검색에는 원문 쌍과 세 출처 문서의 전체 스냅샷만 넣는다. 문서 자체의 외부 링크는 따라가지 않는다. 문서 사이 관계를 평가하는 것이며, 운영 동작이나 외부 API의 사실성을 검증하는 실험은 아니다.

- audio-owner: 공유 상태와 오디오 단일 소유 계약이 같으므로 duplicate.
- cors-scope: API와 별도 R2 버킷이라는 대상 차이로 unrelated.
- desktop-layer: 요약표의 무조건적인 아이콘 아래와 상세 계약의 기본 아이콘 위가 대립한다. 일반 계약 충돌로 읽는 conflict와 입력 모드 생략을 지적하는 uncertain 모두 허용한다. 특정 모드라고 임의로 확정하는 설명은 허용하지 않는다.

각 사례를 실제 로컬 모델로 세 번 실행하고 전체 요청·응답을 기록한다. 처리 오류와 판정 불일치, 근거의 적절성을 따로 확인한다. 원문만으로 가능한 판단에 검색이 발생하면 횟수를 보고하되 이번에는 검색 0회를 필수 통과 조건으로 두지 않는다. 이 세 사례로 문서 버전 차이나 일반 정확도까지 검증했다고 주장하지 않는다.

## 결과

[실제 모델 실행](runs/01/summary.json)은 3쌍을 각각 세 번 실행했다. 모델은 gemma4:31b-mlx, 제품은 v26이며, 실행 전후 소스·사례·문서·색인·모델 일치를 확인했다. [전체 요청 재생](runs/01/verified.json)도 9건 일치했다. 재생은 추가 실제 모델 실행이 아니다.

| 사례          | 실제 판정 | 판정명 일치 | 설명 검토                                     | 검색 / 모델 호출, 매회 |
| ------------- | --------- | ----------- | --------------------------------------------- | ---------------------- |
| audio-owner   | duplicate | 3/3         | 3/3: 공유 상태·오디오 단일 소유를 근거로 설명 | 0 / 3                  |
| cors-scope    | unrelated | 3/3         | 3/3: API와 R2라는 적용 대상 차이를 설명       | 0 / 3                  |
| desktop-layer | uncertain | 3/3         | 0/3: 모드 조건 대신 잘린 질문을 이유로 제시   | 1 / 6                  |

판정명은 9/9건 허용 범위지만, 설명까지 포함한 사전 기준은 6/9건만 충족했다. 총 검색 3회·모델 호출 36회이며 처리 오류나 상한 위반은 없다. 설명 검토는 이 작업에서 원문과 출력을 대조한 결과이고 사용자 승인이나 독립적인 사람 평가가 아니다. 기존 합성 사례 점수와 합산하지 않는다.

## 재현된 결함

[첫 실행 기록](runs/01/1-desktop-layer.json)의 최초 판정은 uncertain이며 질문 생성은 빈 배열을 반환한다. [연구 어댑터](../../../../src/adapters/experimental/research.ts)는 이 경우 최초 설명의 앞 300자를 질문으로 대신 사용한다. 실제 질문은 `Because Rule B introduces specific conditions (e.g., user`에서 끊긴다. 이후 판정은 문서의 모드 조건이 아니라 질문이 불완전하다는 이유로 uncertain을 반환한다.

세 번 모두 질문 길이가 정확히 300자이고 최초 설명의 앞 300자와 같음을 실행 기록에서 검사했다. 최종 이유도 세 번 모두 질문 절단을 지적한다. 문서가 부족한 상황과 제품이 질문을 훼손한 상황을 구분해야 하므로 이 결과를 품질 통과로 세지 않는다. 원문과 기대값, 제품 코드는 수정하지 않았다.

## 다음 개선을 위한 재조사

반복 실패 후 2026-09-09에 공개 방법을 다시 확인했다.

- [RQ-RAG 원 논문](https://arxiv.org/abs/2404.00610)과 [저자 구현](https://github.com/chanchimin/RQ-RAG)은 명시적 질문 재작성·분해·모호성 해소를 다룬다. 현재 결함에는 잘린 설명 대신 완결된 확인 질문을 만드는 관점만 참고한다. 학습 모델이나 외부 코드를 도입한 것은 아니다.
- [NVIDIA 질문 분해 문서](https://docs.nvidia.com/rag/latest/query_decomposition.html)는 필요한 후속 질문을 만들되 종료 조건과 재귀 상한을 둔다. 단순 질문에는 불필요한 분해를 피하도록 구분한다. 정상 경로에 매번 추가 호출을 넣기보다 질문 누락 경로에 한정하는 후보를 검토한다.
- [ReQueR 공개 구현](https://github.com/newera-xiao/ReQueR)은 별도 학습된 질문 정제 모델을 사용한다. 이번 문자열 절단 결함 때문에 별도 모델 학습까지 도입할 근거는 없으므로 적용하지 않는다.

다음 개선의 통과 조건은 문서 적용 범위를 묻는 완결된 질문과 그 조건에 대한 최종 설명이다. 단순히 절단 길이를 늘리거나 uncertain을 conflict로 바꾸는 것으로 통과시키지 않는다. 정상적인 검색 없는 사례와 기존 보조 근거 사례의 퇴행, 추가 호출 수를 함께 검증해야 한다.

## v27 질문 누락 처리 수정

질문이 없는 초기 uncertain에서만 원문과 전체 판정 이유로 완결된 질문을 생성한다. 기존 300자 설명 절단을 제거하고, 질문별 길이·개수 제한과 중복 검사를 유지한다. 빈 목록·공백·길이 초과 출력은 잘라서 쓰지 않고 invalid-inspection-response로 반환한다. 질문이 이미 있는 경우와 확정 판정에는 이 요청을 추가하지 않는다. 검색 상한과 재판정·근거 검토는 변경하지 않았다.

[실제 재검증](runs/02/summary.json)에서 실패했던 사례를 동일한 모델·색인·원문으로 세 번 실행했다. 모두 uncertain을 유지하면서 이유는 요약표의 '아이콘 아래'가 입력 통과 상태만 뜻하는지 기본 상태도 포함하는지 확인되지 않았다는 내용으로 바뀌었다. 질문 절단을 이유로 한 uncertain은 재발하지 않았다. 이것은 문서 작성자의 의도를 확정했다는 뜻이 아니다.

매회 검색은 1→3회, 모델 호출은 6→7회로 증가했다. 세 번 합계는 검색 9회·호출 21회다. 완결된 질문 두 개를 만들었으며 창 이름의 대응 관계도 질문해 검색이 늘었다. 이번 변경은 설명 품질 수정이지 비용 개선이 아니다. 불필요한 질문을 줄이는 것은 별도 후속 과제로 남긴다.

[수정 경로 3건 재생](runs/02/verified.json), [기존 합성 사례 18건 재생](runs/02/holdout-replay.json), [프로젝트 미변경 6건 재생](runs/02/unchanged-replay.json)에서 요청·결과 일치를 확인했다. 신규 실제 실행은 3건뿐이며 재생 24건을 새 모델 실행으로 세지 않는다. 실제 실행 뒤 테스트 입력과 코드 표현을 정리했으므로 실행 당시 소스 해시는 최종 소스와 다르다. 최종 상태는 요청·결과 재생으로 별도 확인한다.

회귀 테스트는 전체 이유가 재작성 입력에 보존되고, 생성된 질문이 다음 검색 계획에 전달되는지 확인한다. 빈 질문·공백·길이 초과 응답도 거부되는지 검사한다. 단위 테스트의 네트워크 응답은 모의 응답이며, 실제 문장의 품질은 위 모델 기록으로 구분해 검증했다.

최종 검증: Wallaby 대상 50개와 전체 Vitest 54파일·486개가 통과했다. 타입 검사와 소스 lint도 통과했다. 최종 정리 후 [수정 경로 재생](runs/02/final-verified.json), [합성 사례 재생](runs/02/final-holdout-replay.json), [미변경 프로젝트 사례 재생](runs/02/final-unchanged-replay.json)을 다시 확인했다. 재생은 같은 기록의 재확인이지 새로운 독립 표본이 아니다.

## v28 불필요한 확인 질문 축소: 사전 기준

2026-09-09에 [NVIDIA 질문 분해 지침](https://docs.nvidia.com/rag/latest/query_decomposition.html)과 [Sufficient Context](https://github.com/hljoren/sufficientcontext)를 다시 확인했다. 단순한 사실 확인을 불필요하게 분해하지 않고, 제공 문맥으로 답할 수 있는지 구분하는 관점을 기존 재작성 요청에 적용한다. 별도 판별 모델이나 외부 의존성은 추가하지 않는다.

질문 누락 시의 재작성 요청에만 세 조건을 더한다. 원문으로 답할 수 있는 질문을 제외하고, 답에 따라 비교 결론이 달라질 미확인 전제만 남기며, 같은 전제를 묻는 질문은 합친다. 스키마·질문 개수·검색 상한은 유지하고 v27과 같은 원문·모델·색인에서 desktop-layer를 세 번 실행한다.

채택 조건은 요약표의 입력 모드 범위를 묻는 완결된 질문과 타당한 최종 이유를 유지하면서 창 이름 대응 질문을 줄이는 것이다. 검색·호출이 증가하면 비용 개선으로 채택하지 않는다. 실제 문장의 품질은 모델 기록으로 검토하며 프롬프트 문자열 단위 테스트만으로 주장하지 않는다. 기존 통과 경로는 정확한 요청·결과 재생으로 확인하되 새 모델 실행과 구분한다.

## v28 결과: 미채택, v27 유지

[후보 실제 실행](runs/03/summary.json)은 세 번 모두 uncertain이었다. [후보 코드에서 수행한 재생](runs/03/verified.json)도 3건 일치했다. 이 검증은 v27 복원 전에 수행한 v28 기록 검증이다.

| 매회      | v27 | v28 후보 |
| --------- | --: | -------: |
| 질문      |   2 |        1 |
| 검색      |   3 |        2 |
| 모델 호출 |   7 |        8 |

세 번 합계는 v27 검색 9회·호출 21회, v28 검색 6회·호출 24회다. 후보는 창 이름 대응 질문을 없앴지만, 남은 질문이 '두 요구사항이 동일한가'라는 비교 결론 자체를 다시 묻는다. 최종 이유도 그 비교가 미확인이라는 내용이다. 이는 v27의 '요약표가 입력 통과 상태만 뜻하는가'라는 구체적 조건 질문보다 채택 기준에 덜 맞는다. 검색 감소만으로 성공 처리하지 않았다.

후보에서 [합성 18건](runs/03/holdout-replay.json)과 [미변경 프로젝트 6건](runs/03/unchanged-replay.json)의 정확한 요청·결과 재생은 통과했다. 전체 테스트 486개와 타입 검사도 통과했지만, 실제 품질·호출 기준을 대신하지는 않는다. 후보 지시 세 문장과 해당 지시를 검사하는 테스트 변경, 버전 증가를 되돌려 v27을 유지한다. 기존 질문 절단 수정은 유지한다.

다음 후보는 비교 결론을 검색 질문으로 되묻지 않고 구체적인 미확인 사실을 묻도록 해야 한다. 추가 필터 모델을 도입하거나 검색을 강제로 생략하지는 않았다. 이번 실험으로 확인한 것은 한 후보의 한계이며, 질문 축소가 일반적으로 불가능하다는 뜻은 아니다.

복원 후 Wallaby 대상 50개, 전체 Vitest 486개, 타입 검사와 소스 lint가 통과했다. [복원한 v27의 기존 실제 실행 재생](runs/03/restored-verified.json)도 3건 일치했다.

## 사실 질문 후보: 질문 단계에서 미채택

[질문 생성 실험](runs/04-probe/summary.json)은 v27의 원문·전체 판정 이유·출력 스키마·모델 요청을 유지하고, 비교 결론 대신 대상·조건·시점·정의 같은 미확인 사실을 직접 묻는 지침만 추가했다. [실행기](probe.mjs)는 모델 digest를 전후 확인하고 각 응답을 별도 저장한다. 입력 모드 범위 질문을 유지하고 창 이름 대응 확인을 제외한다는 기준은 실행 전 input.json에 기록했다.

세 번 모두 WebView와 background의 대응, 조작 창과 controls의 대응만 확인하는 문장 두 개를 생성했다. 핵심 입력 모드 질문은 없었다. 형식 검사는 통과했지만 의미 기준은 0/3회 통과이므로 전체 검색·판정 단계로 진행하지 않았다. 모델 호출은 질문 생성 3회뿐이며, 이 기록을 전체 경로 검증이나 최종 판정 실패 횟수로 세지 않는다. 제품 버전과 프롬프트는 v27 그대로 유지했다.

반복 실패 뒤 [Sufficient Context의 공개 평가 지침](https://github.com/hljoren/sufficientcontext)과 [RQ-RAG 저자 구현](https://github.com/chanchimin/RQ-RAG)을 2026-09-09에 다시 확인했다. 문맥에서 답할 수 있는지 점검하고 질문을 재작성하는 방법은 참고할 수 있지만, 이번 지침만으로 필요한 조건 선택이 개선되지는 않았다. 다음 가설을 세울 때는 기존에 유효했던 조건을 보존하는지와 불필요한 질문을 줄이는지를 별도 기준으로 검증해야 한다. 이 실험은 초기 이유의 영향이나 모델의 일반 능력 한계를 분리해 검증하지 않았다.

## 기존 질문 유지·제외 실험

2026-09-09에 [Sufficient Context](https://github.com/hljoren/sufficientcontext)의 제공 문맥만으로 답할 수 있는지 판정하는 기준을 재확인했다. [실행기](filter.mjs)는 v27이 이미 만든 질문을 ID로 유지하고, 질문 재작성 없이 유지·제외만 판단한다. 제외하려면 원문 인용을 요구하며 인용이 실제 본문에 존재하는지 검사한다. 인용 문자열이 존재한다는 사실만으로 의미상 타당성을 자동 보장하지는 않는다.

[실제 발췌문 조건](runs/05-filter/summary.json)에서는 세 번 모두 두 질문을 유지했다. 핵심 입력 모드 질문은 보존했지만 질문 감소 기준은 0/3회 충족했다. 모델은 WebView/background와 조작 창/controls의 명시적 연결이 없다고 설명했다. 이 결과만으로 두 이름의 관계가 실제로 다르거나 반드시 별도 질문이 필요하다고 확정할 수는 없다.

필터가 명백한 근거도 무시하는지 구분하기 위해, 별도 합성 대조 입력에만 두 이름이 대응한다는 문장을 추가했다. [대조 조건](runs/06-filter-control/summary.json)에서는 세 번 모두 그 문장을 인용해 창 이름 질문을 제외하고 핵심 입력 모드 질문을 유지했다. 원래 사례·실제 문서·원래 기대값은 변경하지 않았다. 대조 입력은 프로젝트의 실제 사실이나 문서 수정 결과가 아니다.

원래 발췌문 3회와 합성 대조 3회, 총 여섯 번의 필터 모델 호출을 수행했다. 검색·최종 판정은 실행하지 않았고 비용 절감이나 일반 품질 개선을 주장하지 않는다. v27 제품 코드는 유지한다. 창 이름 대응 질문이 원문만으로 명백히 불필요하다는 초기 가정은 충분히 입증되지 않았으므로, 이후 기준에서는 명시적 연결 근거가 있는 조건과 없는 조건을 분리해야 한다. 필터를 제품에 추가하면 호출이 늘 수 있으므로 전체 경로의 비용도 별도 검증이 필요하다.

## v27 실제 문서 재실행: 질문에 답하지 않는 근거 수용

[재실행 기록](runs/07-recheck/summary.json)은 기존 desktop-layer의 문서 스냅샷·색인·모델과 사전 기준을 유지한 실제 실행 세 건이다. 최신 프로젝트 문서를 새로 수집한 실험은 아니다. 제품 코드는 수정하지 않았으며 같은 가설의 후속 검증으로 기존 방법론 조사를 재사용했다. 실행 전후 불변 검사와 [전체 요청·검색·결과 재생](runs/07-recheck/verified.json)을 통과했다. 재생은 추가 모델 실행이 아니다.

세 번 모두 uncertain으로 허용 판정명은 3/3건 일치했지만, 핵심 입력 모드 조건을 최종 이유에 남긴다는 설명 기준은 0/3건 충족했다. 매회 검색 3회·모델 호출 9회이며 처리 오류나 상한 위반은 없다. 이전 v27 실행의 7회보다 호출이 늘었다. 동일 모델·색인이라는 사실만으로 출력 차이의 원인까지 확정할 수는 없다.

[첫 실행](runs/07-recheck/1-desktop-layer.json)의 흐름은 다음과 같다. 나머지 두 실행에서도 같은 의미의 문제가 나타났다.

1. 질문은 ‘A의 아이콘 아래가 입력 통과 상태만 뜻하는지, 기본 상태까지 포함하는지’를 묻는다.
2. 검색은 `docs/reference/source-1.md`의 ‘창 모드 계약’을 찾는다. 해당 문단에는 B의 기본 아이콘 위·입력 통과 시 아이콘 아래 동작이 있다.
3. 확인된 답에는 그 B의 동작 설명이 들어가고, 질문의 `remaining`은 빈 문자열이 된다. 그러나 이 인용은 A 요약표의 적용 범위를 명시하지 않는다.
4. 최종 이유에는 창 이름의 대응 관계만 남고 입력 모드 범위는 빠진다.

이는 관련 문서 검색과 질문에 대한 답변 충족을 구분해야 하는 사례다. uncertain이라는 최종 판정명만으로 통과시키지 않는다. 다음 개선 검토의 대상으로 남기며, 근거가 실제 질문의 미확인 조건을 해소하는지 검증하기 전에 프롬프트나 기대값을 바꾸지 않는다.
