# 일반 감사 형식 대조

[범위 진단](scope.md)의 후속으로 기존 방법론 조사를 재사용한다. [실행기](general.mjs)는 사람이 정한 답 선택지를 제거하고 제품의 `createAuditSchema`와 `parseInquiryAudit`를 사용한다. 제안 답 없이 질문과 근거만 보는 독립 근거 확인 단계의 후보이며 전체 검색·답변 감사 경로가 아니다. 제품 v27은 변경하지 않는다.

## 사전 기준

기존 직접 질문과 동일 원문·근거를 사용한다. 질문 자체는 여전히 수동 대조 질문이므로 자동 질문 생성 개선을 검증하지 않는다. 지시는 특정 창·모드 이름 없이 대상과 관계의 근거를 요구한다.

- absent: supported=false, A의 적용 범위를 missing에 남긴다.
- off: supported=true, 추가한 제한 범위 문장을 인용 ID로 선택하고 그 범위를 reason에 설명한다.
- default: supported=true, 추가한 포함 범위 문장을 선택하고 기본 상태도 포함됨을 설명한다.
- retention: supported=true, 기존 R7 정의를 선택하고 보존 기간·삭제 조건을 설명한다.

범위 문장은 실험용이지 실제 프로젝트 사실이 아니다. 조건당 세 번, 총 12회 호출한다. 네 조건 모두 의미 기준 3/3을 충족해야 후속 후보로 남긴다. 형식·불리언 일치와 이유·인용의 의미 검토는 별개다. 기존 감사 스키마를 쓰더라도 제품 함수 전체를 호출한 검증은 아니다.

## 결과

[실제 실행](runs/12-general/summary.json)은 12회 호출을 완료했다. 모델 digest는 실행 전후 같았으며 모든 반환값은 제품 감사 스키마와 파서를 통과했다.

| 조건      | 불리언 일치 | 의미 기준 | 관찰                                                                                             |
| --------- | ----------- | --------- | ------------------------------------------------------------------------------------------------ |
| absent    | 3/3         | 0/3       | A가 original에 있지만, A 본문이 근거에 없다는 이유를 남겼다. 부족한 적용 범위와 구분하지 못했다. |
| off       | 3/3         | 0/3       | 추가 범위 문장이 아닌 B의 동작 설명만 인용했다.                                                  |
| default   | 3/3         | 3/3       | 추가 범위 문장을 인용하고 기본 상태도 포함됨을 설명했다.                                         |
| retention | 3/3         | 3/3       | 기존 R7 정의를 인용하고 기간·삭제 조건을 설명했다.                                               |

총 의미 기준은 6/12건 충족이며 후보를 제품에 반영하지 않는다. `agrees`는 불리언 일치만 의미한다. 조건에 따라 명시적 근거를 사용하기도 하지만, 전체 기준을 통과하지 못했으므로 선택지 없는 일반 검증으로 이전됐다고 판단하지 않는다.

이 후보는 선택지 제거 외에 일반 스키마·복수 질문을 받을 수 있는 입력 형식·지시를 사용하므로, 이전 성공과의 차이를 선택지 하나의 영향으로 단정하지 않는다. 다음 원인 분석에서는 원문과 인용 근거의 역할 구분, 근거 선택과 의미 판정의 연결을 살펴야 한다. 전체 검색·재판정은 실행하지 않았다.

## 입력·인용 경계 점검

후속 점검은 모델을 새로 호출하지 않고 `12-general`의 12개 실제 요청·응답과 제품 파서를 대조했다.

- 네 조건 모두 `original.left/right`가 사전 입력과 같고, A 본문이 비어 있지 않음을 확인했다. 실제 요청도 저장된 사전 요청과 일치했다.
- off/default의 `questions[].evidence`에는 기존 인용과 `scope-control`의 ID·본문이 모두 있었다. 두 조건에서 `scope-control`만 인용한 유효 형식의 응답을 만들어 제품 `createAuditSchema`와 `parseInquiryAudit`에 넣었고 모두 수락됐다. 이 주입은 파서의 허용 여부 검사이며 실제 모델 성공으로 세지 않는다.
- 기록된 모델 응답의 findings와 저장된 findings가 12건 모두 같았다. 즉 이번 실패를 설명하는 입력 누락, 범위 ID 차단, 저장 과정의 응답 변경은 확인되지 않았다.

[감사 스키마·파서](../../../../src/inspection/audit.ts)는 질문 ID, 허용된 인용 ID, 중복, 필수 필드와 검토 결과 조합을 검사한다. 유효한 ID가 가리키는 문장이 질문에 의미상 답하는지는 이 구조 검사로 증명되지 않는다. [조사 경로](../../../../src/inspection/inquiry.ts)는 모델이 선택한 인용을 감사에 넘기며 원문 A·B를 별도 original 필드로 전달한다.

따라서 ‘A가 요청에서 사라졌다’는 설명은 이 기록에 맞지 않는다. A는 original에 있고 인용 목록에는 없다는 역할 차이가 존재한다. absent의 응답은 그 차이를 A의 적용 범위 부재와 구분하지 못했고, off의 응답은 선택 가능한 명시적 범위 근거 대신 기존 B의 동작 근거를 사용했다. 모델 선택의 내부 원인은 확정하지 않는다.

이번 점검에서 제품 수정은 하지 않았다. 입력·저장 결함을 고친 것으로 기록하지 않으며, 후속 실험은 원문 이해와 보조 근거의 답변 충족을 구분하는 입력 계약을 대상으로 삼아야 한다. 구조 변경의 효과는 실제 대조 검증 전까지 가설이다.

## 필드 역할 명시 대조: 사전 기준

[Sufficient Context](https://github.com/hljoren/sufficientcontext)와 [MARCH](https://github.com/jeonghyunpark2002/MARCH)의 저자 공개 문서를 다시 확인했다. 문맥에 포함된 사실과 해소되지 않은 해석을 구분하는 기존 조사 방향을 유지한다. `roles` 모드는 original이 제공된 원문이고 evidence는 인용 가능한 보조 자료임을 설명하는 지시만 추가한다. 원문·질문·근거·스키마·모델 설정은 baseline과 같아야 한다.

같은 네 조건을 각각 세 번 실행한다. 위 사전 기준을 유지하며, absent에서는 A 본문이 없다고 하지 않고 적용 범위를 미확인 사항으로 남겨야 한다. off/default는 scope-control을 선택해야 한다. retention은 정의 인용을 유지해야 한다. 전체 의미 기준을 통과하기 전 제품에 반영하지 않는다.

## 필드 역할 명시 결과: 미채택

[실행 기록](runs/13-roles/summary.json)은 12회 호출을 완료했고 모델 digest는 실행 전후 같았다. baseline의 요청과 비교해 역할 지시만 추가됐으며 문서·질문·스키마·모델 설정은 같음을 검사했다. 모든 응답은 제품 감사 스키마와 파서를 통과했다.

| 조건      | 의미 기준 | 결과                                                          |
| --------- | --------- | ------------------------------------------------------------- |
| absent    | 0/3       | B의 동작 설명으로 A가 조작을 끈 상태에만 적용된다고 확정했다. |
| off       | 3/3       | scope-control을 인용하고 제한 범위를 설명했다.                |
| default   | 3/3       | scope-control을 인용하고 기본 상태 포함을 설명했다.           |
| retention | 3/3       | R7 정의를 인용하고 기간·삭제 조건을 설명했다.                 |

의미 기준 합계는 6/12에서 9/12로 늘었지만, absent가 잘못된 이유로 거부되던 상태에서 근거 없이 승인되는 상태로 바뀌었다. 합계만으로 채택하지 않으며 제품 v27을 유지한다. 역할 지시만으로 명시 근거의 선택과 근거 부재 시 판단 유보를 동시에 만족하지 못했다.

## 인용 사실·가정 분리 후보: 사전 기준

[RefChecker 저자 구현](https://github.com/amazon-science/RefChecker)의 주장 추출·검증 분리를 확인했다. 저장소는 2026-04-08 보관 상태이며 의존성으로 도입하지 않는다. 이번에는 같은 네 조건의 입력을 유지하고 `bridges` 모드에서 facts(인용 ID·원문 그대로의 인용·확인한 내용)와 assumptions(답하기 위해 추가로 필요한 전제)를 출력한다. 기존 역할 지시를 유지하며 스키마·분리 지시만 바꾸는 후보 묶음이다.

조건별 세 번 실행한다. 위 의미 기준에 더해 absent는 A의 적용 범위를 연결하는 미확인 전제를 assumptions에 남겨야 한다. 명시 범위와 R7 조건은 해당 근거를 facts에 인용하고 assumptions는 비어야 한다. 실제 인용 문자열·ID·확정 시 가정 없음은 코드로 검사하지만, 인용과 주장 사이의 의미 관계는 별도로 검토한다. 모델이 가정을 빠뜨릴 수 있으므로 출력 구조 자체를 사실성 보증으로 취급하지 않는다. 제품 변경과 전체 검색은 하지 않는다.

## 인용 사실·가정 분리 결과: 미채택

[실제 실행](runs/14-bridges/summary.json)은 총 12회 호출을 완료했다. 모델 digest는 실행 전후 같았다. 명시 범위 두 조건과 R7은 각 3/3건으로 올바른 사실·인용을 유지했지만, absent는 0/3건이다. absent에서도 B의 동작으로 A의 범위를 확정하고 assumptions를 빈 배열로 반환했다. 의미 기준 합계는 9/12이며 앞선 roles 후보의 근거 없는 승인 문제를 해결하지 못했다.

absent의 세 응답은 추가로 정확 인용 검사에도 실패했다. 줄바꿈을 없앤 B의 문장을 반환해 해당 원문에 그대로 존재하지 않았다. 그 인용을 형식적으로 복원한다고 해도 B의 동작에서 A의 범위를 도출한 의미 오류는 그대로 남는다. 두 실패를 구분하며, 형식 검사로 거부됐다는 사실을 올바른 판단 유보로 세지 않는다.

이 실험은 가정 자기보고 필드만 추가해도 잘못된 연결이 드러날 것이라는 기대를 충족하지 못했다. 제품은 v27 그대로다. 추가 필드가 같은 모델의 오판을 자동으로 교정한다고 볼 수 없으며, 후속 방법을 선택하기 전에 지금까지의 후보 실패와 좁은 범위 선택 실험의 차이를 검토해야 한다.
