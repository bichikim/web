# 후보 7: 분류와 근거 선택 분리

사용자 승인으로 기본 동작을 버전 3으로 복원했다. 후보 6은 [구현·테스트 사본](../../workplace/runs/prompt-6/implementation.json)에 보존했다. 후보 7은 [분리 어댑터](../../../../src/adapters/experimental/separated.ts)이며 현재 CLI·doctor에서 `--inspection-mode separated`로 선택할 수 있다. 아래 기록은 최초 어댑터 단독 실험이며 이후 [CLI 통합 검증](cli/README.md)과 구분한다.

첫 호출은 kind·confidence·reason만 반환한다. 두 번째 호출은 고정된 분류와 원문을 받아 근거 ID만 선택한다. 두 번째 응답은 분류를 바꿀 수 없으며, 원문 구간을 가져온 후 기존 인용 검증을 적용한다. 분류 프롬프트의 정책 문장은 유지하지만 인용 지시와 출력 스키마는 달라졌다.

## 평가 범위

[실행 코드](run.mjs)는 기존 완료 진단에서 선택한 전체 쌍을 같은 좌우 순서로 다시 분류한다. Qdrant에서 읽은 unit 식별자·contentHash·상태를 기존 진단과 대조하고, 실제 입력도 결과에 보존한다. 모델 digest를 실행 전후 확인한다. 정답은 모델에 보내지 않는다. 별도 모델 응답 캐시를 읽거나 쓰지 않는다.

이 결과는 어댑터 실험이며 검색·doctor를 다시 실행한 정상 진단 보고서가 아니다. 기존 baseline 파일을 교체하지 않는다. 합성 55쌍·기존 10쌍·업무 28쌍을 실행하고, 각 자료의 승인 정답 16·4·8쌍만 정확도에 포함한다.

실험 통과 조건은 업무 문서의 인용 오류 없는 완료, 합성 기존 14/16 및 기본 4/4에서 개별 정답 회귀 없음, 캐시 없는 반복 실행이다. 조건을 만족해도 이 작은 고정 자료만으로 일반적인 분류 품질을 보장하지 않는다.

## 결과

같은 모델 digest·후보 구현·원본·정답으로 두 번 실행했다. [첫 실행](01-summary.json)과 [두 번째 실행](02-summary.json) 모두 아래 결과가 나왔다. 전체 93쌍의 분류가 두 실행에서 같았으며 총 186쌍 처리 중 응답·인용 검증 오류는 0건이다. [교차 검증](verification.json)에 원본 payload 해시 재계산과 구현·모델 일치 확인을 기록했다.

| 자료      | 첫 실행                   | 두 번째 실행              | 비교 기준                             |
| --------- | ------------------------- | ------------------------- | ------------------------------------- |
| 합성 16쌍 | [15/16](01-expanded.json) | [15/16](02-expanded.json) | v3의 14/16에서 개별 회귀 없음         |
| 기본 4쌍  | [4/4](01-original.json)   | [4/4](02-original.json)   | v3의 4/4 유지                         |
| 업무 8쌍  | [7/8](01-workplace.json)  | [7/8](02-workplace.json)  | v6의 7/8 유지, 각 전체 28쌍 오류 없음 |

합성 자료의 `staging-undefined-policy`를 uncertain으로 맞혔다. 기존 오답 `complementary-audit`와 업무 자료의 `platform-origins`는 여전히 conflict로 틀렸다. 정답은 수정하지 않았다. v3 업무 문서의 partial 결과와 정확도 차이를 계산하지 않는다.

기본 v3 어댑터가 만드는 요청은 보존된 실제 v3 요청과 프롬프트·스키마·옵션·모델·system까지 같았다. 이는 HTTP를 가로채 요청 본문을 비교한 계약 검증이며 새 v3 모델 평가가 아니다. 기본 버전 상수와 후보 캐시 버전 구분도 테스트했다.

Wallaby 테스트 330건, 패키지 타입 검사와 lint 검사를 통과했다. 후보 어댑터의 실행 커버리지는 100%였다. 중간 전체 실행에서 기존 CLI 테스트 1건이 5초 타임아웃으로 실패했지만, 코드 변경 없이 모델 실행 종료 후 전체 330건이 통과했다. 타임아웃 원인은 확정하지 않았다. `pnpm format`을 실행했다.

## 결정과 다음 단계

분리 후보는 위 어댑터 실험 조건을 통과했다. 기본 동작은 요청대로 v3을 유지하며 후보 7을 자동 채택하지 않는다. v3의 업무 문서 인용 오류가 해결됐다는 뜻도 아니다. 후속 단계에서 후보 7의 별도 버전·캐시 경계를 CLI에 연결했다. 전체 경로의 실행 결과는 [통합 검증 기록](cli/README.md)을 참고한다.

성공 시 모델 생성 호출은 쌍당 두 번이다. 실행 환경 설정은 평가 코드의 로컬 주소를 사용하며 사용자 설정을 변경하지 않는다. 추가 반복은 저장소 루트에서 `node packages/knowledge/evaluation/inspection/runs/prompt-7/run.mjs 03`으로 실행할 수 있다. 기존 번호의 산출물은 덮어쓰지 않는다.
