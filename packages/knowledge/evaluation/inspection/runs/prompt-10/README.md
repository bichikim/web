# 근거 연결 재사용 실측

2026-09-07에 로컬 Ollama `gemma4:latest`와 Qdrant로 검증했다. 근거 저장·재사용은 동작했지만, 승인된 두 사례에서는 검색량 감소나 판정 개선을 확인하지 못했다. 별도 CLI 선택 쌍에서는 검색량이 감소했다.

## 승인 사례 비교

[기존 승인 자료](../../operations/reviewed.json)의 1·2번을 대상으로, 각 사례마다 빈 연결 디렉터리에서 실행한 뒤 같은 디렉터리로 다시 실행했다. v9 입력과 현재 색인 11개 unit 전체가 같은지 확인했다. 모델 digest도 v9와 같았다. 외부 요청은 차단하고 `127.0.0.1:11434`, `127.0.0.1:6333`만 허용했다.

실제 `classifyResearchPair`, hybrid 검색, `readInspectionLinks`·`writeInspectionLinks`, 디렉터리 잠금을 사용했다. 두 쌍은 승인 자료에서 지정했으며 CLI 후보 검색으로 선택한 결과가 아니다. 추가 문서나 정답을 주입하지 않았다.

| 사례             | 실행    | 재사용 unit | 검색 횟수 | 생성 요청 | 입력/출력 토큰 | 소요 시간 | 결과      |
| ---------------- | ------- | ----------: | --------: | --------: | -------------: | --------: | --------- |
| 1 저장 수단      | 첫 실행 |           0 |         6 |         7 |  8,178 / 1,042 |   29.20초 | uncertain |
| 1 저장 수단      | 재사용  |           1 |         6 |         7 |    8,309 / 985 |   25.70초 | uncertain |
| 2 자동 정리 범위 | 첫 실행 |           0 |         6 |         6 |    6,212 / 626 |   18.37초 | uncertain |
| 2 자동 정리 범위 | 재사용  |           3 |         6 |         7 |   10,084 / 899 |   25.56초 | uncertain |

토큰은 Ollama 생성 응답의 `prompt_eval_count`, `eval_count` 합계다. 임베딩 토큰은 포함하지 않았다. 각 조건을 한 번씩만 실행했고 모델 캐시·예열을 통제하지 않았으므로 시간 차이를 성능 개선으로 해석하지 않는다.

- 1번: [입력](storage-backend/input.json), [첫 실행](storage-backend/cold.json), [재사용](storage-backend/warm.json).
- 2번: [입력](cleanup-scope/input.json), [첫 실행](cleanup-scope/cold.json), [재사용](cleanup-scope/warm.json).
- [비교 집계](comparison.json): 원문 식별자·hash가 승인 사례와 일치하고, 저장한 연결 ID와 다음 실행에 전달·사용한 ID가 같은지 assertion으로 확인했다.

첫 실행에서 저장한 연결은 각각 1개·3개였고, 다음 실행에서 전부 재사용했다. 네 실행 모두 미해결 조건 3개가 남았다. 1번 첫 실행은 `round-limit`, 나머지는 `no-new-evidence`로 끝났다. 승인된 정답에는 모두 포함되지만 표본은 두 사례뿐이며, 기존 uncertain을 유지한 결과를 정확도 개선으로 볼 수 없다. 미승인 12개 사례는 채점하지 않았다.

## 발견한 한계

1. **인용됐다는 것만으로 유용한 연결은 아니다.** 1번에서 저장한 `operations/policy`는 자동 정리·`persist()` 정책이었다. 재사용 판정에서도 localStorage의 적용 범위와 공통 계약은 확인되지 않았다고 답했다. 인용 구간의 원문 일치와 질문 해결에 도움이 되는지는 별개다.
2. **같은 질문을 표현만 바꿔 다시 검색한다.** 1번 첫 실행의 두 라운드에는 “공통 계약은 무엇인가요?”와 “공통 계약”처럼 의미가 겹치는 검색어가 있었다. 현재 문자열 정규화는 이런 중복을 제거하지 않는다.
3. **불확실성을 유지하는 정책과 모델의 해석 품질은 구분해야 한다.** 2번 모델 제안은 conflict였지만 미해결 조건이 남아 최종 결과는 uncertain이었다. 승인 정답 일치만으로 모델이 적용 범위를 이해했다고 볼 수 없다.

다음 개선 후보는 연결별로 “어떤 질문의 어느 조건을 확인했는가”를 구분하고, 미해결 질문별 검색 이력을 이용해 같은 조사를 반복하지 않도록 하는 것이다. 이번 검증에서는 구현이나 승인 정답을 수정하지 않았다.

## 실제 CLI 반복 실행

같은 저장소에서 `know doctor ... --model gemma4:latest --inspection-mode research --limit 1 --cache-dir <같은 디렉터리> --json`을 두 번 실행했다. 실제 `bin/know.mjs` 프로세스의 stdout·stderr·종료 코드를 기록했다.

- [첫 CLI 실행](cli.json): 검색 5회, 재사용 0개, 17.10초.
- [두 번째 CLI 실행](cli-warm.json): 근거 2개 재사용, 검색 3회, 16.81초.
- 모두 exit 0, healthy, semantic complete, 오류 0, promptVersion 10, cached 0이었다. 과거 판정 캐시가 아니라 근거 원문을 재사용했다.
- 선택된 쌍은 `operations/lifecycle` ↔ `operations/persistence`다. 두 번 모두 uncertain이며, 승인되지 않은 사례라 정확도 점수에는 포함하지 않는다. 이 쌍에서의 검색 감소를 전체 사례로 일반화하지 않는다.

## 변경 여부

[무결성 확인](integrity.json)에서 실험 전후 전체 색인 snapshot과 승인 자료가 같았다. 이후 두 CLI 실행에서도 원본과 색인의 changed·metadata·missing·stale이 모두 0이었다. 기존 원본·색인·승인 정답은 변경하지 않았으며, 이 디렉터리의 실측 자료와 별도 임시 연결 캐시만 생성했다.
