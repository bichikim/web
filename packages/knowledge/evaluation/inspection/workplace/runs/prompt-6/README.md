# 후보 버전 6: 원문 구간 선택

모델이 인용문을 직접 쓰는 대신 좌우 원문 구간 ID를 선택하고, 어댑터가 원문을 그대로 가져와 기존 인용 검증에 전달한다. [후보 소스](policy.json)와 [구현·테스트 사본](implementation.json)을 보존했다. 사용자 승인에 따라 기본 동작을 버전 3으로 복원했으며 후보 6은 채택하지 않았다. 정답은 변경하지 않았다.

## 계약

[Ollama 구조화 출력 문서](https://docs.ollama.com/capabilities/structured-outputs)의 JSON Schema 생성·응답 검증 방식을 사용한다. 선택 가능한 ID를 좌우별 enum으로 제한하고 반환값도 같은 Zod 스키마로 검증한다. `none`은 기존 계약에 따라 unrelated·uncertain에서 인용을 생략할 때만 사용한다. duplicate·conflict의 빈 인용은 기존 검증기가 거부한다.

원문 전체를 800 UTF-16 단위 이하로 분할하며 문자·줄바꿈을 바꾸거나 서로게이트 쌍을 자르지 않는다. 각 구간은 원문의 연속된 문자열이다. 이 방식은 문장·의미 경계 분할이 아니므로 긴 문서에서 의미가 구간 경계에 걸칠 수 있다. 적절한 근거 구간을 고르는지는 별도 품질 문제다.

공개 Assessment·doctor 출력·캐시는 이전처럼 `leftQuote`, `rightQuote` 원문 문자열을 반환한다. ID는 모델과 어댑터 사이의 전송 계약에만 사용한다. 모델 digest·원본·버전별 캐시 분리와 원문 인용 검증은 유지했다. 이전 버전 3·4·5의 캐시는 재사용하지 않는다.

업무 문서는 매회 전체 28쌍을 정상 분류했고 태그 비교도 duplicate로 맞혔다. 전체 28쌍의 분류가 세 번 모두 같았다. 정답 없는 20쌍은 정확도에서 제외한다. `platform-origins`는 서로 다른 웹·토스 클라이언트의 주소를 conflict로 판단해 세 번 모두 틀렸다. 이전 partial 진단과 정확도 개선 폭을 계산하지 않는다.

합성 자료는 모델·정답 해시·원본 해시가 버전 3 기준과 같았다. `bilingual-undefined-policy`, `production-undefined-policy`가 uncertain에서 unrelated로 회귀했다. 합성 자료는 각각 1회만 실행했으며 전체 품질 개선으로 결론내리지 않는다. 모든 진단 옆 `execution.json`에 실제 저장소·캐시 경로·시간을 기록했다.

## 검증과 결정

테스트는 짧은 원문, 긴 한글·이모지·줄바꿈, 구간 길이·전체 원문 보존, 없는 ID, 좌우 혼동, 필수 인용 누락, 기존 출력 호환성과 캐시 분리를 검사한다. 타입·lint 검사와 모델 평가는 별개다. 인용이 원문에 있다는 사실은 분류나 근거 선택의 타당성까지 보장하지 않는다.

사용자 승인으로 버전 3을 복원하고 후보 6을 보관했다. [분류·근거 분리 후보 7](../../../runs/prompt-7/README.md)은 별도 실험으로 검증한다. 업무 문서 기준선은 후보 6의 평가 이력이지 후보 채택 승인 기록이 아니다.
