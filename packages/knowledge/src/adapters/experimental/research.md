# 미해결 조건의 지식 검색

```sh
know doctor <저장소> --model gemma4:latest --inspection-mode research --json
```

`research`는 발췌 판정 뒤 이전에 연결한 근거 원문을 먼저 읽고, 부족한 조건만 검색어로 바꿔 현재 저장소·브랜치의 지식 베이스를 검색한다. 기존 CLI와 같은 Ollama 임베딩 + Qdrant dense/BM25 검색을 사용한다. 같은 문서나 명시적인 연결 관계가 없어도 찾을 수 있다. 검색 대상 문서는 먼저 색인해야 한다. 외부 웹이나 색인하지 않은 파일은 읽지 않는다.

## 근거 연결 재사용

CLI는 마지막 재판정에서 인용한 보조 unit만 `--cache-dir` 아래 `links/<쌍 키>.json`에 저장한다. 기본 경로는 기존 inspection 캐시와 같다. [저장 계약](../../cli/links.md)을 참고한다. 검색에만 등장했거나 마지막 판단에서 인용하지 않은 문서는 저장하지 않는다. `uncertain`이어도 실제 인용이 있으면 연결을 남긴다.

다음 실행은 저장된 결론이 아니라 현재 색인의 해당 원문을 먼저 재판정한다. 첫 발췌 판정이 확정적이어도 유효한 연결을 읽으며, 미해결 조건이 남을 때만 추가 검색한다. 재사용한 unit과 새 판정은 `research.reused`에 표시한다. 과거 연결 이유는 모델에 전달하지 않는다.

비교 원문이 바뀌면 다른 쌍 키를 사용한다. 보조 unit의 hash·본문·문서 식별자·scope를 현재 색인 snapshot과 대조하고, 변경·삭제·비활성화된 근거는 제외한다. 수정한 파일을 아직 색인하지 않았다면 이 비교만으로 파일 변경을 확인할 수 없으므로 먼저 `know index`로 반영한다. 원본의 `relations`, status, 평가 정답은 수정하지 않는다.

## 한도와 중단

- [질문별 이력](../../inspection/inquiry.md)을 이어 사용한다. 첫 검색 뒤에는 새 근거가 없어도 다른 검색어로 한 번 더 시도할 수 있다. 이후에는 새 인용 구간이 있어야 추가 검색하며, 같은 색인 상태에서 질문당 최대 6회다. 빈 결과도 시도로 기록한다. 색인·모델·프롬프트 변경 시 이 제한 이력을 다시 시작한다.
- 문서 쌍당 최대 2라운드, 라운드당 검색어 3개, 검색어당 결과 3개다. 검색어가 한도를 넘는 모델 응답은 거부한다.
- 추가 본문은 재사용 근거와 전체 검색 라운드를 합쳐 중복 없이 최대 12,000자(UTF-16 기준)다. unit마다 앞부분 최대 4,000자를 읽으며 생략 여부를 표시한다. 후속 요청에 이전 근거를 다시 전달하므로 실제 모델 입력·출력 토큰 총량과는 다르다.
- 이미 사용한 검색어는 정규화해 제외한다. 원래 비교한 두 unit, 이미 읽은 unit, 다른 문서에 실린 동일 본문과 비활성 문서는 새 근거에 넣지 않는다. 검색 결과 3개에 제외 대상이 포함돼도 더 요청해 채우지 않는다.
- 문제가 해결되면 즉시 종료한다. 새 검색어가 없거나 라운드·본문 한도에 도달해도 종료한다. 첫 라운드에 새 근거가 없으면 남은 라운드에서 다른 검색어를 시도할 수 있다.
- 부족한 조건이 남으면 최종 결과는 uncertain이다. 검색 결과에 예외 설명이 없다는 이유만으로 “예외가 없다”거나 “충돌한다”고 판단하지 않는다.

새 근거를 읽은 뒤 발견한 다른 미확인 조건은 다음 라운드의 검색 질문이 된다. 모델이 필요한 조건을 빠뜨리거나 관련성이 낮은 검색어를 만들 수 있으므로, 한도 내 검색 완료가 조사 완결성이나 정확도 보증은 아니다.

후속 조건은 고정된 질문 ID의 `remaining`에 기록한다. 질문 표현을 바꿔 조사 횟수를 초기화하지 않는다. `research.journal`에서 질문별 확인 내용·미해결 조건·인용 구간·검색 시도를 볼 수 있다. `confirmed`는 모델의 제안이며 사람이 승인한 사실이 아니다.

## 결과

JSON `semantic.assessments[].research`에 검색 전 판정(`initial`), 라운드별 미해결 조건·검색어·검색 결과 point ID·새로 읽은 ID·모델 제안과 인용(`rounds`), 읽은 원문과 경로·문서 ID·hash(`selection`), 남은 조건(`unresolved`), 중단 이유(`stop`)를 남긴다. 최종 판정은 기존 `assessment` 필드다. `initial`은 검색 전 부족한 조건까지 확인한 판정이며 v7의 발췌 전용 원시 응답과는 다르다.

중단 이유는 `resolved`, `round-limit`, `text-limit`, `no-new-queries`, `no-new-evidence`, `call-limit`이다. 검색·모델 오류나 snapshot과 달라진 결과는 성공적인 “근거 없음”으로 바꾸지 않고 진단 오류로 반환한다. 실패한 쌍은 정상 평가에 포함하지 않으며, 해당 쌍의 중간 검색 기록은 현재 오류 결과에 포함하지 않는다.

## 모델 호출 예산

v28은 실행 단계가 시작되기 전에 필요한 생성 호출을 예약한다. 기본 예산은 쌍당 14회이며 어댑터의 `maxCalls`로 조정할 수 있다. 새 CLI 옵션은 추가하지 않았다. 초기 비교·발췌·질문 확인에 3회, 필요한 질문 재작성에 1회, 검색 계획과 재판정에 각각 1회, 독립 근거 확인과 답변 감사에 합쳐 2회를 예약한다. 감사 예산이 부족하면 두 요청 모두 시작하지 않는다. `research.budget`의 `limit`과 `reserved`는 한도와 예약 횟수이며 토큰 수·과금액이 아니다. 모델 목록 조회와 임베딩·검색 호출은 생성 예산에 포함하지 않고 기존 검색 한도를 유지한다.

질문이 준비된 뒤 예산이 부족하면 `stop: call-limit`과 미해결 결과를 반환한다. 이미 읽은 자료는 `selection`, 완료한 검색은 `rounds`와 질문 이력에 남긴다. 감사 전 제안 답은 `decision.unreviewed`에 질문·근거와 함께 남기고 `confirmed`는 비운다. 수행하지 않은 감사를 승인이나 거부로 꾸미지 않는다. 재판정 전에 중단된 자료는 읽은 자료로 보존할 뿐, 인용된 근거인 것처럼 연결하지 않는다.

초기 3회조차 예약할 수 없거나 미해결 질문을 새로 작성하기 전에 예산이 소진되면 아직 검색 이력이 없으므로 `inspection-call-limit` 오류를 반환한다. 음수·소수·비유한수 예산은 `invalid-inspection-budget`이다. 모델 장애나 잘못된 응답은 이 정상 중단 계약으로 바꾸지 않는다.

2026-09-13에 [Pydantic AI의 사용량 제한](https://pydantic.dev/docs/ai/core-concepts/agent/#usage-limits)을 확인했다. 요청 전 제한 검사와 실행 전체의 공유 예산을 참고했으며, 라이브러리를 도입하지 않았다. 현재 어댑터의 고정 단계별 호출 수에 맞춘 예약 방식이며, 단계 내부 요청 수를 바꾸면 예약량과 전체 경로 테스트도 함께 바꿔야 한다.

[회귀 테스트](./__tests__/research.budget.spec.ts)는 실제 초기 비교부터 감사까지의 제품 함수를 실행하되 모델 HTTP 응답과 검색 결과는 대체한다. 초기·질문 재작성·검색 계획·재판정·감사 경계의 중단, 자료·질문 보존, 보존 이력으로 재개를 검사한다. 실제 모델의 판정 품질 개선을 입증하는 테스트는 아니다. 평면 입력 감사 후보는 이번 변경에 포함하지 않았다.

검색 결과의 내용·범위는 시작 시점 snapshot과 대조한다. 인용 ID는 전달한 원문 구간에 한정하지만, 인용이 결론을 논리적으로 뒷받침하는지는 별도의 검토가 필요하다. 재판정 모델이 단정적인 답을 내도 미해결 조건이 있으면 최종 결과는 uncertain이며 원래 제안은 라운드 기록에 보존한다.

기존 combined·separated·contextual 모드는 유지한다. research의 판정 결과 캐시는 재사용하지 않으며 `cached`는 0이다. 정상 실행에서 생성 요청은 연결 재판정과 근거 검토를 포함해 쌍당 최대 14회, 검색용 임베딩·조회는 최대 6회다. 한 요청은 기존 어댑터의 120초 timeout을 따르며 전체 벽시계 시간 한도는 별도로 두지 않았다. 원본·색인·정답은 변경하지 않는다. 출력과 연결 기록에는 지식 원문이 포함되므로 공유 전 확인한다.

연결 파일 읽기·쓰기 실패는 각각 `inspection-links-read-failed`, `inspection-links-write-failed`로 보고한다. 오류를 근거 부재나 성공으로 처리하지 않으며, 모델 실패 시 기존 연결은 유지한다. 반복 실행은 입력 근거가 달라질 수 있으므로 품질 평가에서는 서로 다른 빈 `--cache-dir`로 시작한 실행과 재사용 실행을 구분한다. v11 반복 실행 (로컬 보관: `.local/evaluation/inspection/runs/prompt-11/README.md`)은 검색 생략을 확인한 실험이며 정확도 개선을 입증하지 않는다.

구현: [검색 루프와 한도](../../inspection/research.ts), [모델 요청](research.ts), [검색 연결](../../cli/runtime.ts). [Qdrant hybrid query](https://qdrant.tech/documentation/search/hybrid-queries/)와 [Ollama 구조화 출력](https://docs.ollama.com/capabilities/structured-outputs)을 사용한다.

v12 검증 (로컬 보관: `.local/evaluation/inspection/runs/prompt-12/README.md`)에서는 대안 검색 실행을 확인했다. 실제 모델의 두 승인 사례는 모두 uncertain을 유지했으며, 판정 품질 개선은 확인하지 못했다.

v13은 v12의 질문·검색 정책을 유지하고, 재판정 응답에서 같은 유효 인용 ID를 반복한 경우에만 중복을 제거한다. 알 수 없는 ID나 6개를 초과한 입력은 계속 거부한다. 판정 지침 실험 (로컬 보관: `.local/evaluation/inspection/quality/README.md`)의 후보들은 회귀가 있어 채택하지 않았다. 인용 형식 오류 수정과 판정 품질 개선은 별개다.

## 근거와 답변의 검토

모든 질문을 해결했다고 제안한 재판정에만 [검토 요청](audit.ts)을 추가한다. 첫 요청은 제안 답변 없이 질문·원문·인용문만 보고 답할 근거가 있는지 확인한다. 두 번째 요청은 기존 v14와 같이 제안 답변이 질문에 맞는지 검토한다. 두 요청은 서로의 결과를 받지 않으며, 둘 다 승인해야 질문을 닫는다. 초기 발췌 판정이나 미해결 조건이 이미 남은 재판정은 검토하지 않는다. 최종 라벨과 판정 이유는 검토 입력에 넣지 않는다. 구조화 출력은 [Ollama의 schema 전달·응답 검증 방식](https://docs.ollama.com/capabilities/structured-outputs)을 따른다.

검토가 거부한 질문만 `confirmed`를 비우고 `remaining`에 부족한 조건을 적는다. 질문 ID·인용 근거·검색 시도 횟수는 유지하며, 기존 검색 한도 안에서 다음 검색을 계획한다. 한도가 소진됐거나 새 검색어가 없으면 uncertain으로 끝난다. 새 근거를 얻어 다시 확정하려면 다시 검토해야 한다. 검토 대상은 연결 원문과 두 검색 라운드를 합쳐 최대 3회이며, 대상마다 근거 확인·답변 검토를 각각 한 번 요청한다. 중첩 검토는 없다.

질문 생성은 정책의 대상뿐 아니라 금지하는 행위와 상대 규칙의 실행 조건을 묻도록 지시한다. 검색 계획에는 이전 판정 대신 비교 원문과 미해결 질문을 전달한다. 조사한 적 없는 질문이 있으면 최소 한 검색어를 요구한다. 이후에는 유용한 새 검색어가 없을 때 빈 목록으로 종료할 수 있다. 구조화 응답이 첫 검색 조건을 어기면 `invalid-inspection-queries`로 반환한다.

`research.reused.decision.audits`와 `research.rounds[].decision.audits`에 질문별 검토 이유·부족한 조건·검토자가 선택한 근거 ID를 남긴다. 검토 당시 질문·답변·ID별 인용문도 함께 저장해 이후 질문 이력이 갱신돼도 대조할 수 있다. ID는 `<질문 ID>:<해당 답변의 인용 순번>`이다. 거부돼도 읽은 근거 연결은 유지한다. 원래 판정 제안과 검토 의견은 모두 모델 출력이지 사람이 승인한 사실이 아니다.

`audits[].checks.evidence`와 `checks.answers`에 두 검토 결과를 각각 남긴다. 하나라도 거부하면 최종 검토도 거부이며, 독립 근거 확인이 거부한 경우 그 미확인 조건을 우선한다. 기존 단일 답변 검토 소비자의 기록에는 `checks`가 없을 수 있다.

잘못된 검토 응답은 `invalid-inquiry-audit`, 검토 요청 실패는 `inspection-audit-unavailable`이다. 둘 다 성공적인 근거 부족으로 처리하지 않으며 기존 조사·인용 검사를 완화하지 않는다. 이전 프롬프트 버전의 질문 이력은 CLI에서 재사용하지 않지만 유효한 원문 연결은 다시 읽을 수 있다. 후검토 실험과 통합 검증 (로컬 보관: `.local/evaluation/inspection/quality/context/README.md`)을 참고한다.

v19의 실제 품질 검증은 로컬 `gemma4:31b-mlx`의 고정 digest에서 수행했다. 근거 유무 대조와 기존 18조건을 통과한 결과이며, 다른 모델이나 문서의 정확도를 보장하지 않는다. 독립 확인이 오승인한 사례가 남아 있어 기존 답변 검토도 유지한다. 패키지의 기본 모델은 변경하지 않았다.
