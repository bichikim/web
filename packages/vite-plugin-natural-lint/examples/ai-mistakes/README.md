# AI mistakes example

AI가 생성한 코드에서 자주 논의되는 의미적 실수를 현재 환경의 자동 선택 backend로 평가한다. 독립적인 test oracle에는 통과·위반 fixture가 각각 10개 있다. silent fallback에는 `pass`, `fail`, `uncertain` fixture가 각각 6개 있고, 나머지 탐색 규칙에는 각각 한 쌍이 있다. [`natural-lint.config.mjs`](./natural-lint.config.mjs)의 `expected`가 정답을 제공한다.

silent fallback은 실제 내장 규칙
`@natural-lint/unexpected-error-becomes-success-like-result`를 튜플로 불러오고, 이 예제의
fixture 범위와 `expected`만 override한다. 따라서 아래 성능은 별도로 복사한 예제 구현이 아니라
배포되는 내장 규칙의 결과다.

이 예제는 그대로 복사하는 범용 정책이 아니라, 프로젝트 고유 규칙을 실제 사례로 검증하는
완성형 예제다. 처음 규칙을 만드는 흐름은 패키지 README의
[`내 규칙을 만드는 순서`](../../README.md#내-규칙을-만드는-순서)와
[`자연어 규칙 작성 가이드`](../../RULE_AUTHORING.md)부터 읽는다.

## 프로젝트에 맞게 바꾸는 부분

- `select`: 어떤 파일을 후보로 볼지 결정한다.
- `inspect`: 프로젝트 AST와 계약으로 확정 가능한 사례를 먼저 판정한다.
- `questions`: 남은 의미 판단을 프로젝트 용어로 묻는다.
- `reduce`: 프로젝트가 허용할 확률 경계와 `uncertain` 기준을 정한다.
- `expected`: 실험 사례의 독립 정답이며 실제 `warn` 또는 `error` 규칙에는 넣지 않는다.

silent fallback의 `request`, `query`, `fetch` 판정은 Pomo에서 가져온 이 예제의 정책이다.
다른 프로젝트에서 이 이름이 optional 또는 best-effort 작업을 의미한다면 그대로 사용하면 안
된다. 사용자는 자기 계약에 맞춰 `inspect`를 바꾸고 별도 사례로 다시 평가해야 한다.

## 실험 대상

| 규칙                                                         | 확인하려는 실수                                    |
| ------------------------------------------------------------ | -------------------------------------------------- |
| `test-does-not-provide-independent-oracle`                   | 구현과 같은 계산으로 기대값을 만들어 스스로 확인함 |
| `@natural-lint/unexpected-error-becomes-success-like-result` | 예상하지 못한 오류를 `undefined` 같은 값으로 숨김  |
| `change-adds-unrequested-public-behavior`                    | 요청 범위를 벗어난 공개 동작을 함께 추가함         |
| `comment-contradicts-implementation`                         | 주석의 동작 설명과 실제 구현이 일치하지 않음       |

테스트 oracle 문제는 잘못된 구현 뒤에 생성한 테스트가 같은 오류를 답으로 받아들일 수 있다는 [실증 연구](https://arxiv.org/abs/2607.05139)를 바탕으로 했다. 나머지는 AI 생성 코드에서 요구사항 오해, 경계 사례 누락, 불완전 구현, 요청하지 않은 고려 사항이 발견된 [버그 분류 연구](https://arxiv.org/abs/2403.08937)를 참고했다.

## 실행

package를 build한 뒤 이 디렉터리에서 실행한다.

```bash
node ../../bin/index.js check
```

test-oracle과 구문으로 확정 가능한 사례는 `inspect`가 판정한다. 나머지는 위반·준수·근거 부족을 대칭적인 choice 질문으로 한 번에 비교한다. 모두 `experiment` 규칙이므로 결과와 관계없이 종료 코드는 `0`이고 진단도 만들지 않는다.

## 실제 평가 결과

Apple Silicon managed CoreML 환경에서 같은 모델과 임계값 `0.8`로 실행했다. 먼저 규칙마다 한 쌍만 둔 탐색 실행에서 원본 TypeScript 전체와 구조화된 근거를 비교했다.

| 근거                          | 정확도 | 판정 가능률 | 반복 일치율 |
| ----------------------------- | ------ | ----------- | ----------- |
| 원본 TypeScript 전체          | 25.0%  | 50.0%       | 100.0%      |
| 규칙별로 추출한 구조화된 사실 | 41.7%  | 75.0%       | 100.0%      |

구조화된 근거의 탐색 결과는 다음과 같다.

| 규칙                    | 정상 확률 | 위반 확률 | 평가                                                |
| ----------------------- | --------- | --------- | --------------------------------------------------- |
| 독립적 test oracle      | `0.0369`  | `0.7430`  | 분리는 되지만 위반이 `uncertain`이라 추가 보정 필요 |
| 오류를 숨기는 fallback  | `0.8093`  | `0.8249`  | 정상 사례까지 실패하므로 사용 불가                  |
| 요청 범위를 벗어난 동작 | `0.9319`  | `0.9815`  | 정상 사례까지 실패하므로 사용 불가                  |
| 주석과 구현의 불일치    | `0.8701`  | `0.7776`  | 판정 방향도 맞지 않아 사용 불가                     |

test oracle을 정상 10개와 위반 10개로 확장하자 작은 표본의 인상은 유지되지 않았다.

| 규칙               | 정확도 | 판정 가능률 | 반복 일치율 | 오탐 | 미탐 |
| ------------------ | ------ | ----------- | ----------- | ---- | ---- |
| 독립적 test oracle | 20.0%  | 25.0%       | 100.0%      | 1    | 7    |

판정 문구만 더 구체적으로 바꾼 추가 실험도 test oracle은 정확도 `25.0%`, 오탐 2개였다. 같은 calibration fixture에 맞춘 문구를 채택하면 일반화 성능을 과장할 수 있으므로 원래 문구를 유지한다. 파일별 확률과 두 문구의 비교는 [`EVALUATION.md`](./EVALUATION.md)에 기록했다.

반복 결과는 모든 파일에서 동일했지만 높은 반복 일치율이 정확성을 의미하지는 않았다.

V2에서는 test-oracle을 AST `inspect`와 두 typed question으로 바꿨다. 모델 답변만 사용한 보수적인 reducer는 20개를 모두 `uncertain`으로 보류했다. 이후 `inspect`로 직접 참조, 같은 callee 호출, 독립적인 literal을 구분한 결과는 다음과 같다.

| 경로                            | 정확도 | coverage | precision | recall | Laya 호출 |
| ------------------------------- | ------ | -------- | --------- | ------ | --------- |
| typed question과 reducer만 사용 | 0.0%   | 0.0%     | n/a       | 0.0%   | 20        |
| AST `inspect` 포함              | 100.0% | 100.0%   | 100.0%    | 100.0% | 0         |

두 번째 결과는 자연어 모델 정확도가 아니라 구문으로 확정 가능한 범위를 모델에서 분리한 결과다. 의미 판단이 필요한 fallback은 아직 검증되지 않았으므로 모든 규칙은 `experiment`를 유지한다. 상세 분포는 [`EVALUATION.md`](./EVALUATION.md)에 기록했다. 실제 Pomo 코드에서 분리한 독립 사례와 정답 근거는 [`HOLDOUT.md`](./HOLDOUT.md)에서 확인할 수 있다.

## 현재 결과

오탐을 줄이기 위해 위반 여부가 구문적 사실로 확정되는 정상·위반 사례는 `inspect`로 이동하고, 모델 질문은 `violation`, `compliant`, `insufficient`를 대칭적으로 비교하도록 변경했다.

| 규칙                           | 정확도 | coverage | 오탐 | Laya 호출 |
| ------------------------------ | ------ | -------- | ---- | --------- |
| 독립적 test oracle             | 100%   | 100%     | 0    | 0         |
| 오류를 숨기는 fallback holdout | 93.3%  | 60.0%    | 0    | 6         |
| 요청 범위를 벗어난 공개 동작   | 100%   | 100%     | 0    | 0         |
| 주석과 구현의 불일치           | 100%   | 100%     | 0    | 0         |

silent fallback은 AST로 catch 조건, 성공처럼 보이는 반환, rethrow, 명시적인 실패 결과, 문서화된 fallback과 주 작업 호출을 추출한다. 실제 코드 기반 holdout 15개 중 14개를 맞혔다. 정상 5개와 모호한 5개는 모두 맞혔고, 실제 위반 5개 중 4개를 탐지했다. 남은 metadata 사례는 파일만으로 필수 읽기와 선택적 cache miss를 구분하지 못해 `uncertain`으로 보류했다. 작은 두 사례만 있는 나머지 규칙의 100%는 실행 경로를 확인한 smoke 결과일 뿐 승격 근거가 아니다.
