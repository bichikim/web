# TS7 파일 접근 반복 측정

2026-10-15, TS7 7.0.2 / Node 24.15.0 / macOS arm64에서 측정했다. 이 변경은 TS7 실험 경로에만 적용한다. 기본 제품의 TS6 workspace와 navigation worker를 다시 빌드해 이전 번들과 SHA-256이 일치함을 확인했다.

## 변경과 근거

별칭의 대상 확인마다 닫힌 파일에도 `didOpen`을 보내던 동작을 줄였다. 프로젝트 준비 후의 심볼 확인은 디스크 문서에 직접 요청한다. 이미 열린 버퍼는 계속 동기화하며, 요청한 소스와 디스크 내용이 다르면 거부한다. BOM·UTF-16처럼 컴파일러가 디코딩한 내용에는 기존 오버레이를 사용해 위치를 보존한다. 원본·선언 연결, CommonJS 보완, 프로젝트 밖 파일 범위와 기존 준비 겹치기는 유지했다.

탐색 클라이언트가 소비하지 않는 push diagnostics와 자동 import 제안용 워밍을 초기화 옵션으로 끈다. 파일 감시는 유지한다. 검색 중 파일 변경으로 분석이 실패하면 부분적으로 구축한 분석 상태를 폐기해 다음 조회에서 다시 준비한다.

설정과 동작은 설치된 바이너리의 revision `2bd066d87f5bafd315be9f40889d0a60b9e58e0b`의 구현과 대조했다. [project/session.go](https://github.com/microsoft/typescript-go/blob/2bd066d87f5bafd315be9f40889d0a60b9e58e0b/internal/project/session.go)의 `DidOpenFile`은 스냅샷을 갱신하고, 준비된 문서 조회는 현재 스냅샷을 재사용한다. 자동 import 캐시는 사용자 설정을 확인한다. [lsp/server.go](https://github.com/microsoft/typescript-go/blob/2bd066d87f5bafd315be9f40889d0a60b9e58e0b/internal/lsp/server.go)와 [userpreferences.go](https://github.com/microsoft/typescript-go/blob/2bd066d87f5bafd315be9f40889d0a60b9e58e0b/internal/ls/lsutil/userpreferences.go)에서 초기화 설정의 전달과 `suggest.autoImports`의 매핑을 확인했다.

## 반복 작업

실제 모노레포의 `getWindow` 사용처 조회를 전후 번갈아 3회씩 추적했다. 임시 바이너리 복사본에 Apple dyld interposition을 적용했고, 서명 변경 전후의 `__TEXT,__text`가 일치했다. 아래는 중앙값이다.

| 관측값                           |      전 |      후 |
| -------------------------------- | ------: | ------: |
| stat 호출                        | 293,151 | 281,001 |
| 같은 경로의 추가 stat 호출       | 219,186 | 207,293 |
| open 호출                        |  57,865 |  56,321 |
| 파일에서 바이트를 읽은 read 호출 |  24,288 |  23,004 |
| 같은 경로의 추가 read 호출       |   4,033 |   2,768 |
| 열린 문서 수                     |     126 |      28 |
| adopted snapshot 로그 수         |     136 |      38 |

stat은 4.1%, 같은 경로의 추가 read는 31.4% 줄었다. 추가 호출은 동일 경로에 대한 두 번째 이후 호출을 뜻한다. 프로젝트별 해석 조건이나 분할 읽기도 포함하므로 모두 제거 가능한 중복이라고 해석하면 안 된다. stat 범위는 전 275,801–308,641, 후 265,966–296,475였다. 디렉터리 열거 등 모든 파일 API를 추적한 것은 아니다. 임시 SDK 경로와 계측 비용이 있으므로 추적 실행 시간은 아래 성능 비교에 사용하지 않았다. 추적한 6회 모두 결과 102개가 정확히 일치했다.

자체 모듈 해석 호출은 25,932회, 캐시 적중은 11,753회로 전후 동일했다. 파일 범위를 줄이거나 해석 검사를 생략한 개선이 아니다. 준비된 프로젝트에 불필요한 문서 열기와 제안용 백그라운드 작업을 덜 보내는 방식이다.

## 실제 모노레포 성능

서명·코드를 변경하지 않은 원본 바이너리로 측정했다. 각 최초 조회는 새 프로세스와 빈 `CODEX_HOME`에서 시작하고, 같은 세션에서 재조회했다. 전후 순서를 번갈아 실행했으며 `fileRevision`·`getWindow`는 각각 5회, 정의·JavaScript는 각각 3회다. 단위는 ms, 중앙값이며 `전 → 후`다.

| 조회                               |  최초 첫 결과 | 최초 전체 완료 | 재조회 첫 결과 | 재조회 전체 완료 |
| ---------------------------------- | ------------: | -------------: | -------------: | ---------------: |
| fileRevision 사용처 24개           |   1,119 → 897 |  8,850 → 7,624 |      225 → 225 |        316 → 324 |
| getWindow 사용처 102개             |     342 → 455 |  5,854 → 5,785 |      177 → 160 |        349 → 301 |
| 앱 정의 1개                        |     467 → 473 |      496 → 502 |        32 → 32 |          58 → 58 |
| JavaScript compareFiles 사용처 6개 | 1,551 → 1,543 |  4,682 → 4,371 |      148 → 132 |        198 → 197 |

`fileRevision` 전체 완료는 13.8%, JavaScript는 6.7% 줄었다. `getWindow` 전체 완료는 1.2% 차이로 개선 효과가 작고, 첫 결과는 114ms 느려졌다. 재조회 전체 완료는 `getWindow`에서 13.9% 줄었지만 `fileRevision`은 8ms 늘었다. 모든 조회가 빨라졌다고 결론 내릴 수 없다.

`getWindow` 별칭 대상 확인은 494 → 167ms로 줄었다. 다만 메타데이터 준비는 3,085 → 3,317ms로 늘었고 여전히 큰 비용이다. 같은 회차의 전체 파일 범위 6,584개, 분석 소스 409개, 입력 23,594개, binding 173개, 선언 99개는 모두 동일했다.

첫 결과는 서버가 반환한 첫 비어 있지 않은 결과 묶음이며 브라우저 렌더링 시간은 아니다. Node 모듈 로딩은 제외했고 OS 파일 캐시는 비우지 않았다. 호스트 부하가 약 10–20 이상으로 변동해 이전 회차의 절대 시간과 직접 비교하지 않는다. 파일 감시는 호스트에서 활성화한 상태로 측정했다. 이전 샌드박스의 FSEvents 시작 실패 실행은 이번 비교에 섞지 않았다.

## 정확성과 변경 검증

- 독립적인 기대 위치를 가진 25개 사례: 별칭·재노출, 패키지 밖 파일, 프로젝트별 paths, CommonJS, ESM/CJS 조건부 exports, 원본·선언 및 declaration map, 겹친 프로젝트, BOM·UTF-16. 누락 0, 예상 밖 위치 0.
- 실제 모노레포 결과는 이전 제품 기준 위치와 일치했다. 최종 기록 164건에서 전후 결과 위치와 분석 범위를 비교했다.
- 파일·설정 무효화 25개 검사: 같은 크기와 복원된 mtime, 교체·생성·삭제, symlink 대상, paths와 선언 map 대상, 닫힌 소비자 변경, include 변경 등을 통과했다.
- 최초 검색 중 닫힌 CommonJS 별칭 파일을 수정하는 검사에서 오래된 소스를 거부하고, 재조회 시 상태를 다시 구축해 이전 별칭 사용처가 남지 않음을 확인했다. 이 검사에서 발견한 실패 후 재조회 오류도 수정했다.
- Wallaby 단위 검사 52개 통과, 변경 파일 TypeScript 검사 및 oxlint 통과.

이 검증은 해당 사례와 실행 환경의 근거다. 모든 언어·프로젝트 구성, 모든 동시 수정 순서나 네트워크 파일 시스템의 정확성을 증명하지는 않는다.
