# 큰 파일 화면 표시 측정

2026-10-16, macOS·Codex 인앱 브라우저·생산 번들. [원시 결과](results/2026-10-16/display/summary.json), [측정 조건과 미확정 사항](results/2026-10-16/display/measurement-notes.json).

## 방법

원본 번들과 수정 번들을 별도 서버에서 실행하고 같은 파일·같은 입력으로 비교했다. 브라우저의 파일 선택 `click` 또는 키·휠·검색 `input` 이벤트에서 시계를 시작했다. 대상 파일의 본문과 경로, 검색의 일치 개수·강조가 DOM에 반영된 뒤 두 번의 `requestAnimationFrame`을 거친 시간을 기록했다. 도구 호출 왕복 시간이나 서버 응답 시간은 화면 반영 시간으로 사용하지 않았다. 프레임 콜백은 [다음 repaint 전 실행](https://developer.mozilla.org/en-US/docs/Web/API/Window/requestAnimationFrame)되므로 하드웨어 모니터의 실제 표시 시각을 직접 측정한 값은 아니다.

아래 비교는 새 탭을 `visible: true`로 열어 같은 조건으로 수집했다. 원문 캐시 없는 첫 열기도 OS 디스크 캐시는 따뜻한 상태다. 계측 스크립트·프로파일은 임시 미리보기에만 넣었으며 제품에는 계측 분기를 추가하지 않았다.

## 확인된 병목과 변경

[수신 경로](../../src/viewer/load-document-source.ts)는 같은 세션·파일·리비전의 완료된 원문 한 개를 포트별로 재사용한다. 큰 원문을 받은 직후 변경 확인에서 같은 원문을 두 번 더 수신하던 경로를 줄였다. 파일 리비전이 달라지면 다시 받으며 취소·교체 확인을 생략하지 않는다. 이전 파일 이력을 원문 캐시에 쌓지 않는다.

[분할 크기](../../src/shared/reading-limits.ts)는 JSON의 최대 이스케이프 팽창까지 MCP 수신 제한 안에 들어가도록 정했다. 32 MiB 원문의 분할 요청은 한 번 수신할 때 128개에서 32개로 줄었다. 별도 SDK stdio 검증에서 제어 문자 원문의 최대 응답은 6,291,517바이트였고, 전체 원문 해시가 일치했다. 서버 CPU 프로파일에서는 서버 주 스레드의 전체 파일 파싱이 첫 표시 시간을 차지한다는 증거가 없었다. 분석 작업자의 파싱은 별도 스레드에 있었다. 원문 전체의 줄 분할 두 번은 합계 19ms여서 이번에 별도 인덱스 구조로 교체하지 않았다.

## 정확성과 한계

큰 TS 파일 별칭에서 `core.ts:1:14`로 이동하고, 사용처 6개가 큰 파일 3개·외부 파일 3개와 정확히 일치하는지 확인했다. 결과를 눌러 `large.ts:2:1`로 돌아갔다. 같은 경로의 32 MiB 원문을 교체한 뒤 새 리비전의 `EDITD_LINE_32MB`가 표시되어 캐시 무효화도 실제 화면에서 확인했다. 작은 파일은 편집 가능한 상태를 유지하고, 편집 모드에서 큰 파일로 넘어가도 읽기 전용을 유지했다. 단위 테스트 146개와 통합 테스트 138개가 통과했고 리비전 변경 후 다른 원문을 반환하는 단언도 별도로 통과했다.

초기 실험에는 수 초의 프레임 계측 지연이 있었고, 편집 모드 후 전환에서도 4.6·6.5초가 관찰됐다. 새 활성 탭에서 같은 전환을 분해해 재측정하면 DOM 82ms·첫 프레임 콜백 84ms·후속 콜백 86ms였다. 간헐 지연의 원인은 확정하지 못했으며 모든 이상치를 해결했다고 주장하지 않는다. Chrome 교차 검증은 `ERR_BLOCKED_BY_CLIENT`로 차단됐다. 자동 포커스가 큰 영역을 가운데로 이동시킨 키 입력과, 스크롤 끝의 무동작을 다음 입력까지 기다리던 초기 계측 오류도 별도로 기록했다. 비교 표의 스크롤은 실제 네이티브 키·휠 입력을 사용했다.
