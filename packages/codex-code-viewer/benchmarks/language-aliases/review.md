# 언어별 별칭 누락 수정 검토

Ruby 순차 재할당·정적 로드 순서·외부 Solargraph 경로는 이후 구현했다. 현재 결과는 [Ruby 후속 검증](../ruby-reassignment/README.md)에 기록했으며 아래는 이 작업 당시의 기록이다.

범위는 Python 원본·스텁 연결 및 중첩 설정, Rust 독립 Cargo 소비자, Ruby 상수 별칭과 관련 문서 동기화다. 전체 위험도는 보통이다. 이전에 재현한 P2 네 건을 수정했고, 그 네 재현 사례에서 남은 실패는 없다. P0/P1은 발견하지 않았다. 동작, 구조·테스트 가능성, 명명·파일 배치를 함께 검토했다.

## 수정한 P2

1. **Python 원본에서 스텁 소비자 누락**: 원본과 대응 스텁에서 같은 이름을 가진 선언을 후보로 찾은 뒤, Pyright가 반환한 구현 정의 위치를 비교해 연결한다. 동명 메서드를 함께 둔 native 통합 테스트에서 원본 조회가 소비자 import·별칭·호출 세 위치를 반환하고 다른 메서드는 제외했다. 편집 중 원본과 저장된 원본으로 돌아오는 경우도 같은 소비자를 유지했다. [구현](../../src/server/read-python-reference-targets.ts#L64), [회귀 테스트](../../src/server/__tests__/create-workspace.aliases.integration.ts#L22).
2. **Python 중첩 설정의 소비자 누락**: 가까운 `pyrightconfig.json` 또는 `[tool.pyright]` 설정으로 분석기를 선택하고, 후보 파일을 그 설정 컨텍스트에서 확인한다. 조회한 정의는 정규화한 공통 목표로 사용한다. 소유 설정이 다른 파일의 결과는 해당 컨텍스트의 결과로 병합해 잘못된 설정의 검색 결과가 섞이지 않게 한다. JSON/TOML 설정, 다른 `api.greet`, 패키지 밖 소비자, 재별칭, 스텁과 설정을 함께 쓰는 경우를 확인했다. [설정 선택](../../src/server/read-python-project.ts#L6), [수집](../../src/server/collect-python-references.ts#L105).
3. **Rust 독립 Cargo 소비자 조회 실패**: 후보 파일이 속한 Cargo 프로젝트의 분석기로 정의를 검증한다. 원래 라이브러리의 분석기는 유지하고 컨텍스트를 재사용한다. renamed path dependency와 `as` 별칭에서 import·바인딩·호출 세 위치를 반환했고, 다른 Cargo 프로젝트의 동명 함수를 제외했다. [구현](../../src/server/create-rust-navigation.ts#L61).
4. **Ruby 상수 별칭 사용처 누락**: Solargraph의 상수 대입 AST가 상수 참조인 경우에만 정의 관계를 따라 확장한다. 여러 네임스페이스, 두 단계 별칭, 인스턴스 생성 결과 대입, 다른 클래스로 재할당, 관련 없는 순환 별칭을 검증했다. 메서드 별칭의 기존 동작도 유지했다. [구현](../../src/server/ruby/reference-handler.ts#L25).

Python 관련 파일을 여는 동안 현재 편집 문서가 닫히는 추가 문제도 수정했다. 관련 의미 조회는 원본 draft를 유지하고, 다음 주 문서 조회에서 해제한다. [동기화 계약](../../src/server/lsp/create-workspace-sync.ts#L38)을 단위 테스트와 native 원본·스텁 테스트로 확인했다. 진행 중 해제 뒤 분석기를 새로 만들지 않는 경우도 단위 테스트로 확인했다.

## 검증 공백

1. 속도와 독립 기대 위치 집합은 언어별 48개 소비자 파일을 만든 fixture에서 확인했다. 사용자 실제 Python/Rust/Ruby 저장소의 완전한 정답 집합을 구축한 검증은 아니다. 첫 결과는 서버 스트림 도착이며 브라우저 paint는 측정하지 않았다.
2. Python의 여러 인터프리터·복잡한 실행 환경·동적 대입, Rust procedural macro·생성 소스·feature 조합, Ruby 동적 상수 조회와 메타프로그래밍은 전수 검증하지 않았다.
3. Ruby 상수가 여러 클래스로 재할당되면 그 이름 전체를 별칭으로 확장하지 않는다. 재할당 전후 실행 순서를 따라 각 사용처의 런타임 대상을 구분하는 기능은 구현하지 않았다.
4. `SOLARGRAPH_BINARY`로 외부 서버를 지정하면 기존 경로대로 inline handler를 적용하지 않는다. 이번 Ruby 수정과 검증은 기본 Solargraph 실행 경로에 적용된다. 별도 외부 서버의 상수 별칭 결과는 검증하지 않았다.
5. Python/Cargo 프로젝트가 많은 경우 분석기 프로세스도 늘어난다. 이번 데이터에서는 설정 두 개의 Python 소비자, 독립 Cargo 소비자 세 개를 사용했으며 수십·수백 프로젝트의 최대 메모리 사용량은 측정하지 않았다.

## 구조·명명 검토

Python의 프로젝트 선택, 원본·스텁 목표 찾기, 컨텍스트별 수집을 역할별로 분리했다. 기존 의미 후보 검증과 별칭 수집 연산을 재사용했다. 변경 파일은 600줄 미만이고 새 패키지 의존성, 패키지 스크립트, 타이머를 추가하지 않았다. 별도 P3/P4 제안은 남기지 않는다.

## 범위 밖

TypeScript 프로젝트 분할, 문법 강조만 지원하는 언어의 의미 분석기 추가, 외부 Solargraph 서버 코드 수정은 포함하지 않았다.
