# 검색 전체 완료 시간 개선 검증

2026-10-13. 프로젝트별 별칭과 `.d.ts` 원본 연결 수정이 포함된 기존 검색을 기준으로 비교했다. 프로젝트 분할 방식은 적용하지 않았다.

## 병목과 변경

단일 계측 요청에서 전체 의미 분석 프로그램 준비에 8.535초, 검색 뒤 후보 인덱스 갱신에 3.177초가 걸렸다. 최종 참조 조회 자체는 0.201초였다. 인덱스 하위 단계는 상위 시간에 포함되므로 합산하지 않는다. [계측 로그](results/2026-10-13/stages-before.txt)와 [계측 코드](results/2026-10-13/stages.mts.txt)를 보존했다. 이 단일 요청의 시간은 아래 반복 비교와 별도다.

- [모듈 해석 재사용](../../src/server/create-module-resolutions.ts#L22): 검색 루트가 늘어날 때 이미 성공한 해석을 재사용한다. 새 파일이 실패한 후보 경로를 채우거나 workspace 선언과 원본 연결에 영향을 주면 해당 해석을 다시 확인한다. native TypeScript 통합 테스트에서 동일한 `./shared` 해석 호출이 2회에서 1회로 줄었다.
- [인덱스 준비 중첩](../../src/server/navigation-cache/create-navigation-cache.ts#L137): 첫 의미 분석 결과를 반환한 뒤 인덱스 준비를 시작해 남은 검색과 겹친다. 전체 완료에는 인덱스 준비와 마지막 파일 변경 검증을 포함한다. 변경 검증을 생략하거나 완료 후로 미루지 않는다.

## 속도 비교

각 칸은 수정 전 → 후다. 독립 프로세스 3회의 중앙값이며, 전후 실행 순서를 번갈아 배치했다. 총 60개 기록이다.

| 대상                                |  첫 결과 (초) |  전체 완료 (초) | 같은 프로세스 재조회 완료 (ms) |
| ----------------------------------- | ------------: | --------------: | -----------------------------: |
| 프로젝트별 별칭 fixture             | 0.366 → 0.358 |   0.637 → 0.520 |                    9.65 → 8.81 |
| 선언 원본 연결 fixture              | 0.347 → 0.333 |   0.605 → 0.491 |                    8.05 → 7.92 |
| 실제 모노레포 `fileRevision` 사용처 | 1.725 → 1.530 | 18.402 → 11.150 |                  52.13 → 72.90 |
| 실제 모노레포 `getWindow` 사용처    | 2.539 → 2.339 | 25.193 → 20.966 |                  76.83 → 68.42 |
| 실제 모노레포 `getWindow` 정의      | 0.841 → 0.818 |   0.877 → 0.855 |                  31.95 → 27.55 |

실제 사용처 조회의 전체 완료 중앙값은 각각 39.4%, 16.8% 줄었다. `fileRevision` 재조회는 20.77ms 늘어 모든 지표가 개선된 것은 아니다. 3회 표본이며 실제 데스크톱 부하가 있는 환경이다. `fileRevision` 완료 범위는 전 15.93–21.37초, 후 10.99–18.63초, `getWindow`는 전 20.62–28.49초, 후 13.51–22.00초였다. 작은 첫 결과·재조회 차이를 확정적인 성능 향상이나 회귀로 일반화하지 않는다.

### 측정 조건

- [기존 측정 CLI](../module-resolution/measure.ts)로 동일한 파일·위치를 조회했다. 타이머는 workspace 파일 읽기가 끝난 후 검색 요청부터 시작한다.
- 최초 조회는 프로세스와 `CODEX_HOME`을 새로 만든다. 재조회는 완료 직후 같은 workspace의 같은 검색을 반복한다. 프로세스 재시작 후 조회나 취소 후 재조회와 구별한다.
- 첫 결과는 서버 스트림의 첫 비어 있지 않은 결과 묶음이다. 브라우저 화면 표시 시간은 측정하지 않았다.
- 전체 완료는 스트림 종료까지이며 최종 의미 분석, 인덱스 준비·저장과 변경 검증을 포함한다.
- OS 파일 캐시는 지우지 않았다. Node 24.15.0, TypeScript runtime 6.0.3을 사용했다.
- 기준 번들은 이전 정확도 수정이 반영된 빌드 사본이다. 최종 소스 번들과 함께 SHA-256을 [요약](results/2026-10-13/summary.json)에 기록했다. [실행 코드](results/2026-10-13/run.py.txt), [번들 생성 코드](results/2026-10-13/bundle.mts.txt), [원시 결과](results/2026-10-13/measurements.jsonl)를 보존했다. 임시 경로는 실행 당시 경로이며 fixture 생성 방법은 [이전 실험](../project-analysis/README.md)을 참고한다.

## 정확도와 실행 검증

[위치 검증 코드](results/2026-10-13/validation.py.txt)가 60개 기록 전체를 확인했다. 모든 대상에서 수정 전후 및 최초·재조회·3개 프로세스의 위치 집합이 같았다.

- 프로젝트별 별칭 14개와 선언 연결 17개는 fixture의 기대 위치 집합과 정확히 같고, 무관한 동명 심볼은 포함하지 않았다.
- 실제 모노레포 `fileRevision` 15개, `getWindow` 102개를 유지했다. `getWindow`의 앱 소비자 import·호출과 원본 정의 위치를 별도 단언했다. 이 비교는 기존 결과의 유지와 알려진 소비자를 증명하며 모노레포 전체의 독립적인 정답 집합을 증명하지는 않는다.
- 새 파일 생성으로 기존 모듈 우선순위가 바뀌는 경우와, 선언만 있다가 패키지 원본이 생기는 경우를 native TypeScript 통합 테스트로 확인했다. 후자의 추가 누락을 측정 중 발견해 수정했다.
- [통합 테스트](results/2026-10-13/integration.txt) 370/370, [관련 단위 테스트](results/2026-10-13/unit.txt) 25/25가 통과했다. oxlint, typecheck, build, `pnpm format`도 실행했다.

다른 의미 기반 지원 언어에서는 Python 2건, Rust 1건, Ruby 1건의 누락·실패를 재현했다. 이번 요청의 추가 검토 결과이며 구현 수정은 남아 있다. 원인·대조군·검증 공백은 [검토 보고서](review.md)에 정리했다.
