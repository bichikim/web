# 지원 언어의 사용처 누락 검토

이 문서는 발견 당시의 기록이다. 네 재현 사례는 이후 수정했으며, 현재 검증과 남은 한계는 [후속 수정 검토](../language-aliases/review.md)에 정리했다.

검토 범위는 TypeScript/JavaScript, Python, Rust, Ruby의 정의·사용처 검색과 별칭·프로젝트 경계다. 전체 위험도는 보통이다. P0/P1은 확인되지 않았다. TypeScript 최적화의 재현 사례는 수정했으며, 다른 언어에서 P2 네 건을 확인했다. 이 네 건은 추가 검토 결과이며 이번 성능 수정에서는 고치지 않았다.

## P2 발견 사항

### 1. Python 원본과 스텁 사이의 참조 연결 누락

- 영향: `core.py`와 대응하는 `core.pyi`가 함께 있으면 구현 함수에서 검색한 사용처가 비어 있을 수 있다.
- 원인: [Python 검색](../../src/server/create-python-navigation.ts#L39)은 선택한 위치의 참조만 받는다. 별칭 보완도 그 결과에서 출발하므로, 원본 조회가 비어 있으면 스텁으로 연결되는 소비자까지 확장하지 못한다.
- 검증: 같은 파일 세트에서 `core.py:greet` 조회는 0개, `core.pyi:greet` 조회는 소비자의 import·별칭·호출 위치를 반환했다. 호출의 정의 조회에는 원본과 스텁이 모두 포함됐다.
- 수정 방향: 분석기의 의미 정보로 확인한 원본·스텁 대응을 사용해 양쪽 참조를 합치고 중복·정의 위치를 정리해야 한다. 파일 이름만으로 심볼을 합치면 동명 심볼을 잘못 연결할 수 있다. 수정안 자체의 동작은 아직 검증하지 않았다.

### 2. Python 중첩 프로젝트의 설정 미적용

- 영향: 모노레포 내부 소비자 프로젝트의 `pyrightconfig.json`에 설정한 `extraPaths`가 적용되지 않아 import와 사용처가 누락된다.
- 원인: [분석기 생성](../../src/server/create-python-navigation.ts#L23)은 뷰어 루트 하나를 전달한다. 현재 경로에는 소비자별 설정 컨텍스트 선택이나 통합이 없다.
- 검증: `apps/consumer/pyrightconfig.json`의 `extraPaths`로 `packages/core/src/api.py`를 참조하는 fixture에서 뷰어의 정의·사용처 조회가 모두 0개였다. 동일한 Pyright를 소비자 디렉터리로 직접 초기화한 대조군에서는 원본 정의가 반환됐다. 소비자 폴더만 뷰어 루트로 열면 원본이 그 경계 밖에 놓이므로, 그 결과를 설정 검증의 대조군으로 사용하지 않았다.
- 수정 방향: 프로젝트 설정이 적용된 컨텍스트에서 소비자를 검증하되, 결과를 전체 뷰어 루트 안에서 합쳐야 한다. 실행 환경 설정의 통합 또는 프로젝트별 분석기 선택에 대한 별도 정확도·메모리 비교가 필요하다.

### 3. Rust의 독립 Cargo 프로젝트 소비자 조회 실패

- 영향: 같은 뷰어 루트 안에 있지만 공통 Cargo workspace에 속하지 않은 앱이 라이브러리를 path dependency로 쓰면, 라이브러리에서 사용처 조회가 실패한다.
- 원인: [프로젝트 선택](../../src/server/create-rust-navigation.ts#L26)은 조회한 라이브러리의 프로젝트를 고른다. [후보 검증](../../src/server/create-rust-navigation.ts#L57)도 그 분석기를 사용하므로 소비자 크레이트의 의존성 컨텍스트를 알지 못한다.
- 검증: 라이브러리 사용처 조회가 세 번 모두 `rust-analysis-failed`였다. 소비자 호출에서 정의 조회는 원본을 찾았다. 루트에 공통 workspace와 두 member를 선언한 대조군에서는 동일한 별칭 import·바인딩·호출 세 위치가 반환됐다.
- 수정 방향: 후보 파일이 속한 Cargo 프로젝트 컨텍스트로 정의를 검증하고, 원본의 정규화된 정의 위치와 비교해야 한다. 프로젝트별 분석기 재사용과 중복 크레이트 처리 비용도 확인해야 한다.

### 4. Ruby 상수 별칭을 통한 사용처 누락

- 영향: `Alias = Original` 이후 `Alias.new`를 호출해도 `Original` 클래스의 사용처 조회에 그 호출이 포함되지 않는다.
- 원인: [별칭 확장](../../src/server/ruby/reference-handler.ts#L15)은 `MethodAlias`만 대상으로 한다. 상수 별칭의 이름을 따라가는 확장이 없다.
- 검증: 원본 클래스 조회는 `Alias = Original`의 오른쪽 값만 반환했다. 별칭 자체의 조회에서는 바인딩과 `Alias.new` 호출이 반환됐다. 메서드의 `alias welcome greet`를 쓰는 대조군에서는 별칭 호출이 정상 반환됐다.
- 수정 방향: 분석기에서 확인한 상수 별칭 관계를 따라 참조를 확장해야 한다. 재할당, 같은 이름의 다른 네임스페이스, 순환 별칭을 구분하는 검증이 필요하다.

## 검증 공백

1. 다른 언어 결과는 위의 작은 재현 fixture와 대조군으로 검증했다. 모든 실제 프로젝트의 완전한 정답 집합을 구축한 것은 아니다.
2. Python의 여러 인터프리터·복잡한 대입 별칭, Rust의 procedural macro·생성 소스·feature 조합, Ruby의 동적 메타프로그래밍은 이번 검토에서 전수 검증하지 않았다.
3. `SOLARGRAPH_BINARY`로 외부 서버를 지정하는 경로는 현재 실행한 기본 Ruby 서버와 다르며, 그 경로의 별칭 확장·부분 결과 동작은 별도 검증이 필요하다.
4. TypeScript에서 여러 원본을 묶은 선언 맵의 개별 원본 연결은 이전 검증 범위와 마찬가지로 남아 있다. 이번 성능 수정으로 해결한 기능은 아니다.

## 구조·명명 검토

관련 호출부, 분석기 소유·해제, 후보 검증과 결과 정규화, 파일 배치를 함께 검토했다. 위 동작 문제 외에 별도의 P3/P4 제안은 추가하지 않는다. TypeScript 모듈 해석 재사용은 별도 파일에 두었고, 인덱스 준비는 기존 캐시의 생명주기에 묶어 오류·취소 결과를 처리한다.

## 범위 밖

위 P2 네 건의 구현 수정과, 문법 강조만 지원하는 언어의 의미 기반 탐색 구현은 이번 작업에 포함하지 않았다.

재현 결과와 실행 코드 사본은 `results/2026-10-13/languages.jsonl`, `language-controls.jsonl`, `languages.mts.txt`, `language-controls.mts.txt`에 보존한다.
