# TypeScript 프로젝트 분할 분석 실험

2026-10-13 비교 결과, **프로젝트별 설정은 별칭 조회의 정확도를 높였지만, 모든 프로젝트를 분석하고 합치는 방식은 그대로 적용하기 어렵다.** 실제 검색 경로는 변경하지 않았다.

## 비교 방식

- `unified`: 검색 대상 파일의 설정으로 전체 파일을 분석하는 기존 `createLanguageService.scanReferences` 경로.
- `split`: 가장 가까운 `tsconfig.json`별로 파일을 나누고, 각 설정으로 순차 분석한다. 대상 파일의 프로젝트를 먼저 처리하고 분석기를 유지한다.
- `split-release`: 동일하게 분석하되 프로젝트마다 분석기를 해제한다.

분할 방식은 각 프로젝트에 검색 대상 원본 파일을 추가한다. 각 분석기가 반환하는 참조를 작업 폴더 기준 파일 경로·문자 오프셋·길이로 중복 제거한다. `DocumentRegistry`는 공유하며, 후보 탐색과 전체 의미 분석은 기존 구현을 재사용한다. 프로젝트의 `include`·`exclude`로 조회 파일을 제거하지 않아 뷰어의 파일 탐색 범위를 유지한다. 이 분할은 편집기의 프로젝트 관리 전체를 구현한 것이 아니다.

## 실제 모노레포 결과

TypeScript 6.0.3, Node 24.15.0, macOS arm64. 코드 파일 6,516개, 가장 가까운 설정 기준 25개 프로젝트. 각 조건 3회 중앙값이며 단위는 초다. 최초 조회는 파일 목록 탐색·프로젝트 분류 시간을 포함한다. 재조회는 같은 프로세스에서 분석을 완료한 직후 실행한다.

| 대상           | 상태   | 기존 첫 결과 / 완료 | 분할·해제 첫 결과 / 완료 |
| -------------- | ------ | ------------------: | -----------------------: |
| `fileRevision` | 최초   |       0.705 / 6.370 |           0.745 / 15.973 |
| `fileRevision` | 재조회 |       0.136 / 0.282 |           0.292 / 15.129 |
| `getWindow`    | 최초   |       1.587 / 7.663 |           0.663 / 17.016 |
| `getWindow`    | 재조회 |       0.385 / 0.385 |           0.225 / 16.296 |

첫 결과는 분석기의 첫 비어 있지 않은 배치가 실험 소비자에 도착한 시점이다. UI 표시나 RPC·worker 전달·영속 인덱스 검증은 포함하지 않는다. OS 파일 캐시는 비우지 않았다. 최초 분석 완료 시간의 편차가 컸으므로 원시 데이터의 범위도 함께 확인해야 한다. 특히 `fileRevision`의 기존 분석 단계 완료 시간은 약 6.0~15.3초였다. 이전 UI 측정값과 직접 비교할 수 없다.

두 대상은 모든 반복에서 기존·분할 결과의 정확한 위치 집합이 각각 13개·22개로 일치했다. 그러나 `getWindow`의 알려진 앱 호출은 두 방식 모두 누락했다. 따라서 이 일치는 전체 정확성의 증명이 아니다.

분석기를 모두 유지하는 `split`은 실제 모노레포에서 두 번 모두 약 4GB 힙 한도에 도달해 종료했다. 공유 registry만으로 분석기별 프로그램·checker 상태의 비용을 해소하지 못했다. 이 조건은 완료 시간을 비교할 수 없다.

`split-release`도 최대 RSS가 기존보다 높았다. 최초 조회의 중앙값은 `fileRevision`에서 기존 2,627MiB / 분할 3,038MiB, `getWindow`에서 기존 2,645MiB / 분할 2,813MiB였다. `dispose()`는 즉시 OS 메모리를 반환한다는 보장이 없으며 재조회 때 다시 분석해야 한다. 측정값은 프로세스 누적 최대 RSS이며 JS 힙 사용량과 다르다.

두 대상 모두 선택된 프로젝트에서 모든 반환 위치를 찾았고, 나머지 24개 프로젝트는 새로운 위치를 추가하지 않았다. 분할·해제의 첫 조회에서 결과를 추가하지 않은 프로젝트의 분석 시간 합계 중앙값은 각각 약 14.5초·15.9초였다. 모든 프로젝트에 원본을 넣고 순회하는 비용이 완료 시간을 지배했다.

## 누락 검증

각 fixture는 무관한 동명 선언 2,000개와 프로젝트 밖 파일을 포함한다. 기대 위치는 실제 작성한 import·별칭 선언·재내보내기·호출로 별도 구성했으며, 무관한 동명 선언이 결과에 섞이지 않는 것도 검사했다. 각 조건의 최초·재조회·3회 반복에서 결과 집합은 일정했다.

| 사례                                                          | 기대 위치 | 기존 | 프로젝트별 합치기 |
| ------------------------------------------------------------- | --------: | ---: | ----------------: |
| 공통 설정: 별칭, 연쇄 재내보내기, namespace, 프로젝트 밖 호출 |        14 |   14 |                14 |
| 소비자 프로젝트에만 있는 `paths` 별칭                         |        14 |   11 |                14 |
| 빌드된 `.d.ts` 및 실제 컴파일러가 생성한 declaration map      |        17 |   14 |                14 |

`paths` 사례에서는 소비자의 `@public` 설정을 적용해야 `apps/consumer/use.ts`의 세 참조를 찾는다. 기존 실제 `workspace.references` API에서도 11개만 반환했다.

선언 파일 사례에서는 `apps/built/use.ts`의 import 이름·별칭 선언·호출 세 참조가 누락됐다. 기존 실제 API도 14개를 반환했으며, 소비자에서 정의를 조회하면 원본 대신 `packages/core/dist/entry.d.ts`를 반환했다. 같은 fixture를 설치된 TypeScript의 `tsserver`에 전달하고 원본·소비자 파일을 열어 조회하면 정의를 제외한 **17개가 수동 기대 위치 집합과 정확히 일치**했다. 이 검증은 정확성 비교이며 tsserver의 성능은 측정하지 않았다.

실제 모노레포의 기존 API에서도 `apps/coong/src/components/service-worker/ServiceWorker.tsx` 49·93줄의 `getWindow()` 호출이 결과에 없었다. 현재 패키지 배포 선언과 원본 소스 사이의 연결은 별도 해결이 필요하다. 이 실험에서는 제품 코드를 수정하지 않았다.

## 검토 결론

검토 범위는 실험 코드·분석기 호출·프로젝트 설정·실행 결과다. 동작, 책임과 생명주기, 이름과 배치를 검토했다. P0/P1은 발견하지 않았고, 적용 전에 해결할 P2 세 항목은 남아 있다. 제품 수정은 이번 실험 범위에 포함하지 않았다.

| 확인된 항목                             | 원인과 관찰                                                                                 | 해결 방향과 비용                                                                                                          |
| --------------------------------------- | ------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| P2: 분할 분석기의 메모리·완료 비용      | 유지형은 두 번 모두 힙 부족으로 종료했다. 해제형은 24개 무기여 프로젝트의 분석을 반복했다.  | 정의가 연결된 프로젝트만 선택하고 분석기 수를 제한한다. 프로젝트 간 연결을 정확하게 판별하는 비용이 필요하다.             |
| P2: 기존 조회의 프로젝트별 `paths` 누락 | 기존 실제 API는 소비자 별칭 세 위치를 누락했다. 소비자 설정으로 분할하면 14/14다.           | 설정별 해석을 보존한다. 하나의 설정으로 모든 파일을 해석하는 방식을 수정해야 한다.                                        |
| P2: 원본·생성 선언 간 참조 연결 누락    | 기존 API·단순 분할은 declaration map 사례에서 14/17, tsserver는 기대 집합과 같은 17/17이다. | 프로젝트와 source mapper를 통한 정의 위치 연결이 필요하다. 단순 결과 합치기보다 복잡하지만 정확성을 위해 필요한 부분이다. |

1. **전체 프로젝트 순회 방식은 적용 보류.** 분석기 유지형은 메모리 한도로 실패하고, 해제형은 완료·재조회 비용이 커졌다. 초기 병렬화도 먼저 적용하지 않는다. 동시 분석은 이번에 측정하지 않았으며 메모리 비용을 따로 검증해야 한다.
2. **프로젝트별 설정과 심볼 위치 연결은 다음 실험 대상으로 채택할 근거가 있다.** `paths` 사례는 실제로 개선됐다. 다만 원본을 각 프로젝트에 추가하는 대신, 그 프로젝트의 소스·생성 선언에서 같은 정의가 어디에 있는지 매핑한 뒤 조회해야 한다.
3. **관련 프로젝트 선택과 완전성 보장을 함께 설계한다.** 설치된 tsserver의 `getPerProjectReferences`는 프로젝트에 해당 위치가 있는지 확인하고 원본/생성 위치·심볼 연결을 따라 조회를 확장한다. 단순히 이름이 없거나 패키지 밖이라는 이유로 제외하면 안 된다. 판별 불가능한 경우의 전체 조회 경로도 필요하다.
4. 다음 비교는 tsserver의 프로젝트 관리·source mapper를 재사용하는 방식과 경량 프로젝트 그래프를 사용하는 방식으로 좁히는 것이 타당하다. 기존 후보 기반 첫 결과 전달을 유지하면서 완전성 조회를 결합할 수 있는지 검증해야 한다. **tsserver가 실제 모노레포에서 더 빠르다는 증거는 아직 없다.**

TypeScript도 전체 사용처 조회의 정확성을 위해 관련 프로젝트를 메모리에 로드한다고 설명한다. [공식 설명](https://www.typescriptlang.org/tsconfig/disableReferencedProjectLoad.html), [프로젝트 참조 성능 고려사항](https://github.com/microsoft/TypeScript/wiki/Performance#performance-considerations).

## 검증 범위와 한계

- 실제 실행: 78개 측정 결과, 기대 위치 집합 검사, 기존 workspace API 조회, tsserver 선언 매핑 비교, 유지형 메모리 실패 재현.
- 타입 검사·oxlint·oxfmt를 실행했다. 제품 동작 변경이 없으므로 전체 제품 테스트나 UI 재빌드는 이 실험의 정확성 근거로 사용하지 않았다.
- 두 실제 심볼과 세 fixture의 결과다. 메서드·상속·ambient/global·symlink·복수 설정 소속·`jsconfig`·source map 없는 패키지의 일반적 정확성은 미검증이다.
- UI 첫 표시, 취소, 편집 초안, 파일 변경 중 조회, 프로세스 재시작 후 영속 인덱스와의 통합은 미검증이다. 동일 프로세스 재조회와 프로세스 재시작을 구분해야 한다.
- 결과 집합 합치기는 실험 경로에만 있으며 제품의 스트리밍·취소·캐시에 연결하지 않았다.
- 별도의 P3/P4 구조 변경 제안은 없다. 위 동작 문제의 해결 없이 추상화나 파일 분리를 추가할 근거는 부족하다.

## 재현

패키지 디렉터리에서 실행한다. `node --import tsx benchmarks/project-analysis/measure.ts <작업폴더> <대상파일> <검색시작문자열> <모드>`는 최초·재조회 JSON을 stdout에, 프로젝트별 시간을 stderr에 출력한다.

```sh
node --import tsx benchmarks/project-analysis/measure.ts /absolute/path/to/web packages/codex-code-viewer/src/server/file-revision.ts 'fileRevision =' unified
node --import tsx benchmarks/project-analysis/measure.ts /absolute/path/to/web packages/codex-code-viewer/src/server/file-revision.ts 'fileRevision =' split-release
node --import tsx benchmarks/project-analysis/create-fixture.ts paths
```

fixture 생성 명령은 임시 작업 폴더를 출력한다. 그 폴더에서 `packages/core/entry.ts`의 `greet`를 같은 측정 명령으로 조회한다. 다른 fixture 이름은 `shared`, `declarations`다. 분석기를 유지하는 비교는 `split` 모드를 사용한다.
