# 전체 완료 병목 최적화

2026-10-14. 기존 [언어별 누락 수정](README.md)을 모두 포함한 실행본과 이번 최적화를 같은 현재 모노레포에서 비교했다. TypeScript `fileRevision` 전체 완료 중앙값은 **7.681→7.451초(3.0% 감소)**, `getWindow`는 **8.359→7.466초(10.7% 감소)**다. 첫 결과는 거의 같았으며, JavaScript·Python·Rust·Ruby의 완료 시간에는 뚜렷한 개선을 확인하지 못했다. 모든 검색이 몇 초 안에 끝나도록 해결한 결과는 아니다.

## 확인한 병목과 변경

CPU 프로파일에서 동기 파일 읽기·stat·open이 크게 나타났고, [진단용 단계 측정](results/2026-10-14/completion-stages-stderr.jsonl)에서는 전체 TypeScript 프로그램 준비가 참조 수집보다 오래 걸렸다. 진단용 실행에는 추가 계측 비용이 있으므로 이 시간과 최종 속도 표를 직접 비교하지 않는다. 현재 프로그램은 의존 선언을 포함해 약 18,490개 소스를 읽는 사례였다. [소스 수·단계 기록](results/2026-10-14/completion-preload-stages-stderr.jsonl).

- [조회 단위 파일시스템 캐시](../../src/server/create-navigation-file-system.ts#L15): 파일·디렉터리 존재 확인, 설정 파일 읽기, 디렉터리 목록, realpath의 반복 조회를 재사용한다. 없던 파일이 새로 생겨도 다음 조회에서 다시 확인하도록 시작·종료 경계에서 비운다. 독립 경로 확인의 음수 캐시가 다음 검색을 막던 사례도 재현 후 수정했다. [시작 경계](../../src/server/create-language-service.ts#L70), [실패 증거](results/2026-10-14/completion-filesystem-boundary-before.txt).
- [소스 사전 읽기](../../src/server/create-source-snapshots.ts#L67): 선택한 전체 루트의 아직 읽지 않은 소스를 64개씩 비동기로 준비한다. 기존 스냅샷과 편집 중 원문을 유지하며, UTF-8/BOM·UTF-16 양쪽 바이트 순서, 취소와 dispose 후 늦게 도착하는 읽기를 처리한다. 미래의 동일 수명 경계에서도 오래된 읽기가 캐시를 채우지 않도록 작은 세대 번호 검사를 추가했다.
- [전체 범위 판정 조기 종료](../../src/server/create-reference-scope.ts#L179): 외부 선언 연결 때문에 전체 문맥이 필요해지면 나머지 파일의 사전 요약을 끝낸다. 컴파일러에 넘기는 전체 후보 목록은 유지한다. [사전 읽기 호출을 확인한 실패 사례](results/2026-10-14/completion-scope-before.txt).

프로젝트별 별칭, `.d.ts` 원본 연결, 최종 네이티브 참조 검증과 별칭 결과 병합은 유지했다. 재귀적으로 외부 의존성까지 미리 읽는 시도는 파싱·해석이 중복되어 실제 비교에서 느려졌으므로 최종 코드에서 제거했다. [폐기한 중간 실험 요약](results/2026-10-14/completion-intermediate-summary.json). 중간 수치를 최종 개선 수치로 사용하지 않는다.

## 비교 조건

수정 전 번들은 `/tmp/code-viewer-language-coverage-speed/after`의 복사본이며 이전 누락 수정까지 모두 포함한다. 주요 TypeScript 사용처는 독립 프로세스 5쌍, 나머지는 3쌍을 전후 교대로 실행했다. 각 프로세스는 빈 CODEX_HOME에서 시작하며 별도 warmup을 호출하지 않는다. 첫 결과는 첫 비어 있지 않은 서버 배치, 완료는 최종 검증을 포함한 스트림 종료, 재조회는 완료 후 동일 workspace에서 다시 요청한 시간이다. 브라우저 paint 시간은 측정하지 않았다. 파일 읽기가 끝난 뒤부터 타이머를 시작한다. OS 파일 캐시는 지우지 않았으며 측정 중 빌드·테스트·소스 수정은 하지 않았다.
