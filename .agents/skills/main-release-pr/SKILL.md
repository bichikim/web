# main 배포 PR 생성

사용자가 이 스킬을 명시적으로 호출했을 때만 실행한다. 일반 작업 PR 생성 규칙 대신 이 스킬의 브랜치 이름과 PR 대상을 적용한다.

## 절차

1. 저장소, `origin` 원격, 현재 브랜치와 작업 트리 상태를 확인한다. 기존 변경을 커밋하거나 이동하지 않는다.
2. `origin`에서 `dev`와 `main`을 fetch하고 최신 `origin/dev` 커밋을 배포 기준으로 기록한다. fetch 실패 시 오래된 로컬 브랜치로 대체하지 않는다.
3. `origin/main...origin/dev`의 커밋과 diff를 확인한다. main에 반영할 변경이 없으면 PR을 만들지 않고 알린다. 충돌이 있으면 임의로 해결하거나 배포 범위를 변경하지 않고 보고한다.
4. 실행 시점의 `Asia/Seoul` 시간을 `YYYY-MM-DD-HH-mm` 형식으로 구해 `-main`을 붙인다. 이 이름에는 별도 접두사를 붙이지 않는다. 같은 이름의 로컬 또는 원격 브랜치가 있으면 덮어쓰지 않고 중단해 충돌을 알린다.
5. 기록한 `origin/dev` 커밋에서 해당 이름의 로컬 브랜치를 만든다. 현재 체크아웃은 전환하지 않아 기존 작업을 유지한다. 생성한 브랜치의 커밋이 기록한 기준과 같은지 확인한 뒤 해당 브랜치만 `origin`에 일반 push한다. force push는 하지 않는다.
6. GitHub MCP 또는 인증된 `gh`로 head를 생성한 브랜치, base를 `main`으로 지정해 배포 PR을 만든다. 기본은 draft이며 사용자가 ready PR을 요청하면 따른다. 제목에는 배포 날짜를, 본문에는 `Summary`와 `Testing`을 포함한다. 실제 diff를 요약하고 실행한 검증과 미실행 항목을 구분한다. CLI로 여러 줄 본문을 전달할 때는 임시 파일과 `--body-file`을 사용한다.
7. 응답이 불명확하면 원격 브랜치와 해당 head/base의 PR 상태를 조회한 뒤 재시도 여부를 결정한다. 중복 PR을 만들거나 기존 브랜치를 다른 커밋으로 갱신하지 않는다.
8. GitHub에서 PR URL, draft 상태, base가 `main`인지, head 이름과 커밋이 배포 기준과 일치하는지 확인한다. Codex의 PR 첨부 도구가 있으면 생성한 PR을 현재 채팅에 첨부한다. URL과 브랜치 이름, 검증 결과를 보고한다. 검증 실패 시 생성 여부와 남은 문제를 구분해 알린다.

## 실행 범위

- PR 생성까지 수행한다. PR 병합, 배포 실행, 태그 생성은 별도 요청이 있어야 한다.
- CI 완료 대기나 지속적인 모니터링은 요청받았을 때만 수행한다.
- 인증이나 권한 오류는 환경의 실행 권한 지침에 따라 재시도하고, 해결되지 않으면 정확한 차단 원인을 보고한다.
