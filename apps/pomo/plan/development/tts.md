# 온디바이스 TTS

[개발 기술 계획으로 돌아가기](../development.md)

## 합성과 목소리

`sherpa-onnx`의 Supertonic 3 INT8 모델을 사용한다. 앱인토스 빌드에는 모델을 포함하지 않고 사용자가 처음 대사를 설정하기 전에 Vercel Blob에서 내려받아 플랫폼의 바이너리 저장소에 영속 저장한다. 앱인토스와 웹 브라우저 모두 WebAssembly와 CPU를 사용해 기기에서 음성을 합성하며, TTS 서버는 두지 않는다.

최초 출시에서는 Supertonic 3의 여성형 기본 목소리 `F1`~`F5`를 같은 한국어 대사로 비교한 뒤, 캐릭터와 잘 어울리는 2~3개를 선정해 제공한다. 마이크로 녹음한 음성을 사용자 샘플 목소리로 저장하는 기능과 녹음의 최소·최대 길이는 추후 결정하고 구현한다.

선정된 각 목소리의 짧은 한국어 미리 듣기 음원은 앱 번들에 포함하며, 사용자가 목소리를 선택할 때 즉시 재생한다.

사용자는 캐릭터 목소리 하나를 선택하며 이후 새로 합성하는 대사에 공통으로 적용한다. 목소리 설정을 변경해도 이미 생성된 음성 파일은 자동으로 다시 합성하지 않으며, 기존 음성의 관리는 사용자에게 맡긴다.

최초 출시에서는 시작 대사 1개와 종료 대사 1개를 저장하고 각 시점에 재생한다.

## 실행과 저장

TTS 모델 로딩과 추론은 전용 Web Worker에서 실행한다. 메인 스레드는 SolidStart UI와 Needle Engine 렌더링을 담당하고, Worker는 합성된 음성 데이터를 영속 저장 호환 계층으로 전달한다. TTS 작업은 낮은 우선순위 큐에서 한 번에 하나씩 순차 실행한다.

사용자가 작성한 대사는 외부 서버로 전송하지 않는다. 앱인토스 실제 WebView에서 모델 로딩 시간, 합성 속도, 메모리 사용량과 3D 장면 동시 실행을 검증한다.

기기의 CPU 성능이 부족하면 TTS 합성 중 3D 렌더링의 프레임레이트를 잠시 낮추고 `말 연습 중…` 상태를 표시한다. 그래도 부족하면 3D 렌더링을 일시 정지한다. 음성 합성이 끝나면 정상 프레임레이트로 복귀하고 대사를 재생한다.

사용자가 대사를 지정하면 낮은 우선순위로 음성을 천천히 합성한다. 결과는 `Blob`이나 `File` 같은 재생 가능한 파일 데이터로 만들어 영속 저장소에 보관한다. OS 파일 쓰기 API는 요구하지 않는다. 대사를 수정하면 기존 음성 파일 데이터를 새로 생성한 데이터로 교체한다.

## 타이머 시점의 대사

뽀모도로 시작·종료 시 음성 파일이 아직 준비되지 않았어도 타이머는 즉시 진행한다. 해당 대사는 자막만 표시하고 스피커 아이콘에 로딩 상태를 보여주며, 뒤늦게 완성된 음성을 해당 시점에 재생하지 않는다.

대사 음성이 없거나 준비되지 않았을 때 별도의 기본 알림음은 재생하지 않는다.

대사 자막은 음성이 있으면 재생이 끝날 때까지 표시하고, 음성이 없으면 5초 동안 표시한다.

3D 장면, 타이머와 음악은 모델 다운로드 전에도 사용할 수 있다. 대사 설정에 진입하면 모델 다운로드가 필요하다고 안내하며, 다운로드가 끝날 때까지 대사 설정과 TTS 기능은 비활성화한다.

## 다운로드 정책

앱인토스에서는 모델 다운로드 직전에 `getNetworkStatus()`를 확인한다. `WIFI`가 아니면 모바일 데이터 사용으로 추가 요금이 발생할 수 있다고 경고하고, 사용자가 확인하면 다운로드를 진행한다. `OFFLINE`이면 인터넷 연결이 필요하다고 안내한다.

일반 브라우저에서 네트워크 종류를 확인할 수 없으면 `데이터 요금이 발생할 수 있다`고 경고하고, 사용자가 확인하면 다운로드를 진행한다.

새 TTS 모델 버전이 있으면 사용자에게 다운로드를 안내하며 자동으로 내려받지 않는다. 기존 모델은 새 버전 다운로드가 완전히 끝날 때까지 유지하고, 다운로드가 완료된 뒤 새 버전으로 교체한다.

모델은 하나만 관리하므로 별도의 모델 관리 화면은 제공하지 않는다. 설정에는 `모델 새로 받기` 버튼만 두며, 기존 모델은 새 다운로드와 검증이 끝날 때까지 유지한 뒤 교체한다. 그 밖의 모델 저장과 교체는 앱 내부에서 자동으로 관리한다.

## 모델 자산 배포

모델 파일은 `public`과 같은 레벨의 `blob` 폴더에 두고 일반 Git으로 관리한다. 모델 업데이트는 자주 하지 않으므로 최초 출시에서는 Git LFS를 사용하지 않는다.

개발 모드에서는 Vite 개발 서버가 `blob` 폴더를 가상 Blob URL로 제공한다. 앱은 로컬 파일을 직접 가져오지 않고 운영 환경과 동일하게 `fetch()`로 모델을 내려받는다.

운영 배포에서는 GitHub Actions가 `blob` 폴더를 Vercel Public Blob에 동기화한 뒤 앱을 배포한다. `BLOB_READ_WRITE_TOKEN`은 GitHub Secret에 저장하고 클라이언트에는 노출하지 않는다.

GitHub Actions는 모델 버전과 파일별 URL, 크기, SHA-256 체크섬을 담은 manifest를 생성한다. 모델 파일은 버전별 경로에 업로드하고 기존 파일을 덮어쓰지 않는다.

앱은 내려받은 모델 manifest를 사용하기 전에 Zod 스키마로 검증한다.

앱은 Vercel Public Blob의 HTTP Range 요청을 사용해 모델 파일을 나누어 내려받고 진행 위치와 부분 데이터를 플랫폼의 바이너리 저장소에 저장한다. 중단 후에는 마지막으로 저장한 바이트부터 이어받는다.

- 응답이 `206 Partial Content`이면 기존 부분 데이터에 이어 붙인다.
- 응답이 `200 OK`이면 기존 부분 데이터를 버리고 해당 파일을 처음부터 저장한다.
- 다운로드가 끝나면 파일 크기와 SHA-256 체크섬을 검증한다.
- 검증에 실패하면 해당 파일만 다시 내려받는다.
- 모든 파일의 검증이 끝난 모델만 활성화한다.
