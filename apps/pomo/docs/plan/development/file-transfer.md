# 도구: 두 기기 간 파일 전송 계획

상태: 기존 Pomo 서버에서 핸드셰이크만 중개하도록 수정했다. 별도 시그널링 앱과 영구 저장소는 사용하지 않는다. 공개 배포와 데스크톱·모바일 실기기 검증은 남았다.

## 서버 역할과 배포 조건 (2026-09-30)

- 기존 Pomo의 `/api/transfer/socket` WebSocket이 연결 생성·참가·수락·SDP·ICE 후보만 처리한다. 별도 Worker 앱·Durable Object·DB·객체 저장소·전용 시그널링 주소 설정은 제거했다.
- 대기 중인 두 연결을 찾기 위한 세션 ID, 참가 비밀값, 소켓 참조는 해당 서버 프로세스의 메모리에만 잠시 둔다. SDP·ICE는 상대에게 즉시 전달하며 저장하지 않는다. 파일 이름·내용·청크는 이 경로로 보내지 않는다.
- 두 기기가 DataChannel 연결 완료를 알리면 세션과 참가 비밀값을 삭제하고 두 WebSocket도 닫는다. 이후 파일 전송은 서버 연결 없이 계속한다. 연결 도중 한쪽이 나가면 세션도 삭제한다. 서버 재시작으로 대기 정보가 사라지면 새 QR을 만든다.
- 참가·핸드셰이크 유효기간은 생성 후 5분이다. 기한 검사는 메시지와 새 연결 생성 시 수행한다. 주기적 타이머는 두지 않으므로, 아무 이벤트가 없는 만료 세션은 다음 메시지/생성 또는 소켓 종료 때 정리한다. 대기 세션은 최대 100개로 제한한다.
- 이 메모리 방식은 두 기기의 소켓이 같은 Pomo 서버 프로세스에 연결되는 환경을 전제로 한다. Vercel의 현재 WebSocket 문서는 새 연결들이 같은 함수 인스턴스에 도착할 것을 보장하지 않는다. **현재 Vercel 배포에 그대로 적용하면 두 기기가 서로를 찾지 못할 수 있다.** 서버 메모리 방식으로 출시하려면 기존 Pomo 서버의 단일 인스턴스 운영 또는 동일 인스턴스 연결 라우팅을 먼저 확정해야 한다. 공유 DB를 자동으로 추가하지 않는다. [Vercel WebSocket 배포 조건](https://vercel.com/docs/functions/websockets), [Nitro WebSocket](https://nitro.build/docs/websocket)
- 수정 후 로컬 Chromium 두 페이지에서 A→B·B→A 파일을 다운로드하고 내용 일치를 확인했다. 파일 선택 전에 양쪽 시그널링 소켓이 종료됐으며, 전송 중 추가 시그널링 메시지가 없었다. 같은 초대 주소의 재참가도 거절됐다. QR 참가자와 생성자 모두 홈의 같은 도구 모달을 사용하며, 다른 도구로 전환·모달 닫기와 재열기·클라이언트 내 링크 이동 뒤에도 연결이 유지됐다. 기존 세션 주소로 참가하는 것도 확인했다. 이는 같은 컴퓨터의 로컬 웹 검증이다.
- 기존 도구 목록과 Pomo 홈의 공통 도구 모달을 사용한다. 새 QR은 `/?tool=transfer&session=...#참가비밀값`으로 홈의 파일 전송 탭을 자동으로 연다. 기존 `/transfer`, `/transfer/:sessionId` 주소도 홈으로 연결한다. 처음 방문한 기기도 시작 버튼을 누르지 않고 전송 화면을 사용할 수 있다. 어느 쪽이든 파일당 100 MiB 이하 파일 하나를 제안하고 수락받아 직접 전송한다. 수신 크기와 CRC32를 검사한 뒤 사용자가 다운로드한다. 100 MiB는 실험 한도이며 실기기 출시 보장값이 아니다.
- 데스크톱 도구 창은 전송 세션 활성 중 숨기고 다시 열 때 기존 WebView를 재사용한다. 실제 Tauri 창의 닫기·재열기·파일 저장, 다른 네트워크와 iOS·Android 브라우저 검증은 남았다. 앱인토스는 후속 검증 전까지 기능을 노출하지 않는다.

출시 전 남은 항목: 기존 Pomo 배포의 소켓 라우팅 조건 확정, 다른 네트워크에서 직접 ICE 연결과 실패 안내 확인, 데스크톱과 모바일 실기기의 저장·창 수명·메모리 측정, 서비스 측 연결 남용 제한과 운영 관측. URL·비밀값·SDP·ICE는 운영 로그와 분석에 남기지 않는다.

## 받은 파일 화면과 임시 보관 (2026-09-30)

- `모든 파일 받기 허용`을 켜면 현재 연결 상대의 파일 제안을 자동 수락한다. 이미 수락 대기 중인 파일도 즉시 수락하며, 파일 크기와 무결성 검사는 유지한다. 기본값은 꺼짐이고 연결 종료·오류·새 연결 시 초기화한다. 수신은 임시 보관까지이며 디스크 저장은 사용자가 선택한다.

- 받은 파일은 겹치지 않는 가로 한 줄의 카드로 표시한다. 좌우로 스크롤해 파일을 확인하며 각 카드에서 바로 저장하거나 삭제할 수 있다. 이미지는 미리보기를 표시하며, 표시할 수 없는 이미지와 다른 파일은 형식별 아이콘 또는 일반 파일 아이콘으로 보여 준다.
- 클라이언트 보관 한도는 총 300 MB로 정했다. 초과하면 오래된 파일 내용부터 삭제하고, 회색 카드에 사유를 남긴다. 개별 삭제도 카드를 즉시 제거한다. 용량 초과로 남은 회색 카드는 삭제된 파일 정리로 제거한다. 모두 삭제는 파일 내용과 모든 카드 기록을 즉시 제거한다. [보관 정책 구현](../../../src/features/file-transfer/received-files.ts)
- 개별 저장과 모두 저장을 제공한다. 모두 저장은 남아 있는 파일만 ZIP으로 묶으며, 같은 파일명은 구분해서 포함한다. 저장 버튼 실행은 브라우저에 다운로드를 요청한 것이므로 실제 기기 저장 완료로 표시하지 않는다.
- 도구 전환과 연결 종료 후에도 현재 페이지의 수신 목록은 남는다. 새로고침·페이지 종료 뒤 보존은 제공하지 않는다. ZIP 생성 중에는 파일 데이터 외에 임시 출력 메모리가 필요하므로 300 MB는 전체 프로세스 메모리 제한이 아니다.
- 연결 후 QR과 주소는 연결 정보 보기로 접는다. 완료된 초대 주소를 다시 사용할 수 없다는 안내를 함께 표시한다.
- 로컬 Chromium에서 실제 WebRTC 연속 수신, 이미지 디코딩, 개별 파일 바이트, ZIP 내용, 삭제·정리와 연결 종료 후 보관을 확인했다. 모바일 너비의 화면을 확인했으며, 100 MB Blob 네 개를 보관 목록에 넣는 실험으로 한도 초과와 회색 카드 정리도 검증했다. 이 용량 실험은 WebRTC로 400 MB를 전송한 검증이 아니다.

## 목표와 결론

기기 A 또는 B가 `도구 → 전송`에서 일회용 QR 코드와 같은 주소를 만든다. 다른 기기는 QR을 스캔하거나 주소를 복사해 세션에 들어온다. 연결 후에는 **세션을 만든 쪽과 참가한 쪽 모두** 파일을 선택해 상대에게 보낼 수 있다. 받는 쪽이 파일을 수락하고 저장한다. 계정 로그인은 필수로 두지 않는다.

**1차는 서버가 연결 정보만 중개한다.** QR/URL은 짧은 일회용 세션 주소이며, 두 기기는 서버를 통해 WebRTC 제안·응답·ICE 후보를 교환한다. 연결 후 파일 본문은 `RTCDataChannel`로 기기끼리 직접 전송한다. Pomo 서버에 파일을 업로드·저장·중계하지 않는다. 따라서 다른 기기가 주소를 한 번 열면 별도의 응답 QR 스캔 없이 연결 절차를 진행할 수 있다. WebRTC는 시그널링 수단을 정해 두지 않으므로 서버는 연결 정보를 전달하는 역할만 맡는다. [WebRTC 세션 수명과 시그널링](https://developer.mozilla.org/en-US/docs/Web/API/WebRTC_API/Session_lifetime)

직접 연결이 막힌 네트워크에서 TURN을 사용하면 파일 바이트가 TURN 서버를 경유한다. **1차는 TURN을 쓰지 않고 직접 연결 실패를 안내하기로 결정했다.** 인터넷을 통한 연결에는 STUN 주소 조회가 필요할 수 있다. 서버를 쓰는 범위는 핸드셰이크 정보로 제한한다. [STUN·TURN 설명](https://developer.mozilla.org/en-US/docs/Web/API/WebRTC_API/Protocols)

현재 Pomo의 [`worker-rpc`](../../../src/features/worker-rpc/index.ts#L31-L51)는 브라우저 내부 Worker 요청용이며 기기 간 전송에 사용하지 않는다. 도구 목록은 [`Content.tsx`](../../../src/components/tools/Content.tsx#L7-L49)에 있고, 일반 화면과 데스크톱 대화상자가 이를 공유한다. 기존 도구 버튼과 모달 진입점은 [`PTools.tsx`](../../../src/components/p-tools/PTools.tsx#L10-L48)에 있다. 따라서 새 최상위 버튼 대신 기존 도구 목록에 `전송`을 추가한다.

## 방식 선택

| 방식                               | 적합한 점                                                  | 비용·제약                                                                      | 판단                 |
| ---------------------------------- | ---------------------------------------------------------- | ------------------------------------------------------------------------------ | -------------------- |
| WebRTC DataChannel + 최소 시그널링 | QR 한 번으로 세션에 들어가고 연결되면 파일을 직접 주고받음 | 작은 연결 정보 서버가 필요함. 제한된 네트워크에서는 직접 연결이 실패할 수 있음 | **1차 권장**         |
| WebRTC + 카메라로 읽는 화면 신호   | 서버 없이 제안·응답을 교환할 수 있음                       | 양쪽 화면·카메라가 필요하고 전송량·인식률을 확인해야 함. 추가 스캔이 필요함    | 후속 실험            |
| WebRTC + 소리 신호                 | 화면 신호의 보조 수단이 될 수 있음                         | 마이크 권한과 주변 소음에 영향받음                                             | 보조 후보            |
| WebRTC + TURN                      | 직접 연결이 어려운 네트워크에서도 연결 가능성이 높아짐     | 파일이 TURN 서버를 경유하고 대역폭 비용이 발생함                               | 1차에서 제외         |
| 서버 경유 WebSocket 전송           | 연결 경로가 단순하고 중앙에서 상태를 제어하기 쉬움         | 파일 바이트가 서버를 통과하고 장시간 연결·대역폭을 감당해야 함                 | 현재 요구에서는 제외 |
| 임시 객체 저장소 업로드/다운로드   | 상대가 나중에 받아도 됨                                    | 보관·삭제·접근 제어·저장 비용이 추가됨                                         | 현재 요구에서는 제외 |

화면 신호는 일반 QR 한 장에 모든 연결 정보를 넣는 방식뿐 아니라, 화면에 연속으로 표시한 코드 프레임을 카메라가 읽는 방식도 실험한다. 1차 연결을 이 방식에 의존시키지 않는다. 소리는 노이즈와 권한 문제 때문에 화면 신호가 어려울 때의 보조 후보로만 둔다. 파일 본문까지 카메라 신호로 옮길지는 별도 요구와 전송 속도 실험이 있을 때 판단한다.

## 사용자 흐름

1. 어느 기기에서든 `도구 → 전송 → 연결 만들기`를 누른다. 서버에서 짧게 유효한 세션을 만들고 화면에 QR과 바로 아래 복사 가능한 HTTPS 주소를 표시한다. 주소에는 짧은 세션 식별자와 참가 비밀값을 담는다.
2. 다른 기기가 QR을 스캔하거나 주소를 열면 Pomo 홈에서 기존 도구 모달의 파일 전송 탭이 열린다. 참가 정보를 읽은 뒤 주소에서 세션과 비밀값을 지운다. 서버는 두 기기의 연결 정보만 교환한다. 첫 기기에 참가 요청을 보여 주고 수락하면 연결한다. 별도의 역방향 QR 스캔이나 소리 교환은 요구하지 않는다. 연결 전에는 파일을 받지 않는다.
3. 두 화면 모두 `파일 보내기`와 `받은 파일` 영역을 제공한다. 보내는 쪽이 파일을 선택하면 받는 쪽에 이름·크기를 보여 주고 수락을 기다린다. 수락 후 전송률, 취소, 완료·실패를 양쪽에 표시한다.
4. 받는 쪽은 완료된 파일을 명시적으로 저장한다. 저장 성공 여부를 보내는 쪽의 전송 완료와 구분한다. 양쪽 중 누구든 다음 파일을 보낼 수 있다.
5. 연결을 닫거나 참가 기한이 지나면 기존 주소로 새 기기가 들어오지 못하게 한다. 이미 연결된 두 기기의 전송은 QR 참가 기한과 별개로 유지한다. Pomo 안에서 도구를 바꾸거나 도구 창을 닫아도 전송은 계속하고, 다시 열면 진행 상태를 보여 준다. 앱 자체를 종료하거나 네트워크가 끊기면 진행 중 전송을 실패로 표시하고 새 연결을 만든다. 1차에는 중단 지점 재개를 약속하지 않는다.

## 기술 설계

- **시그널링:** 기존 Pomo 서버의 WebSocket으로 생성·참가·수락과 SDP·ICE 후보만 중개한다. 두 소켓을 매칭하는 정보만 프로세스 메모리에 잠시 두며 영구 저장하지 않는다. 직접 연결 완료 시 해당 정보를 버리고 서버 연결도 끝낸다. 배포는 두 기기가 같은 서버 프로세스에 도착하는 조건을 확인한 뒤 진행한다.
- **연결:** `RTCPeerConnection`에 STUN을 구성하고 직접 연결을 우선한다. STUN은 접속 주소를 찾는 데 쓰며 파일 본문을 중계하지 않는다. 어느 쪽이 QR을 만들었든 연결 후 같은 송신·수신 UI를 사용한다. 연결 상태 변경 이벤트로 준비·끊김을 처리한다. TURN은 기본 전송 경로에 넣지 않고, 직접 연결 실패율을 측정한 뒤 별도 선택한다.
- **화면과 수명:** WebRTC 연결과 파일 송수신은 도구 콘텐츠보다 오래 살아 있는 앱 영역이 소유한다. 도구 모달·탭과 데스크톱 대화상자는 상태를 표시하고 명령을 보낸다. 데스크톱 대화상자를 닫아 해당 창이 사라져도 실제 연결 소유 영역이 유지되는지 확인한다. 앱 종료·새로고침에서 종료와 정리를 처리한다.
- **파일:** 전송 전 파일 메타데이터와 수락 메시지를 교환한다. 파일을 작은 청크로 나누고 `RTCDataChannel`의 송신 버퍼 상태에 맞춰 흐름을 제어한다. 브라우저별 최대 메시지 크기를 넘기지 않는다. 전송 ID·청크 순서·총 크기·최종 무결성 검사를 정의하고, 이름을 정규화해 표시·저장한다. [DataChannel 전송 한계](https://developer.mozilla.org/en-US/docs/Web/API/RTCDataChannel/send), [버퍼 상태](https://developer.mozilla.org/en-US/docs/Web/API/RTCDataChannel/bufferedAmount)
- **초기 한도:** 1파일·1전송씩, 파일당 100 MiB를 실험 시작값으로 둔다. 이 수치는 플랫폼 보장값이 아니다. 모바일 메모리·저장 API와 직접 전송 성능을 측정해 출시 한도를 정한다. 메모리에 파일 전체를 중복 보관하지 않는 수신 경로를 우선 검토한다.
- **접근 제어:** QR 주소를 가진 사람은 참가를 요청할 수 있으므로 생성 기기의 명시적 수락을 요구한다. 참가 비밀값은 URL fragment에 두어 일반 HTTP 요청에 자동으로 실리지 않게 하고, 클라이언트가 서버에 별도로 제시하면 서버는 대기 세션의 임시 비밀값과 비교한다. URL·비밀값·SDP·ICE 후보를 로그와 분석 이벤트에 남기지 않는다. 만료·중복 참가·메시지 크기·요청 빈도를 서버에서 제한한다. WebRTC 데이터 채널은 전송 중 암호화되지만, 상대가 보낸 파일은 열기 전에 사용자가 판단해야 한다.

## 검토에서 확인한 보완점

- **직접 연결 실패:** 1차는 TURN 없이 실패를 안내한다. 일부 네트워크에서 전송 자체가 불가능할 수 있으므로, 검증 때 선택된 ICE 후보 쌍을 확인해 실제 직접 경로와 실패율을 구분해 기록한다. [ICE 연결 통계](https://developer.mozilla.org/en-US/docs/Web/API/RTCIceCandidatePairStats)
- **도구 화면 수명:** 현재 도구 콘텐츠는 선택에 따라 바뀐다([`Content.tsx`](../../../src/components/tools/Content.tsx#L44-L68)). 결정에 따라 도구를 바꾸거나 일반 모달·데스크톱 대화상자를 닫아도 전송을 유지한다. 앱의 연결 소유 영역과 데스크톱 창 사이 상태 전달 방법을 구현 전에 확인한다. 휴대폰에서 Pomo를 OS 백그라운드로 보내거나 화면을 잠근 동안의 지속 전송은 1차 보장 범위에서 제외한다. 복귀하면 연결·전송 상태를 확인하고, 끊겼다면 실패를 표시한다.
- **QR 진입 경로:** 현재 도구는 모달 안에서 열리므로 QR의 HTTPS 주소가 새 기기에서 전송 화면을 직접 열 수 있는 경로가 필요하다. 웹의 새로고침·언어 경로와 앱인토스의 외부 주소 진입을 각각 확인한다. 주소가 만료되거나 잘못됐을 때도 도구 화면에서 이유를 보여 준다.
- **실제 저장:** 수신 완료와 사용자의 기기 저장 완료는 다르다. iOS·Android·앱인토스·데스크톱에서 저장 성공을 확인할 수 있는 범위와 큰 파일의 메모리 사용량을 실험하고, 확인할 수 없는 플랫폼에는 전송 완료만 표시한다.
- **지원 범위:** 앱인토스의 QR 주소 진입·파일 저장 또는 WebRTC가 실기기에서 막히면 웹·데스크톱을 먼저 출시하고 앱인토스는 후속 작업으로 둔다. 해당 플랫폼에는 동작하지 않는 전송 기능을 노출하지 않는다. 일반 웹 성공을 앱인토스 성공으로 간주하지 않는다.

## 플랫폼 검증과 결정 항목

| 대상            | 필요한 확인                                                                                                                                                     |
| --------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 일반 웹·PWA     | HTTPS 진입, QR 카메라 스캔 또는 URL 복사, 파일 선택·저장, 백그라운드 전환 후 연결 상태                                                                          |
| 모바일 브라우저 | iOS Safari·Android Chrome에서 큰 파일 수신 시 메모리 사용, 다운로드와 취소 동작                                                                                 |
| 앱인토스        | 외부 QR 주소가 Pomo 화면으로 열리는지, WebView의 WebRTC DataChannel·파일 선택·다운로드가 가능한지 실기기 확인. 막히면 1차 기능을 노출하지 않고 후속 작업으로 둠 |
| 데스크톱 앱     | [`도구 대화상자`](../../../src/components/desktop-dialog/Tools.tsx#L10-L25)의 닫기·창 이동 중 연결 수명과 파일 저장 경로 확인                                   |

시그널링은 기존 Pomo 서버의 WebSocket과 일시적인 메모리 매칭으로 정했다. 파일 크기 출시 한도는 실기기 측정 후 확정한다. 카메라 화면 신호의 구현 여부는 1차 전송 검증 후 판단한다.

## 구현 순서와 완료 기준

1. **최소 연결 실험:** 실제 Pomo 배포 출처에서 짧은 QR/URL 진입, 서버의 제안·응답·ICE 후보 전달, STUN 직접 연결을 확인한다. A 또는 B 어느 쪽이 시작해도 같은 Wi-Fi와 서로 다른 네트워크에서 실험한다. 앱인토스 실기기를 포함하고 실패 원인을 단계별로 기록한다. 서버에는 파일 바이트를 보내지 않는다.
2. **세션 기반:** 일회용 생성·참가·명시적 수락·만료·종료와 두 기기 상태 동기화를 구현한다. 대기 연결에서 중복 참가를 막고, 직접 연결 완료 시 초대 정보를 삭제해 재사용을 막는다.
3. **양방향 파일:** 두 기기 모두 파일 선택·수락·청크 전송·취소·진행률·완료 확인·저장을 구현한다. 0바이트, 한도 초과, 연결 끊김, 거절을 각각 처리한다.
4. **도구 통합:** 기존 도구 목록과 번역 메시지에 `전송`을 추가하고 QR 주소에서 전송 화면을 직접 여는 경로를 연결한다. URL 복사·새로고침·키보드 탐색·작은 화면 배치를 검증한다. 도구·모달·데스크톱 대화상자를 닫았다 다시 열어도 전송과 진행 상태가 유지되는지 확인한다. 집중 타이머와 음악 상태도 유지한다.
5. **출시 검증:** 웹·PWA·모바일 브라우저·데스크톱 앱에서 실제 지원 범위를 기록한다. 앱인토스도 실기기에서 검증하되 막히면 웹·데스크톱을 먼저 출시하고 앱인토스는 후속으로 둔다. 서로 다른 네트워크에서 직접 연결을 통한 양방향 전송, 파일 바이트/체크섬 일치, 세션 재사용 차단, 수신 거절과 중단 시 정리를 확인한다. 서버가 연결 정보만 처리하고 파일 본문이 서버·객체 저장소로 전송되지 않는지도 확인한다.

후속 실험에서는 화면에 연속으로 표시되는 코드 프레임을 카메라로 읽어 서버의 시그널링을 대체할 수 있는지 측정한다. iOS·Android·앱인토스의 카메라 권한, 화면 밝기·반사, 인식률, 데이터 크기와 재시도를 확인한다. 소리 신호는 화면 방식의 보조 후보로만 평가한다.

완료는 문서나 단위 테스트만으로 판단하지 않는다. 1차 지원 플랫폼인 웹과 데스크톱에서 **A가 만든 링크로 B가 들어온 경우 A→B와 B→A가 모두 실제 파일 저장까지 성공**해야 한다. B가 링크를 만든 경우도 같은 순서로 검증한다. 앱인토스 실기기에서 실패하면 1차 지원 범위에서 빼고 실패 원인과 후속 해결 계획을 남긴다.
