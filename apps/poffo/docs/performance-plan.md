런타임에 구조적 개선을 적용하며 새 런타임 의존성을 추가하지 않는다.

## 적용 순서

1. **좌표 캐시의 임시 객체 줄이기.** 부모 공간의 지연 변환은 점 하나의 x/y를 함께 계산한다.
   같은 점을 Map에서 다시 찾는 대신 Float64 버퍼와 초기화 표시를 사용한다. 기존 숫자 배열 조회,
   지연 평가, 이전 프레임 스냅샷, 실패 시 재시도 계약은 유지한다.
2. **정적 바인딩 메타데이터 재사용.** 반복 범위는 불변 파라미터 정의 배열과 바인딩 ID 배열을
   기준으로 캐시한다. 문서 편집으로 정의가 교체되면 새 결과를 사용한다. ID 순서, 없는 ID,
   중복 정의의 기존 첫 항목 선택을 보존한다.
3. **실측 후 유지 여부 결정.** 두 변경을 각각 비교한다. 실제 이득이 없는 변경은 제거한다.
   추가로 필요한 경우에만 정적 장면 의존성의 재사용과 변경 전파를 별도 실험한다.

재생 전용 굽기, WASM/Rust 이식, GPU 변형, 마스크 아틀라스 재설계는 이번 변경에 섞지 않는다.
굽기는 원본 리그를 보존하는 파생 캐시로 설계할 수 있지만, 물리의 반복 경계와 입력 변경에 따른
무효화 계약이 먼저 필요하다. 이 항목들은 이번 검증 완료를 뜻하지 않는다.

## 검증 기준

- JS 계산 최적화는 같은 파일·브라우저·해상도·AA로 비교한다. AA 비교에서는 AA만 바꾸고
  원본 PNG와 캔버스 크기를 유지한다. 원본 PNG를 축소하거나 대체하지 않는다.
- FPS와 프레임 준비 단계별 시간을 함께 기록한다. 검사·빌드와 성능 측정은 동시에 실행하지 않는다.
- Idle·Walk의 여러 시점에서 기존 변형 계산과 최종 정점을 비교한다.
- 확대율별 화면을 대조하고 GPU 오류를 확인한다. 포즈와 입력을 고정한 비교를 사용한다.
- 지연 평가의 최초 샘플링, 배열 반영·동결, 실패 후 재시도, 문서 교체를 테스트한다.
- Puppet·Poffo의 단위·통합·브라우저 테스트, 타입 검사, 빌드, lint와 포맷을 확인한다.

## 적용 결과와 측정 범위

1·2번을 구현했다. 점의 x/y를 한 번에 저장하는 Float64 버퍼로 Map 조회와 점 객체의 보관을
줄였고, 반복 범위는 문서 정의와 바인딩 ID 배열이 유지되는 동안 재사용한다. 이전 프레임의
배열을 다음 프레임에서 덮어쓰지 않는다. Glue 준비는 별도 진단에서 약 1~2ms여서 변경하지 않았다.

원본 WhiteCat 모델을 WebKit의 같은 브라우저 세션에 유지하고 기준→변경→변경→기준 순서로
각 10초간 비교했다. 기준 경로는 기존 Map 점 캐시·스칼라 좌표 버퍼와 비캐시 반복 범위 조회다.
두 경로는 같은 모듈 인스턴스를 사용하며, 실제 측정 창에서는 검사와 빌드를 실행하지 않았다.

| 항목                    | 기준 경로의 두 측정 | 변경 경로의 두 측정 |
| ----------------------- | ------------------- | ------------------- |
| FPS                     | 6.88 / 5.74         | 8.53 / 8.06         |
| 프레임 준비 중앙값      | 88 / 100ms          | 64 / 71ms           |
| 디포머·Glue 적용 중앙값 | 49 / 55ms           | 36 / 39ms           |

이는 macOS·WebKit 개발 서버, 화면 1100×1000, DPR 1, 캔버스 1908×2385,
해상도 배율 0.265, 4배 MSAA 조건의 결과다. 원본 8192 PNG 두 장을 그대로 사용했다.
실행 부하에 따른 변동이 있으므로 다른 기기·브라우저나 배포 빌드의 FPS를 보장하지 않는다.
GPU 시간만 따로 측정한 수치도 아니다. 30/60fps에는 아직 미치지 못한다.

- Idle·Walk 각각 4개 시점에서 최종 정점 좌표 551,232개를 대조했고 최대 차이는 0이었다.
- 고정 시점 8개와 확대율 16단계의 화면 24쌍은 픽셀 단위로 같았다.
- 같은 검증에서 4배 MSAA와 캔버스 크기를 확인했으며, 조회 시 GPU 오류는 0이었다.
- 이 비교는 두 좌표 캐시 방식의 동등성을 확인한다. Live2D Core와의 화질·성능 대조는 아니다.

다음 후보는 정적 장면 의존성의 재사용과 변경된 입력의 전파 범위다. 적용 전 단계별 실측으로
효과를 확인한다. 프레임 굽기나 물리 계산 생략을 이미 적용한 것으로 해석하지 않는다.

## 30fps 목표의 추가 작업

목표는 원본 WhiteCat Walk를 같은 화질과 물리로 30fps 이상 재생하는 것이다. 아직 달성하지
못했다. 사용자의 결정에 따라 JS 최적화를 계속한다. JS의 한계를 입증하기 전에 WASM으로
옮기거나 툴체인을 설치하지 않는다.

### 현재 적용한 경로

- 불변 바인딩의 색상 채널과 관련 파라미터 ID를 준비해 두고, 최신 입력과 결과만 재사용한다.
- 네이티브 부모 공간의 warp·rotation에는 렌더러가 소유한 좌표 평가기를 사용한다. 문서에
  원래 저장된 리그와 배열을 수정하지 않으며, 로컬 좌표와 부모를 거친 좌표의 무효화를 구분한다.
  지원 범위를 벗어나는 바인딩·스키닝·공간 메시 등은 기존 일반 평가기를 사용한다.
- 격자 보간과 단일 회전 구간에서 기존 Float64 연산 순서와 가중 단계의 반올림을 유지한다.
- 중첩 마스크도 픽셀이 같으면 먼저 한 번만 렌더링한다. 각 수신부의 반전 설정은 유지한다.
  완전히 빈 마스크는 한 픽셀의 투명 타깃을 유지한다. 일반 over 합성에서 그 마스크로 완전히
  가려진 파츠는 장면과 좌표를 유지하면서 그리기만 생략한다.
- 같은 해상도에서 움직이는 마스크 타깃의 용량을 재사용한다. 해상도 변경과 비활성화 시에는
  크기를 다시 조정한다. 원본 이미지, 캔버스 크기와 MSAA 샘플 수는 바꾸지 않는다.

### 측정과 남은 차이

Chrome/Metal, Apple M5 Pro, 화면 1100×1000, DPR 1, 캔버스 1908×2385, 해상도 배율
0.265, 실제 4배 MSAA 조건이다. 실제 주 화면의 render 호출 수와 RAF 수를 함께 확인했다.
위 WebKit 결과와 브라우저가 다르므로 두 FPS를 직접 개선 배율로 비교하지 않는다.

| 측정                                               | 실제 Walk FPS | 프레임 준비 중앙값 | 디포머·Glue 중앙값 |
| -------------------------------------------------- | ------------- | ------------------ | ------------------ |
| Chrome 창을 띄운 실행, 각 20초                     | 18.86 / 18.56 | 26 / 27ms          | 19 / 20ms          |
| 빈 마스크 생략까지 적용한 headless Chrome, 각 20초 | 17.96 / 18.56 | 28 / 27ms          | 20 / 20ms          |

빈 마스크 생략과 최근 효과 캐시는 뚜렷한 FPS 상승을 입증하지 못했다. 중첩 마스크 공유는
별도 진단에서 마스크 render 호출을 프레임당 56회에서 21회로 줄였지만, 그것만으로 30fps를
달성했다는 뜻은 아니다.

원인을 분리하는 진단에서는 좌표 준비를 멈춰도 약 17.5fps, 마스크 패스까지 생략해도 약
18fps였다. 모델을 그리지 않을 때는 약 59fps였다. 이 조건들은 제품 성능이나 완료 기준으로
사용하지 않는다. 명시적인 WebGL flush·finish도 이득이 없어 제품 코드에 넣지 않았다.
Chrome 추적에는 그래픽 명령 제출을 기다리는 구간이 관찰됐지만, GPU 타이머의 값은 동기
완료 시간·실제 프레임 간격과 일치하지 않아 GPU 단독 시간으로 채택하지 않았다.

현재 변경과 이 단계 시작 전 소스를 대조한 결과는 다음과 같다.

- Idle·Walk 각 6개 시점의 최종 정점 좌표 826,848개와 파라미터는 차이가 0이었다.
- 포즈 12개와 확대율 16단계의 화면 28쌍 중 26쌍은 픽셀까지 같았다. Walk 2.49초의 1픽셀과
  확대율 0.15의 4,868픽셀에서 색상 채널 값이 최대 1 차이였다. 완전한 픽셀 동일성으로
  보고하지 않는다.
- 같은 검사에서 원본 8192 PNG 두 장, 4배 MSAA와 캔버스 크기를 유지했고 GPU 오류는 0이었다.

다음 단계는 실제 장면의 렌더링 패스·픽셀 처리량을 나눠 측정하고, 격자 셀의 반복 조회 비용도
함께 검증하는 것이다. 지금의 증거로는 JS 최적화가 소진됐거나 WASM이면 30fps가 된다고
결론 낼 수 없다. 전체 회귀 검사는 성능 측정과 분리해 실행한다.

## AA·렌더러 선택과 추가 비교

사용자가 AA 방식과 WebGL/WebGPU를 직접 선택하고, 자동 선택도 제공하도록 확정했다.
3D 편집 오버레이는 WebGL을 사용하며, 편집을 마치면 요청한 렌더러로 복귀한다. 이 절부터는
위의 MSAA 고정 검증과 구분한다. AA 대체를 허용한 뒤에도 리그·물리·문서 의미는 유지한다.

### 설정과 생명주기

- Poffo 헤더의 렌더링 설정에서 렌더러 자동·WebGL·WebGPU와 AA 자동·SSAA·기존 MSAA를
  선택한다. Poffo의 자동 AA는 기존 표시 해상도의 SSAA를 사용한다. Puppet 직접 호출에서
  AA를 생략하거나 자동으로 지정하면 기존 MSAA를 유지한다.
- 렌더러 자동은 PixiJS 8.22의 WebGL 우선 순서를 따른다. 명시한 렌더러를 지원하지 않으면
  다른 렌더러로 조용히 바꾸지 않는다. 초기화가 실패하면 기존 화면을 유지하고 오류를 알린다.
- SSAA는 각 표시 축의 2배 해상도와 기존 최대 backing-buffer 제한을 사용한다. MSAA 선택은
  같은 해상도에 멀티샘플링도 적용한다. 텍스처나 마스크를 별도로 축소하는 설정이 아니다.
- 설정은 브라우저의 `poffo:rendering:v1`에 저장한다. 모델 JSON, 공유 문서의 revision,
  undo/redo와 복구 스냅샷에는 넣지 않는다. 잘못된 저장값은 자동으로 초기화한다.
- GPU 리소스만 교체한다. 플레이어 인스턴스·재생 위치·물리 적분 상태·표정·외부 파라미터와
  카메라는 유지한다. 준비 중에도 기존 플레이어가 계속 재생하며 최신 프레임을 새 리소스에
  적용한다. 프레임을 다시 계산하거나 물리를 초기화하지 않는다.
- 연속 요청은 마지막 요청만 적용하고 이전 요청의 리소스를 해제한다. 준비 도중 문서가
  바뀌면 최신 문서에 맞춘다. 해제 후 도착한 요청도 리소스를 해제한다.
- 평소 Editor·Studio·Viewer 이동은 같은 캔버스를 유지한다. GPU 컨텍스트 종류를 바꾸거나
  AA를 명시적으로 변경할 때만 새 캔버스를 사용한다. 3D 편집의 WebGL 전환도 이 경로다.
- 팝오버에서 요청한 선택값과 현재 실제 렌더러·AA를 함께 조회한다. 3D 편집 중에도 저장된
  WebGPU 선택값을 덮어쓰지 않는다.
- 처음 선택한 렌더러의 초기화가 실패해도 설정을 지원되는 렌더러로 바꾸면 다시 시작한다.
  준비 중 설정이나 문서가 바뀐 경우에는 오래된 실패로 최신 요청을 막지 않는다. 최신 문서
  자체의 적용 오류는 숨기거나 무한 재시도하지 않고 기존 오류 계약대로 알린다.

### Worker 선계산 실험 — 2026-10-27

사용자 요청에 따라 전용 Worker에서 최대 1·2·3프레임 앞의 정점과 표시 상태를 계산하는
프로토타입을 비교했다. 제품 파일 대신 별도 개발 서버의 HTTP 응답에 실험 연결을 주입했다.
기본 재생 경로와 공개 Player API에는 아직 반영하지 않았다.

Worker는 기존 Player의 모션·물리·포즈·디포머·Glue 계산을 그대로 사용한다. 메인 스레드는
원본 텍스처와 기존 GPU 렌더러를 유지하고, 계산된 Float32 정점과 파츠·레이어·마스크·색상·
불투명도·그리기 순서의 표시 계획을 적용한다. 모션 한 바퀴를 녹화해 반복하거나 프레임을
보간하는 방식은 아니다. 원본 문서·리그·공유 undo/redo의 소유권도 이전하지 않는다.

실험 조건은 원본 WhiteCat, Walk:0, 물리 활성화, Chrome/Metal/M5 Pro, DPR 2, WebGL,
기존 2배 SSAA다. Studio 성능 검사와 Viewer 입력 검사 모두 렌더 캔버스는 1248×1560이다.
원본 두 8192 텍스처는 메인 스레드에 유지하며 Worker의 문서 복사본에서만 이미지 문자열을
제외한다. 이 측정의 절대 FPS를 다른 크기의 Viewer 측정과 직접 비교하지 않는다.

#### 버퍼와 입력 처리

- 생성 요청은 한 번에 하나다. Worker가 상태를 순서대로 진행하고, 메인 스레드가 마지막으로
  표시한 프레임을 확정하면 이전 체크포인트를 버린다. 정점 버퍼의 소유권은 양쪽에서 번갈아
  넘겨 재사용한다. 같은 포즈의 중복 렌더를 새 프레임 FPS로 세지 않는다.
- 즉시 반영 정책은 입력 시 미래 큐를 비우고 세대를 바꾼다. Worker는 마지막 표시 시점의
  물리·모션 누적값·정점·표시 상태를 복원한 뒤 명령을 적용한다. 이전 세대의 응답은 거부한다.
  미래 상태에서 입력을 적용하거나 물리를 처음부터 초기화하지 않는다.
- 비교용 FIFO 정책은 이미 계산한 미래 프레임을 먼저 표시한다. 입력 지연이 커져 채택하지
  않는다. 실시간 입력을 사용할 때는 큐 무효화와 되감기가 필요하다.

첫 구현에서 물리 상태만 복원하자 재개 직후에 미래 정점이 남았다. 재개 명령은 프레임을
다시 평가하지 않을 수 있으므로 마지막 렌더 결과도 체크포인트에 포함하도록 수정했다.

원인이 확정되지 않았으므로 백엔드 간 픽셀 동일성을 주장하거나 자동 선택을 WebGPU로
바꾸지 않는다.

회귀 검사에서는 Puppet·Poffo 단위 테스트 2,460개와 통합 테스트 173개, 브라우저 테스트
10개가 통과했다. Wallpaper의 Player 테스트 대역에도 새 조회·설정 메서드를 반영했고 관련
9개 테스트가 통과했다. Puppet·Poffo 빌드와 세 앱·패키지의 타입 검사도 통과했다.
브라우저 테스트는 기본 모델의 설정·이동·호환성을 검사하므로 위 원본 성능 측정과 구분한다.

### 축소 시 자글거림과 밉맵 확인

사용자는 확대가 아니라 작게 표시했을 때의 자글거림이 문제였다고 설명했고,
2026-10-27 현재 화면에서는 자글거림이 없어졌다고 확인했다. 현재 화질 설정을 유지하며
자글거림을 없애기 위한 추가 AA·필터·해상도 변경은 적용하지 않는다.

원본 텍스처의 밉맵 생성과 linear 필터링은 기존부터 켜져 있었다. 이번에는 원본 WhiteCat을
직접 열어 GPU 상태를 조회했다. 8192×8192 두 장 모두 밉맵 레벨 수 14, 최대 레벨 13이며,
실제 축소 필터는 `GL_LINEAR_MIPMAP_LINEAR`(9987)였다. 선언만 확인한 것이 아니라 GPU의
트라이리니어 필터 설정까지 확인한 결과다. 원본 텍스처를 낮은 해상도로 교체한 것은 아니다.

Canvas 2D의 [`imageSmoothingEnabled`](https://html.spec.whatwg.org/multipage/canvas.html#image-smoothing)는 WebGL 옵션이 아니다. 현재 자동 AA는 2배 표시
밀도의 SSAA이고, FXAA·SMAA 실험은 제품에 넣지 않았다. 어느 변경이 사용자가 보던
자글거림 해소에 가장 크게 기여했는지는 분리하지 않았으므로 단정하지 않는다.

### 3프레임 선계산 제품 적용 — 2026-10-27

앞의 Worker 프로토타입은 비교 실험 기록이다. 이번에는 같은 수치 계산 경로를 제품의
선택 가능한 재생 경로로 연결했다. 서비스 UI·설정 저장은 Poffo가, 계산·재생 수명과
공개 API는 Puppet이 소유한다. 원본 문서·리그·물리·텍스처·AA와 undo/redo는 변경하지 않는다.

- Viewer의 **렌더링 → 프레임 버퍼**는 기본 켜짐이며 브라우저의 `poffo:buffering:v1`에
  선택을 저장한다. Editor·Studio의 기본 경로는 바꾸지 않는다.
- 라이브러리는 `createPlayer({buffering: true, ...})`로 선택하며 기본값은 꺼짐이다.
  별도 `configurePlayerBuffering`·`getPlayerBufferingInfo` API와 상태 콜백을 제공한다.
  기존 `Player`의 필수 메서드·동기 반환·예외·명령 직후 조회를 유지한다.
- 최대 세 프레임의 정점·표시 계획·물리 체크포인트를 Worker에서 계산한다. 텍스처와 GPU는
  메인 스레드에 남는다. 시간 간격은 처리량과 화면 갱신에 맞추며 **30fps 상한을 두지 않는다**.
- 최초 제품 적용에서는 입력이 미래 큐와 세대를 즉시 무효화했다. 아래 연속 입력 개선에서 이 경로를 보강했다. 연속 입력 중에는 기존 루프로 시간을 진행하고,
  입력 없이 실제 세 프레임이 지난 뒤 마지막 표시 상태에서 선계산을 재개한다. 물리를
  초기화하지 않으며 입력마다 최초 큐 채우기 지연을 반복하지 않는다.
- 오디오·독립 추가 모션·사용자 난수·모션 콜백·자동 눈 깜박임은 설정을 기억한 채 기존
  경로로 실행한다. 실제 상태는 `unsupported`로 조회한다. 미래에 외부 부수효과를 실행하지
  않는다. 동적 비호환 조건이 사라지면 선계산으로 복귀한다.
- Worker 실패는 마지막 표시 상태에서 기존 경로로 복귀하며 `error`를 알린다. 명시적으로
  다시 켜면 재시도한다. 숨김·문서 교체·끄기·종료는 오래된 응답을 적용하지 않는다.

#### WhiteCat Walk 실측

| 중앙값, OFF→ON      | 고개 XYZ | 시선 XY |
| ------------------- | -------: | ------: |
| 명령 호출 시간      |   12→0ms |  12→0ms |
